# Operator checkpoints and isolated recovery

Current implementation: `photo-worker backup-create`, `backup-status`, `backup-prune`, and `backup-restore`. Commands are host-operator entrypoints, never HTTP/job APIs. They require the installed worker wheel with the `restore` dependency group, privileged dedicated PostgreSQL sessions, Docker socket access and explicitly installed tools. No backup, migration or drill was executed while implementing this path.

## Capture installation

Use a private operator-owned JSON file with schema_version `photo-backup-operator/v1`. The strict loader is `runtime/backup_operator.py::load_operator_config`; unknown/missing keys refuse. Install these fields:

| Fields | Authority |
| --- | --- |
| tools | Exactly docker, compose, pgbackrest, age, tar; each `{path,sha256}`. Absolute regular executable files, trusted owner and no group/other writes. Compose is a separately pinned standalone binary; a floating Docker plugin is not accepted. |
| compose_file, compose_sha256, compose_rendered_sha256, project | Exact installed production Compose and project. Pin SHA of canonical JSON from its fully resolved config, including private installed `.env` inputs; each control call rechecks it. Every image must use an immutable @sha256 digest. Running services outside the hardcoded maintenance allowlist refuse capture. |
| database, stanza, pgbackrest_config, pgbackrest_config_sha256 | Dedicated operator database and exact pgBackRest installation. Config must have global repo1-type=s3, repo1-cipher-type=aes-256-cbc and repo1-s3-endpoint matching offhost_endpoint; include/include-path are refused. Credentials stay in this private file. |
| minio_volume, minio_volume_name | Absolute host data-volume directory and actual Docker volume name. Docker volume and MinIO `/data` mount are independently compared before pausing. |
| source_endpoint, source_buckets | Installed TLS MinIO endpoint and exact bucket allowlist. Every ready DB artifact, including expired rows, is streamed at its exact version and checked before capture. |
| offhost_endpoint, offhost_bucket | Independent TLS versioned object repository. It must differ from source_endpoint. DNS/physical independence and disaster credentials require deployment qualification. |
| age_recipients_file, age_recipients_sha256 | Independently installed pinned encryption recipient file. Escrow the corresponding identities separately from the backup. |
| signing_key_file, signing_public_key_sha256 | PEM Ed25519 signing private key and SHA of its 32-byte raw public key. Escrow the public verifier independently; do not obtain it from the backup. |
| config_root | Complete deployment configuration tree including secrets, key versions, model/runtime locks and Caddy configuration. Regular files/directories only; links/devices/hardlinks refuse. Encrypted together, never printed. |
| deletion_history_root | Current independent append-only deletion journal, outside the restored DB namespace. |
| scratch_root, catalogue_root | Separate absolute private directories. Catalogue uses a nonblocking exclusive host lock and durable SQLite publication/withdrawal state. Keep this authority outside restored volumes. |
| maximum_archive_bytes | Positive bounded archive limit. Scratch capacity is checked before copying; all streams have byte limits and cancellation. |

Credentials: PHOTO_BACKUP_DATABASE_URL, PHOTO_BACKUP_SOURCE_ACCESS_KEY, PHOTO_BACKUP_SOURCE_SECRET_KEY, PHOTO_BACKUP_OFFHOST_ACCESS_KEY, PHOTO_BACKUP_OFFHOST_SECRET_KEY. They are not command arguments or evidence fields. Host subprocesses use a minimal environment and the installed local Docker socket.

PostgreSQL must use continuous WAL archiving with archive_mode on/always and archive_timeout 1–900 seconds. The archive_command token vector must be the pinned pgbackrest path followed by `--config=<installed-config> --stanza=<installed-stanza> archive-push %p`. Install this identical pinned binary/config path in the PostgreSQL runtime namespace. pgBackRest configuration must address the actual cluster and encrypted off-host repository. This is an installation prerequisite, not something the backup command silently provisions.

## Capture state and failure policy

Acquire the exclusive operator catalogue lock; verify immutable files/tools and exact volume binding; stop mutators, dispatch, outgoing services and gateways; require no other database client sessions. Verify the complete DB/object closure. Take a new full pgBackRest backup with automatic expiration explicitly disabled and verify its base/WAL/LSN receipt. Create an actual unique PostgreSQL restore point after the full base, switch WAL, wait boundedly for the archive witness, retrieve the required segment through pgBackRest and record its exact SHA/size/timeline. Recheck pause/drain, then stop MinIO and capture the whole data directory including its version metadata. An S3 copy/re-PUT is deliberately not used because it changes version IDs.

Export a verified independent deletion-history snapshot. Tar and age-encrypt MinIO, config and deletion history separately. Upload each encrypted file to an exact versioned checkpoint key and stream it back to verify SHA/size. Publish a signed canonical COMMITTED.json only after all three are verified; read back its exact version and durably record it in the operator catalogue. Only then restart MinIO and the previously running production services.

Any failed/ambiguous capture leaves maintenance in place; there is no automatic `finally/start`. Partial off-host payloads have no committed publication and are not restore points. Preserve operator evidence and investigate before manual service resumption. Restarting an interrupted capture creates a new checkpoint; it never guesses that an old partial upload is complete.

The returned checkpoint_age_seconds and backup-status expose freshness. Schedule capture often enough to keep the last complete object+DB point under 900 seconds and alert on backup-status failure. A full capture pauses the service and may take longer than this bound: this maintenance cost is explicit. Continuous DB WAL alone does not establish object RPO. RPO≤15 minutes/RTO≤4 hours remain measured drill gates; daily execution does not satisfy them.

## Retention and publication authority

backup-prune applies seven daily and four ISO-week points to authenticated publications. Each checkpoint currently has its own full PostgreSQL base and independent encrypted object payloads. It writes and verifies a withdrawal marker before deleting the exact COMMITTED version, exact payload versions and the matching pgBackRest base. The PostgreSQL command is restricted to that set/repository, with maximal retention overrides; other retained bases are checked before/after. Unexpected external dependent backups refuse deletion. The live independent deletion journal is not pruned.

The local withdrawing state is durable before remote operations. Failure leaves the point withdrawn and resumable; it is never re-advertised with missing payloads. At least one retained full base is mandatory. Do not enable an independent pgBackRest expire job or manually mutate its repository: it would bypass publication authority. The [pgBackRest command reference](https://pgbackrest.org/command.html) documents explicit set expiration and its effects on dependent backups/WAL.

## Isolated restore installation

Use a separate private JSON with schema_version `photo-restore-operator/v1`; see the exact closed fields in `backup_restore_operator.py::load_restore_operator_config`. Besides pinned tools and pgBackRest config, supply the independently pinned raw signing public key, independent age identity, off-host endpoint/bucket, database/system_identifier, explicit empty target directories, target MinIO and PostgreSQL uid/gid, independent current deletion-history root, separately installed current consent cluster identity, restored key/witness paths and witness SHA, build SHA, journal/report/scratch roots, and pinned probe configuration.

Storage Compose must contain only postgres/minio on internal nonexternal networks, with no published ports or privileged/network-mode escape. Its project must differ from the source project. Pin both source file and resolved canonical config (compose_rendered_sha256); probe Compose additionally uses probe_compose_rendered_sha256. MinIO `/data` and PostgreSQL data-directory binds must match the independently installed empty target paths exactly. No configuration extracted from the archive is executed. The operator needs network access to these isolated services from its controlled namespace; do not publish them publicly for convenience.

backup-restore requires the exact backup UUID and publication version returned by capture. It rejects a withdrawn publication, verifies its independent Ed25519 signature and required WAL SHA/size, streams every exact encrypted payload/version and verifies bytes, decrypts and manually extracts only regular files/directories into empty private paths. Paths, links, devices, duplicates, limits and cancellation are checked. MinIO file ownership comes from the independently installed target uid/gid. Deletion snapshot directory keeps the original backup UUID. pgBackRest restores the exact full label and named restore point/timeline; only isolated storage is started. The [official recovery options](https://pgbackrest.org/command.html) define named targets and promotion; this avoids treating a backup-end byte boundary as a separately authenticated restore marker. Restored PostgreSQL and MinIO image digests must match captured images. Empty target containers are created, stopped and mount-checked before extraction; PostgreSQL ownership is checked before starting.

Credentials: PHOTO_RESTORE_DATABASE_URL, PHOTO_RESTORE_CONTROL_DATABASE_URL (separate maintenance database for staged reconnect), PHOTO_RESTORE_CONSENT_DATABASE_URL, PHOTO_RESTORE_SOURCE_ACCESS_KEY, PHOTO_RESTORE_SOURCE_SECRET_KEY plus the off-host read credentials above. Restored/control DSNs must use an explicit current isolated PostgreSQL container IP and port5432; the operator binds hostaddr to that verified IP so a DSN/environment cannot redirect to the live original cluster, whose historical system identifier is intentionally identical. The current consent cluster must have a separately pinned system identifier and cannot be the restored historical cluster.

The command then joins existing `recover_isolated_and_report`: closes new restored DB connections, verifies cluster/data-directory/no-other-client isolation, independent deletion watermark, exact physical storage, current consent and actual key decryption witnesses; fences old compute/cleanup/scheduler authority, invalidates intents, reconciles resources/mail/outbox/quarantine and writes a durable report. A newer deletion watermark refuses recovery until reconciliation, without resurrecting the old tenant. The user deletion request does not wait for backup retention expiry.

No writers or production access are authorized by this command. The separate `backup-accept` phase consumes an independently reviewed acceptance config and caller-supplied SHA after real Go replay/report production; it executes real isolated fixtures with the installed embedded worker. Its pinned probe Compose may start only the fixed isolated storage/API/gateway/queue/compute allowlist and an internal certificate-pinned Caddy fixture proxy; it preserves storage image/mount/network bindings and has no production or mail/portal services. All worker, queue, gateway and fixture origins are bound to actual internal project container addresses. Stop it and disable connections after the fixture phase. Cleanup uses fixed project/service-scoped Docker container IDs even if Compose drifts, disables new DB connections and terminates existing isolated fixture clients. Production cutover requires successful acceptance evidence plus an explicit operator approval recorded against the exact checkpoint/build/report pins; a backup or reconstruction alone is not approval.

## Shared host lease and staged cutover

Install a private `0700` state directory beside **each** of the four canonical target directories. Its name is `.photo-restore-` followed by the SHA-256 of the UTF-8 absolute target path. Each state directory contains the same private canonical `installation.json`: schema_version `restore-operator-installation/v1`, project, postgres_target, minio_target, config_target and deletions_target. Supply its independently reviewed SHA-256 as mandatory `operator_state_pin` in restore settings. These directories are external operator installation, never extracted from a checkpoint. Every concrete phase acquires all four regular private lock files in sorted physical-path order. Shared object/config/history storage conflicts even when PostgreSQL paths or report directories differ. Do not replace installation files or lock files while an operation holds the lease.

Run `backup-restore` first. It creates the actual reconciled report and a separate `<run-id>.checkpoint.json` materialization receipt in report_root, binding the full independently authenticated manifest, its SHA, recovery report SHA and exact target namespace/data directory. Preserve both. Then `backup-replay` consumes a separately reviewed replay config and caller-supplied SHA, starts only the isolated broker phase and invokes the pinned actual Go binary; Python does not manufacture a replay receipt. Review the resulting real report/receipt before providing acceptance configuration and its external SHA to `backup-accept`.

After successful isolated acceptance, prepare a separate canonical `restore-cutover-approval/v1` document. Its exact closed fields are checkpoint_id, publication_version, checkpoint/recovery/replay/acceptance `{path,sha256}` pins, build_sha256, approved production compose_file/compose_sha256/compose_rendered_sha256, approved_at and event_root, plus schema_version. `checkpoint` pins the actual materialization sidecar, not an operator-written replacement. Invoke `backup-cutover` with this document, its independently supplied SHA and an explicit confirm_run_id matching the accepted run. This command repeats the real acceptance reports, signed publication, exact materialization binding and current consent/deletion/key authorities, verifies old source writers are stopped, and records immutable approval before enabling the separately approved application services. Storage containers are preserved. The approval and completion events use pending-file fsync followed by atomic no-overwrite publication. Ambiguous activation stops the target services and preserves storage/evidence for investigation; it does not silently resume the old writers or issue automatic approval.

All these commands require a separately bound control connection to another database on the same isolated PostgreSQL container. Acceptance and cutover temporarily open target connections only to establish the controlled held operator session; acceptance closes them again, while successful explicitly approved cutover permits the approved application. Cutover failure appends a `.compensated.json` terminal event binding the exact approval and activation hashes; compensation is confirmed only after fixed-ID stop/readback and a fresh empty running-project projection. Unknown services produce unconfirmed compensation. Any compensated run is permanently ineligible for activation retry: prepare a new recovery/replay/acceptance run and new explicit approval. Retain all events, including activation followed by withdrawal, rather than interpreting an old activation file as current authority. No test, restore drill or activation is implied by source implementation.

SQL startup note: `backup-restore` retains its shared host lease while waiting up to 300 seconds for the actual restored PostgreSQL connection after storage startup/WAL replay. Explicit authentication/database errors fail immediately; cancellation closes a newly opened connection. Startup and consent/control SQL sessions use statement_timeout5s and lock_timeout1s before their first statements. A readiness timeout is a failed isolated operation requiring operator inspection; no evidence or writer approval is fabricated.
