# STRIPE-CONFIG — конфигурация Stripe без ключей

Статус на 23.10.2026: ключей и аккаунтов нет. Решение владельца: ключи добавляются в конфиг после написания кода.
Поэтому весь код пишется против интерфейса провайдера и его подмены (fake) и по умолчанию выключен.

## Правила

- **S1.** Секреты в git, docs, логах и тестовых фикстурах запрещены (05, RULES R6).
- **S2.** Stripe выключен по умолчанию. Без конфигурации capability покупки = false, создание Checkout закрыто, остальной биллинг работает.
- **S3.** Каждая задача `STR-*` проверяется на fake-провайдере. Реальные sandbox-проверки собраны отдельно в `STR-14` (помечена «ЖДЁТ КЛЮЧЕЙ»).
- **S4.** Live-режима нет: значение `STRIPE_ENVIRONMENT` кроме `test` отвергается при старте.

## Переменные (имена из 05; значения по умолчанию и форма хранения — предложение по практике репозитория)

| Переменная | Что это | По умолчанию | Хранение |
|---|---|---|---|
| `BILLING_STRIPE_ENABLED` | Главный флаг (новое имя, предложение) | `false` | env |
| `STRIPE_ENVIRONMENT` | Только `test` на первом этапе | пусто | env |
| `STRIPE_ACCOUNT_ID` | ID sandbox-аккаунта, сверяется с ответом Stripe | пусто | env |
| `STRIPE_API_VERSION` | Фиксируется после spike (`OPEN-13`), выдуманный номер запрещён | пусто | env |
| `STRIPE_SECRET_KEY_REF` | Абсолютный путь к файлу с секретным ключом (как `AUTH_KEYS_FILE`) | пусто | файл вне репозитория |
| `STRIPE_WEBHOOK_SECRET_REF` | Абсолютный путь к файлу с signing secret | пусто | файл вне репозитория |
| `STRIPE_PORTAL_CONFIG_ID` | ID настройки Customer Portal | пусто | env |

Форма «`*_REF` = путь к файлу» выбрана по аналогии с существующим `AUTH_KEYS_FILE` в `backend/internal/config/config.go`. Если владелец предпочтёт внешний secret store, меняется только слой чтения.

## Поведение при старте (реализуется задачей STR-00)

1. `BILLING_STRIPE_ENABLED` не `true` → остальные переменные не требуются, ошибок нет.
2. Флаг `true`, но не задана любая из шести остальных переменных → старт завершается ошибкой по образцу `Load()` («… must be configured together»). Значения секретов в сообщениях не печатать.
3. `STRIPE_ENVIRONMENT` не `test` → ошибка.
4. Путь `*_REF` не абсолютный или файл не читается → ошибка.
5. После старта (STR-02): расхождение account/environment с ответом Stripe или с price mappings закрывает создание Checkout, не весь сервис.

Примеры значений заносятся в `deploy/env/production.env.example` с `REPLACE`; реальные значения хранятся вне репозитория.

## Как добавить ключи позже

1. Создать отдельные Stripe Sandbox для dev и CI (оператор, вручную; шаги и доказательства — в `STR-15`).
2. Записать секретный ключ и webhook signing secret в файлы вне репозитория с правами только владельца.
3. Задать `STRIPE_ENVIRONMENT=test`, `STRIPE_ACCOUNT_ID`, пути `*_REF`, `STRIPE_PORTAL_CONFIG_ID`.
4. Провести integration spike на реальной версии аккаунта и записать `STRIPE_API_VERSION` (закрывает `OPEN-13`).
5. Запустить provisioning (STR-02) на sandbox; повторный запуск не создаёт дублей.
6. Зарегистрировать HTTPS webhook endpoint sandbox и записать его signing secret (шаг 2).
7. Пройти чек-лист `STR-14` на реальном sandbox.
8. Только после этого включить `BILLING_STRIPE_ENABLED=true` для тестового cohort.

## Что нужно от владельца (по готовности кода)

- Два sandbox-аккаунта (dev, CI) и их ID.
- Секретные ключи и webhook secrets, положенные в файлы (шаг 2, не присылать в чат).
- Реквизиты продавца, поддержка, statement descriptor, branding (таблица настроек в 05).
- Тестовые адреса для уведомлений.
- Решение по `OPEN-13` (версия API) после spike.

## Что не блокирует разработку

Контракты, таблицы, функции, handlers, webhook inbox, fulfillment, saga, refund, reconciliation, UI и e2e на fake-провайдере (`STR-01`).
