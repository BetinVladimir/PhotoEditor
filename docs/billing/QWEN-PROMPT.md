# QWEN-PROMPT — как давать работу малой модели

Принцип: модель получает **мало контекста и один жёсткий формат**. Всё, что можно проверить скриптом, проверяет скрипт, а не модель.

## 1. Как собирать контекст (окно 32K)

Пакет собирает скрипт и сам проверяет бюджет. `--task` принимает ID из `TASKS.md` и из `backlog/` (например `FIN-T09`). Руками файлы в контекст не класть.

```
python3 docs/billing/tools/build-pack.py --task T-01 --brief 1B7 \
  --section "18#Admission" --func selected-workflow.sql:billing_bind_operations --out pack.md
```

Состав пакета: системный промпт (~0,5K) + `RULES.md` (~1,9K) + задача + карточка этапа + нужные секции файлов + нужные SQL-функции.
Бюджет (оценка токенов): материалы ≤ 14K; свободно на ответ ≥ 9K. При превышении скрипт завершается с ошибкой, и задачу надо резать.

Как резать:
- `--section "NN#часть заголовка"` берёт секцию файла `NN-*.md` целиком (с подсекциями). Размеры секций: самая большая ~2,6K.
- `--rows слово` оставляет в таблицах секции только строки со словом (так 09 §3 сжимается с 3,7K до ~0,9K).
- `--func файл.sql:имя` берёт одну функцию с её ACL. Без файла скрипт откажется, если имя есть в нескольких файлах.
- Карточки `briefs/BRIEF-*.md` — 0,3–1,9K. Таблицы 1Б.1 лежат отдельно в `briefs/TABLES-1B1.md` (~3K), грузить только по необходимости.

Измеренный худший случай для каждого этапа (карточка + все секции файла этапа + самая большая функция): вход 9,3–12,8K, свободно на ответ 19–23K.

Не класть в контекст: все 18 файлов, `STATUS.md`, `11-implementation-progress.md`, `contracts/seed.json`, SQL-файл целиком.

## 2. Системный промпт (вставить как есть)

```
Ты исполнитель задач в репозитории PhotoEditor, подсистема billing.
Работай ТОЛЬКО по файлам, которые тебе дали. Ничего не додумывай.

Жёсткие правила:
1. Следуй RULES.md. Номер правила (R1…R30) указывай, когда отказываешься или выбираешь вариант.
2. Если для задачи не хватает значения (цена, лимит, срок, налог, имя файла, сигнатура), НЕ подставляй своё.
   Остановись и ответь блоком STOP (формат ниже).
3. Один ответ = одна задача. Не трогай файлы вне поля «Выход».
4. Не правь сгенерированные файлы вручную: меняй source в contracts/ и перечисли команду перегенерации.
5. Не пиши down-миграции. Не меняй существующие миграции.
6. Любая новая SQL-функция: SECURITY DEFINER, SET search_path=pg_catalog,photo, OWNER TO photo_fn_owner,
   REVOKE ALL FROM PUBLIC, GRANT EXECUTE только ролям из задачи.
7. Порядок блокировок: tenant SHARE, control SHARE, balance FOR UPDATE, allowance/buckets, lease/claim.
   Несколько ресурсов — по resource_code, до run/task/adoption locks.

Формат ответа (строго):
PLAN: 3–7 коротких пунктов
FILES: список «путь — что изменено»
CODE: по одному блоку на файл, с путём в первой строке
CHECKS: список команд из поля «Критерий» задачи, с ожидаемым результатом
RULES: какие R-номера применил
Если остановился: 
STOP: что именно отсутствует
ASK: один конкретный вопрос
OPEN: предлагаемая строка для OPEN.md
```

## 3. Как проверять результат (не доверять самооценке модели)

Прогнать по порядку, остановиться на первой ошибке:

1. `bash docs/billing/tools/check-static.sh` (линтер, карточки, образцы, бэклог, 9 генераторов, контрактные тесты)
2. Дальше только то, чего нет в п. 1
4. Тесты из поля «Критерий» задачи
5. Сверка ACL: `execute_roles` в JSON = `GRANT EXECUTE` в SQL (карточка покажет блок «ВНИМАНИЕ», если расходится)

Любая ошибка → вернуть модели текст ошибки и тот же блок задачи, не расширяя контекст.

## 4. Ограничения на размер задачи

- Одна функция или одна таблица или один экран за раз.
- Новая SQL-функция — не длиннее ~80 строк (около 2K токенов); длиннее — делить на helper'ы в разных задачах. (11 из 67 существующих функций длиннее 2K: их правят целиком только вдвоём с человеком.)
- Задача, где «Вход» превышает 3 источника (секции + функции), режется ещё раз.
- Задачи по логике квот, lease, settlement и erasure Qwen выполняет только с человеком-ревьюером.

## 5. Калибровка и что не проверено

Токены в `tools/tokens.py` — оценка (кириллица ~2,2 символа/токен, остальное ~3,2). Токенайзер Qwen не проверялся.
Чтобы откалибровать: посчитать реальные токены для `RULES.md`, получить `TOKEN_SCALE = реальные / оценка` и экспортировать переменную перед запуском скриптов. Бюджет выдержит расхождение до ~1,5 раза.

Не проверено: качество Qwen на этих задачах и соблюдение формата ответа. Перед использованием прогнать T-02 и одну простую задачу по `EXAMPLES.md`.
