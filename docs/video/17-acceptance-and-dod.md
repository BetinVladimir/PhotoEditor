# 17. Критерии приёмки, определение готовности и трассировка

Статус: спроектировано, не реализовано (2026-10-22). Начало: [README](README.md). Задачи — [15](15-task-cards.md); тесты — [16](16-test-logic.md); требования — документы 01–11. Ни один пункт ниже не выполнен: это критерии для будущей реализации.

## 1. Определения

| Термин | Значение |
|---|---|
| **Задача выполнена** | выполнены все пункты DoD своего типа (раздел 3), приложен отчёт (раздел 7), нет пропусков тестов без записи причины |
| **Критерий приёмки (ACC)** | проверяемое утверждение вида «Дано / Когда / Тогда» с числами (раздел 5) |
| **Фаза принята** | все AC фазы подтверждены отчётами; нет открытых дефектов уровня «блокирующий» |
| **Факт завершённости** | не слова исполнителя, а артефакты: вывод команд, список изменённых файлов, результат мутационного контроля (раздел 7) |
| **Блокирующий дефект** | потеря данных, межтенантная утечка, двойное списание квоты, зависший резерв, невозможность отмены, нарушение Paper-политики |

Правила: приёмка принимает только то, что проверено на **финальных исходниках** (не на предыдущей сборке); отчёты о прежних запусках на новую реализацию не переносятся; «не проверено» не равно «пройдено».

## 2. Общие условия готовности для всех задач

1. Файлы созданы **только** из списка карточки; лишних изменений нет (`git status --short` показывает ровно ожидаемые файлы).
2. Имена, сигнатуры и коды ошибок совпадают с DS/FN (проверка поиском: `grep -rn "<КОД>"` находит код в реализации и в тесте).
3. Все тесты карточки — зелёные, пропусков нет.
4. Мутационный контроль выполнен (раздел 7, п. 4).
5. Нет временных/отладочных артефактов (`console.log`, `print`, `TODO`, закомментированный код) — проверка `grep -rn "console.log\|TODO\|print(" <изменённые файлы>`.
6. Строки интерфейса не захардкожены (для UI), секреты и пути не попадают в логи.

Дополнительное общее условие (ревью): каждая новая таблица `photo.video_*` проходит проверку шардируемости (`TC-SC-SQL-07`, [20](20-saas-scaling-operations.md), раздел 11); каждый новый путь, создающий задание или ревизию, проходит допуск раздела 3 того же документа и возвращает коды `VIDEO_TENANT_LIMIT` / `VIDEO_CAPACITY_BUSY` с `Retry-After`.

## 7. Отчёт о выполнении задачи («факт завершённости»)

Каждая выполненная карточка завершается отчётом в таком виде (в ответе исполнителя или в файле `docs/video/reports/TK-nnn.md`):

```
TK-nnn <название>
1. Изменённые файлы: <вывод `git status --short`>
2. Команда проверки: <точная команда>
3. Вывод (последние 20 строк): <вставка>
4. Мутационный контроль: порча «<что изменено>» → тест «<имя>» красный (вывод) → порча откачена → тест зелёный
5. Пропущено/не выполнено: <список с причинами или «нет»>
6. Общие проверки слоя: <команда и итог: typecheck / vet / ruff / contracts-check>
7. Отклонения от карточки: <список или «нет»>
8. Открытые вопросы: <список или «нет»>
```

Принимающий проверяет отчёт механически: п. 1 совпадает с карточкой; п. 3 содержит итоговую строку без `failed`/`skipped`; п. 4 заполнен; п. 5 равно «нет». Любой пункт не выполнен — задача возвращается исполнителю.

4. Прямые SQL-запросы к таблицам видео из Go/Python вместо функций БД.

7. Отметка «выполнено» без отчёта раздела 7.
8. Файлы вне списка карточки в `git status`.
