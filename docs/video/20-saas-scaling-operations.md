# 20. Масштабирование SaaS, справедливость между арендаторами и эксплуатация

Статус: спроектировано, не реализовано (2026-10-22). Начало: [README](README.md). Документ появился по итогам ревью ([21](21-review-report.md)): в 01–19 не были проработаны честное распределение очередей между арендаторами, защита от перегрузки, горячие пути БД, масштабирование раздачи клиентам, жизненный цикл данных и эксплуатационные цели. Здесь они зафиксированы нормативно в том же формате, что и 12–19 (ID, числа, векторы, задачи, критерии), чтобы их мог исполнять слабая модель.

Принцип остаётся прежним: **не изобретать второй механизм**. Платформа уже описывает масштабирование фото-обработки в [12-scale-product.md](../implementation-v2/12-scale-product.md) (этапы A/B/C) и [18-capacity-operations.md](../implementation-v2/18-capacity-operations.md) (`CapacityPolicy`). Видео встраивается в них; всё, чего там нет, добавляется ниже.

## 2. Решения

| ID | Решение | Причина |
|---|---|---|
| D-09 | Классы очереди и пулы по таблице раздела 1; стоимость по `FN-Q-09` | один планировщик, справедливость уже реализована |
| D-10 | Лимиты арендатора на **находящиеся в системе** задания (ожидающие + выполняемые) по четырём группам и суточный бюджет «секунд стоимости» | загрузка пачки роликов должна ставиться в очередь, а не отклоняться; но один арендатор не должен занять весь пул |
| D-11 | При перегрузке пула новые задания отклоняются кодом `VIDEO_CAPACITY_BUSY` с `Retry-After`; предпросмотр кадров не отклоняется | управляемая деградация вместо бесконечной очереди |
| D-12 | Горячие пути БД разгружены: прогресс пишется редко, трафик агрегируется и расходуется «арендами», автосохранение ограничено | иначе нагрузка растёт как число запросов Range и тиков прогресса, а не как число заданий |
| D-13 | Доставка клиенту имеет три режима `proxy` (V1 по умолчанию), `redirect`, `cdn`; режим — настройка сервера, не код клиента | прокси через Go не масштабируется бесконечно ([08](08-delivery-portal.md), раздел 4), нужен заранее определённый путь выхода |
| D-14 | Один узел воркера скачивает один и тот же исходник в рамках одного запуска не более одного раза (кэш запуска в scratch) | ingest из четырёх заданий иначе читает 16 ГиБ четыре раза |
| D-15 | Воспроизведение proxy/раскадровки **владельцем** при монтаже (`GET …/video-media/{id}/proxy`) всегда идёт в режиме `redirect` (раздел 6), независимо от режима портала | монтаж — постоянная перемотка; прогонять её через Go не нужно: трафик владельца не тарифицируется, а авторизация проверяется на каждый запрос диапазона |
| D-16 | Запросы предпросмотра кадров сглаживаются на клиенте (`PREVIEW_DEBOUNCE_MS`), заменяют друг друга и дедуплицируются на сервере | иначе каждый сдвиг ползунка цвета создаёт задание |

### 3.3 Порядок проверок при создании задания

Выполняет `FN-D-17` внутри `FN-D-08` (одна транзакция, блокировки в порядке из [worker-heartbeat-tenant-lock-order.md](../implementation-v2/runbooks/worker-heartbeat-tenant-lock-order.md)):

1. capability и квалификация (как сейчас, `VIDEO_BACKEND_UNAVAILABLE`);
2. лимит находящихся в системе заданий группы → `VIDEO_TENANT_LIMIT / OUTSTANDING_*`;
3. суточный бюджет → `VIDEO_TENANT_LIMIT / DAILY_COST`;
4. порог перегрузки пула (кроме группы `preview`) → `VIDEO_CAPACITY_BUSY`;
5. резерв квоты места (как сейчас, `VIDEO_QUOTA_EXCEEDED`);
6. вставка run/outbox и `video_jobs` со стоимостью; увеличение суточного счётчика.

Идемпотентный повтор с тем же `Idempotency-Key` возвращает исходный ответ и **не** меняет счётчики. Неуспех на любом шаге не оставляет побочных эффектов (счётчик суток обновляется только на шаге 6).

### 3.4 Чистые функции (с векторами)

Векторы: [`vectors/scale.json`](vectors/scale.json), эталон: [`vectors/reference/ref_scale.py`](vectors/reference/ref_scale.py). Целочисленная арифметика, без чисел с плавающей точкой. `ceil(a/b)` = `(a + b − 1) div b`. `TPS = 705600000`. `S = ceil(duration_ticks / TPS)`.

**FN-Q-09 `jobCostSeconds(kind, durationTicks) → int`**

| `kind` | Формула | Условие ошибки |
|---|---|---|
| `ingest` | `30 + ceil(S × 3 / 5)` | `durationTicks ≤ 0` → `DURATION_INVALID` |
| `detect_cuts` | `60 + ceil(S × 7 / 20)` | то же |
| `color_analyze` | `30 + ceil(S / 5)` | то же |
| `audio_analyze` | `20 + ceil(S / 20)` | то же |
| `preview_frames` | `5` (длительность игнорируется, `< 0` → `DURATION_INVALID`) | |
| `render` | `60 + ceil(S × 3 / 2)` | `durationTicks ≤ 0` → `DURATION_INVALID` |
| прочее | — | `KIND_INVALID` |

Вектор `job_cost` (18 кейсов, в том числе 3 часа: `render` = 16260, `ingest` = 6510, `detect_cuts` = 3840).

**Стоимость `ingest` при допуске.** Длительность ролика на момент `complete` ещё неизвестна (её определит `probe`). Поэтому `ingest` оценивается по размеру файла функцией `FN-Q-13`; для `audio` и `lut` — так же (для `.cube` размер ≤ 20 МиБ даёт ≤ 21 с).

**FN-Q-13 `ingestDurationEstimateTicks(bytes) → ticks`**: `bytes ≤ 0` → `BYTES_INVALID`; `secs = min(10800, max(1, ceil(bytes / 1 000 000)))` (допущение 8 Мбит/с); результат `secs × TPS`. Передаётся в `FN-Q-09(ingest, …)` при создании задания. Вектор `ingest_duration_estimate` (7 кейсов: 1 байт → 1 с; 1 000 001 → 2 с; 1 ГиБ → 1074 с; 16 ГиБ → 10800 с).

**FN-Q-10 `retryAfterSeconds(aheadCost, activeWorkers) → int`**: `aheadCost < 0` → `AHEAD_INVALID`; `w = max(1, activeWorkers)`; `raw = ceil(aheadCost / w)`; `raw = min(900, max(5, raw))`; результат — `raw`, округлённое вверх до кратного 5. Вектор `retry_after` (11 кейсов).

**FN-Q-11 `egressLeaseBytes(remaining, activeStreams) → int`**: `activeStreams < 0` → `STREAMS_INVALID`; `remaining ≤ 0` → `0`; `remaining < 8 MiB` → `remaining`; иначе `chunk = remaining div (activeStreams + 1)`, `chunk = min(256 MiB, max(8 MiB, chunk))`, результат `min(chunk, remaining)`. Вектор `egress_lease` (12 кейсов).

**FN-Q-12 `admitJob(state, limits, kind, cost) → результат`**: порядок — шаги 2–4 раздела 3.3 (группа → суточный бюджет, `dailyCost = null` отключает → порог перегрузки, не применяется к группе `preview`; при отказе по перегрузке `retry_after_s = retryAfterSeconds(poolAheadCost, activeWorkers)`). Условие шага 2: `outstanding[группа] + 1 > limits.outstanding[группа]`; шага 3: `dailyUsedCost + cost > limits.dailyCost`; шага 4: `poolAheadCost > limits.shedCost`. Неизвестный `kind` → ошибка `KIND_INVALID`. Вектор `admit_job` (20 кейсов).

**FN-U-14 `autosaveGate(nowMs, lastSaveMs, dirty, minIntervalMs, force) → {action, waitMs}`** (клиент, TS): `!dirty` → `idle`; `force` или `lastSaveMs = null` → `save`; `elapsed = nowMs − lastSaveMs`; `elapsed < 0` (сдвиг часов) или `elapsed ≥ minIntervalMs` → `save`; иначе `wait` с `waitMs = minIntervalMs − elapsed`. Вектор `autosave_gate` (9 кейсов).

Реализации: Go (`video/quota/scale.go`) для FN-Q-09…13 (проверка на сервере); TS-зеркало FN-Q-09 и FN-Q-12 не требуется; FN-U-14 — только TS. SQL-функция `FN-D-17` повторяет FN-Q-12 и проверяется теми же кейсами (раздел 12, `TC-SC-SQL-01`).

## 4. Перегрузка и обратное давление

1. **Порог.** `poolAheadCost` — сумма `cost_seconds` ожидающих (`queued`) заданий **учётного пула** (`video_jobs.pool`: `audio_analyze` и `preview_frames` — `video_light`, остальные, включая `ingest` из-за этапа proxy, — `video_heavy`), считается запросом по частичному индексу (`DS-05`). Если `p95` времени допуска превысит 50 мс при нагрузке теста `TC-LOAD-05`, вычисление заменяется счётчиком пула, обновляемым планировщиком (изменение допускается без пересмотра ТЗ, но с повторным прогоном теста).
2. **Что отклоняется.** Новые `ingest`, `detect_cuts`, `color_analyze`, `audio_analyze`, `render`. Не отклоняются: `preview_frames`, `cancel`, чтение, публикация и скачивание готового. Идущие и уже принятые задания продолжаются.
3. **Что видит пользователь.** Экраны V-02, V-03, V-09 показывают `CapabilityNotice`-вариант «Система загружена, повторите через N с» с обратным отсчётом из `retry_after_s`; для `VIDEO_TENANT_LIMIT` — какое именно ограничение и когда оно снимется (завершение заданий или начало суток). Автоповтор клиент **не** выполняет (кроме явной кнопки), чтобы не усиливать перегрузку.
4. **Аварийные рычаги оператора:** уменьшить `VIDEO_SHED_COST_SECONDS` или суточный бюджет для всех/одного арендатора; kill switch ([TK-805](15-task-cards.md)). Все рычаги применяются без релиза.
5. **Справедливость.** Внутри класса планировщик чередует арендаторов (раздел 1); тесты `TC-LOAD-06` (два арендатора) и `ACC-41` проверяют, что арендатор с одним заданием не ждёт окончания очереди другого.

## 5. Горячие пути базы данных

### 5.1 Прогресс заданий

- Рассылка SSE по прогрессу идёт из памяти Go по событиям воркера не чаще `JOB_PROGRESS_MIN_INTERVAL_MS`.
- Запись в `video_jobs` — не чаще `JOB_PROGRESS_DB_INTERVAL_MS` **и** только при изменении на `JOB_PROGRESS_DB_MIN_DELTA_PCT` п.п. либо смене стадии. Терминальное состояние пишется всегда.
- Таблица `video_jobs` создаётся с `fillfactor = 70` (обновления прогресса остаются «горячими» и не раздувают индексы); индексы по изменяемым столбцам `progress`, `eta_seconds` запрещены.
- Верхняя граница числа записей прогресса одного задания: `ceil(длительность_задания_с / 10) + число_стадий + 2` (критерий `ACC-45`).

### 5.2 Учёт исходящего трафика (замена построчных событий)

Построчная запись `video_egress_events` на каждый запрос Range не масштабируется (плеер шлёт запрос каждые несколько секунд на зрителя). Поэтому:

1. `video_egress_events` ([04](04-data-model-and-api.md), 2.6) остаётся только для **скачиваний** (одна строка на завершённое или прерванное скачивание) — это нужно для отчётов владельцу.
2. Поток учитывается в `video_egress_counters` — одна строка на `(tenant, share, render, kind, часовой интервал)`, обновляется upsert-ом с накоплением `bytes` и `requests`.
3. Лимиты (на ссылку и общий по плану) исполняются **арендами**: перед отдачей очередной порции процесс портала вызывает `FN-D-19 photo.lease_video_egress(tenant, share, want)`, получает `granted ≤ want` (`want` = результат `FN-Q-11`), хранит его в памяти и расходует; остаток возвращается `FN-D-20 photo.settle_video_egress(...)` не позже чем через `EGRESS_LEASE_TTL_SECONDS` или при закрытии потока. `granted = 0` ⇒ `VIDEO_EGRESS_LIMIT`.
4. Невозвращённая аренда (падение процесса) считается потреблённой: перерасход ограничен суммой выданных, но не сданных аренд (≤ `EGRESS_LEASE_MAX_BYTES` на активный поток). Это явное, измеряемое допущение (`ACC-46`).
5. Период общего лимита — месяц UTC; строка `video_egress_period` хранит `consumed_bytes`, `leased_bytes`, `limit_bytes`.

### 5.3 Автосохранение и ревизии

- Клиент вызывает `FN-U-14` перед каждым сохранением; ручное «Сохранить», закрытие экрана и уход в фон — `force = true`.
- Сервер отклоняет `AUTOSAVE_SERVER_MAX_PER_MIN + 1`-ю ревизию монтажа в минуту кодом `VIDEO_TENANT_LIMIT / AUTOSAVE_RATE`; клиент сохраняет черновик локально (`editor-draft-cache`-подобный) и повторяет после `Retry-After`. Потери правок нет (`ACC-48`).
- Сжатие автосохранений (`FN-D-16`) — как в [05](05-storage-quota-retention.md), п. 4.6. Метрика `video_sequence_objects_total` по арендатору (в логах/отчёте, не в метриках) показывает рост числа мелких объектов; если у арендатора > 50 000 объектов ревизий, оператор получает предупреждение (кандидат на хранение маленьких документов внутри БД — **решение откладывается**, фиксируется как вопрос Q-14 в [10](10-testing-acceptance-rollout.md)).

### 5.3a Предпросмотр кадров

1. Клиент запрашивает предпросмотр не раньше чем через `PREVIEW_DEBOUNCE_MS` после последнего изменения параметра и держит **не более одного** незавершённого запроса на монтаж; новый запрос отменяет предыдущий ожидающий (`cancel` задания в состоянии `queued`) и заменяет его.
2. Сервер дедуплицирует: создание `preview_frames` с тем же `(tenant, sequence_id, sequence_revision, params_sha256)` при существующем задании в состоянии `queued`/`running`/`succeeded` возвращает **существующее** задание без нового допуска и без расхода суточного бюджета.
3. Результат кэшируется по ключу `(document_sha256, момент, размер)` (`FN-U-08`); повторный показ не создаёт задание.

### 5.4 Хранение истории и обслуживание

| Данные | Правило | Функция |
|---|---|---|

## 6. Доставка клиенту: режимы и точка перехода

| Режим | Как работает | Отзыв | Учёт трафика | Когда включать |
|---|---|---|---|---|
| `proxy` (V1) | Go читает MinIO и отдаёт `206` ([08](08-delivery-portal.md), 4) | на следующем запросе Range | по реально записанным байтам, через аренды (5.2) | по умолчанию |
| `redirect` | на каждый запрос Range портал проверяет доступ и отвечает `307` на **новую** подписанную ссылку на тот же диапазон (≤ 60 с) | на следующем запросе Range | **пессимистично**: считается длина выданного диапазона в момент выдачи | когда Go-инстанс упирается в сеть, а точность «по факту» не критична |
| `cdn` | отдельное ТЗ: подписанные куки малого срока, отзыв по ключам | в пределах TTL куки | по журналам CDN | не входит в V1; требует решения владельца (оригиналы остаются приватными) |

Режим задаётся серверной настройкой `video_stream_mode` и возвращается в `capabilities`; клиент плеера не зависит от режима (он следует `307` штатно). Триггеры перехода `proxy → redirect` (достаточно любого, держится 15 минут): устойчивая исходящая скорость инстанса портала > 60 % пропускной способности сетевого интерфейса; `p95` времени до первого байта потока > 1,5 с; CPU инстанса портала > 70 %. Переход проверяется тестом `TC-LOAD-07` в обоих режимах; в режиме `redirect` требование VID-SH-03 выполняется (авторизация на каждый запрос Range), а отличие учёта явно описано пользователю в статистике («оценка»).

**Воспроизведение владельцем (D-15).** `GET …/video-media/{id}/proxy` и ссылки на раскадровку/волну работают в режиме `redirect` независимо от `video_stream_mode`: каждый запрос диапазона проходит проверку доступа и получает `307` на подписанную ссылку ≤ 60 с. Байты владельца не тарифицируются и не расходуют аренды; учитываются только метрикой `video_stream_active` с `mode=owner`.

Лимиты потоков (`STREAMS_PER_SESSION`, `STREAMS_PER_SHARE`) и скорости (`STREAM_MAX_BYTES_PER_SECOND`) действуют в режиме `proxy`; в `redirect` действует только ограничение выдачи ссылок (число выдач в секунду на сессию — через общий лимит портала).

### 7.3 Пропускная способность между воркером и хранилищем

Рендер читает все источники через gateway ([05](05-storage-quota-retention.md), 1.2: до 20 ГиБ на задание). Требования:

1. **D-14. Кэш исходников запуска.** В пределах одного `run` (ingest: `probe → proxy/thumbs/waveform`; render) воркер при первом чтении кладёт исходник в scratch под ключом `(tenant, sha256)` и повторно использует; задачи одного запуска получают аффинность к узлу как **оптимизацию** (если узел занят — задача идёт на другой и скачивает заново). Кэш удаляется через `SOURCE_CACHE_TTL_SECONDS` после последнего использования или при нехватке scratch; кэш не пересекает арендаторов (ключ включает `tenant`). Критерий: ingest одного файла на одном узле скачивает ≤ 1,2 × размера исходника (`ACC-49`).
2. Бюджет полосы gateway на воркер задаётся в профиле видео (`WORKER_MAX_DOWNLOAD_BYTES` — [06](06-workers-and-models.md), 8.3); оператор сверяет суммарную полосу пула с пропускной способностью MinIO по формуле раздела 9.3.

## 8. Надёжность

1. **Попытки.** Потеря воркера/lease: до `MAX_TASK_ATTEMPTS_INFRA` = 3 попыток всего; детерминированная ошибка декодера — 2 ([06](06-workers-and-models.md), 7). Выдача повторной попытки — с задержкой не менее 30 с, затем 60 с (если планировщик не поддерживает задержку — допущение A-12, проверяется в TK-001; без поддержки действует только лимит попыток).
2. **Dead letter.** Команда, превысившая попытки, складывается существующим механизмом ([`deadletter.go`](../../backend/internal/queue/deadletter.go)); обработчик видео вызывает `FN-D-09` с итогом `failed`, `error_code = VIDEO_JOB_ABANDONED`, освобождает резерв, переводит медиа ingest в `failed`. Оператору видна запись и метрика `video_dead_letter_total`.
3. **Согласователь (reconciler).** `FN-D-22 photo.reconcile_video_stuck(limit)` раз в 5 минут находит и исправляет: задания `running` с истёкшей lease без живой задачи (возврат в очередь или `abandoned`); медиа в `probing` старше `(таймаут ingest) × MAX_TASK_ATTEMPTS_INFRA`; загрузки в `completing` старше 30 минут (переоценка завершения); рендеры в `verifying` старше 1 часа; резервы `video_*` без живого держателя. Каждое исправление — аудит-событие; функция идемпотентна.
4. **Идемпотентность и повтор** — как в [02](02-architecture.md), инвариант 3.
5. **Деградация зависимостей.** MinIO недоступен: загрузки и стрим возвращают `503` с `Retry-After`; задания не принимаются (`VIDEO_CAPACITY_BUSY`); состояния не портятся. RabbitMQ недоступен: заявки накапливаются в outbox (существующее поведение). Нет живых воркеров пула: допуск возвращает `VIDEO_BACKEND_UNAVAILABLE` с причиной.
6. **Резервное копирование и восстановление.** БД — по общей политике; видео-объекты — по решению Q-07 ([10](10-testing-acceptance-rollout.md)). После восстановления БД без объектов запись `ready` может ссылаться на отсутствующий объект: проверка восстановления ([05](05-storage-quota-retention.md), 4.5) включает видео-префиксы; медиа с отсутствующим объектом переводится в `failed` с кодом `VIDEO_CORRUPT`, квота пересчитывается.

## 9. Хранилище, стоимость и планирование ёмкости

### 9.1 Объекты и ключи

На один исходник приходится 5 объектов (оригинал, probe, proxy, раскадровка, волна); на ревизию монтажа — 1; на рендер — 2 (результат, отчёт проверки). Ключи начинаются с `tenants/{tenant}/video/…` (по правилу [05](05-storage-quota-retention.md), 1.1), что даёт очистку и аудит по префиксу и готовность к размещению арендатора на отдельной ёмкости (раздел 11).

### 9.2 Жизненный цикл бакета

| Правило | Значение |
|---|---|
| Незавершённые multipart | прервать через 8 суток |
| `video_preview_frame` | удалить через 7 суток (уже в [05](05-storage-quota-retention.md)) |
| Версии объектов | старые версии удаляемых объектов физически удаляются в `FN-D-13` (вторая фаза), политика хранения неактуальных версий бакета — 7 суток |
| Холодное хранение оригиналов | не входит в V1; решение зависит от Q-07 и тарифа |

### 9.3 Формулы планирования (для оператора)

Обозначения: `N` — число арендаторов; `O` — средний объём оригиналов на арендатора; `d` — доля производных (по оценке `FN-Q-03` ≈ 0,16 для файлов ≈10 ГиБ); `R` — объём рендеров; `x` — реальное время рендера (кратность скорости), `D` — суммарные минуты рендера в сутки, `u` — целевая загрузка GPU (0,5).

- Хранение: `S = N × (O × (1 + d) + R)`.
- Исходящий трафик в месяц: `E ≤ 10 × включённый_диск` на арендатора (правило [05](05-storage-quota-retention.md), 3.4).
- GPU для рендера: `G = ceil( D / (x × 1440 × u) )`.
- Потоки на инстанс портала: `P = floor( 0,6 × пропускная_способность_сети_Б/с / (STREAM_MAX_BYTES_PER_SECOND или средний битрейт) )`.
- Полоса воркеров: `Σ(скачивание_рендеров_в_час) ≤ 0,5 × пропускная_способность_MinIO`.

**Иллюстрация (числа — допущения, не измерения):** `N = 1000`, `O = 200 ГиБ`, `d = 0,16`, `R = 20 ГиБ` ⇒ `S = 1000 × (200 × 1,16 + 20) ГиБ = 252 000 ГиБ ≈ 246 ТиБ`. Объектов на арендатора ≈ 200·5 + 2000 (ревизии после сжатия) + 200 ≈ 3 200 ⇒ ≈ 3,2 млн на 1000 арендаторов. При `D = 30 000` мин/сутки и `x = 5`: `G = ceil(30000 / (5 × 1440 × 0,5)) = ceil(8,33) = 9` GPU. Портал с сетью 1 Гбит/с (≈ 125 МБ/с) и потоком 1 МБ/с: `P = floor(0,6 × 125) = 75` потоков. Оператор подставляет измеренные значения V0.

### 9.4 Себестоимость и тариф

События использования ([05](05-storage-quota-retention.md), 5) дополняются `video_cost_seconds{kind}` (сумма `cost_seconds` завершённых заданий) и `video_queue_wait_seconds`. Замеры V0 сопоставляют `cost_seconds` с фактическими GPU/CPU-секундами и калибруют формулы `FN-Q-09` (константы меняются в `DS-01` и в векторе одновременно, одним изменением). Единица тарификации (Q-08) выбирается после калибровки.

## 11. Готовность к шардированию и резидентности

Правила проверяются автоматически (`ACC-53`) и обязательны для всех новых таблиц видео:

1. Первичный и каждый уникальный ключ начинаются с `tenant_id` (или содержат его), кроме справочников без данных арендатора (нет таких).
2. Внешние ключи — только внутри одного арендатора `(tenant_id, …)`; ссылок между арендаторами нет.
3. Ни одна транзакция видео не затрагивает двух арендаторов (исключения — операторские функции обслуживания, которые итерируют по арендаторам по одному).
4. Ключи объектов содержат `tenant` первым компонентом после общего префикса.
5. Глобальные счётчики (`video_pool_*`) запрещены в таблицах арендаторов; если нужны — только в операторских таблицах, пересчитываемых.
6. Ничего в видео не предполагает общей файловой системы между узлами: scratch и кэш — локальные, неавторитетные.

Резидентность данных (регион хранения) определяется размещением арендатора; видео-объекты и таблицы следуют за ним; межрегиональная репликация в V1 не предусмотрена. Подробности размещения — раздел «Локальная студия и residency» [12-scale-product.md](../implementation-v2/12-scale-product.md).

## 12. Тесты масштабирования

### 12.1 Модульные и SQL-тесты

| ID | Что | Как |
|---|---|---|
| TC-SC-01 | `FN-Q-09…13`, `FN-U-14` | все кейсы [`scale.json`](vectors/scale.json) в Go (и TS для `FN-U-14`) |
| TC-SC-SQL-01 | `FN-D-17` совпадает с `FN-Q-12` | те же 20 кейсов `admit_job`, состояние строится вставкой строк `video_jobs`; результаты идентичны |
| TC-SC-SQL-02 | гонка на лимите | `heavy = limit − 1`; два параллельных соединения создают задание; ровно одно успешно, второе — `OUTSTANDING_HEAVY`; суточный счётчик увеличен один раз |
| TC-SC-SQL-03 | идемпотентность допуска | повтор того же `Idempotency-Key` не меняет `dailyUsedCost` |
| TC-SC-SQL-04 | аренда трафика | `limit = 100 МиБ`, 10 параллельных `lease` по 256 МиБ: сумма выданного ≤ 100 МиБ; после `settle` с нулевым расходом `leased_bytes` возвращается |
| TC-SC-SQL-05 | свёртка счётчиков | upsert 1000 раз в один интервал даёт 1 строку с суммой |
| TC-SC-SQL-06 | обслуживание истории | строки старше срока удаляются батчами ≤ 1000; повторный запуск возвращает 0 |
| TC-SC-SQL-07 | готовность к шардированию | запрос к `information_schema`/`pg_constraint` (шаблон в `TK-901`): у каждой видео-таблицы PK/UNIQUE содержит `tenant_id`; FK составные |
| TC-SC-PROG-01 | прогресс | воркерная заглушка шлёт 3600 событий прогресса за «1 час» (виртуальное время); записей в БД ≤ `ceil(3600/10) + стадии + 2` |

### 12.2 Нагрузочные и хаос-тесты

Фиктивные воркеры (заглушки операций с заданной длительностью), реальные Go, PostgreSQL, RabbitMQ; запуск ночью, результаты — отчёт формата [16](16-test-logic.md), раздел 7.

| ID | Сценарий | Проходит, если |
|---|---|---|
| TC-LOAD-05 | 200 арендаторов по 4 тяжёлых + 50 ingest одновременно | допуск p95 ≤ 50 мс; ни одного отказа сверх лимитов; в БД нет блокировок > 1 с |
| TC-LOAD-06 | справедливость: арендатор A ставит 4 `render`, затем B 1 `render`, один слот пула | B диспетчеризован не позже чем вторым в общем порядке (`ACC-41`) |
| TC-LOAD-07 | стрим: 200 одновременных зрителей, режимы `proxy` и `redirect` | отзыв действует на следующем запросе в обоих режимах; перерасход лимита ≤ аренда на поток; метрики заполнены |
| TC-LOAD-08 | перегрузка: ожидающая стоимость > порога | новые тяжёлые → `503` + `Retry-After`; `preview_frames` проходит; после разгрузки приём восстанавливается без вмешательства |
| TC-LOAD-09 | хаос: убийство воркера на каждом из этапов (ingest, detect, render) 3 раза подряд | после 3 попыток — dead letter, `VIDEO_JOB_ABANDONED`, резервы освобождены, согласователь не находит расхождений (`ACC-51`) |
| TC-LOAD-10 | 24-часовой «замачивание» с профилем 10 % от пика | нет роста: числа соединений БД, размера кэша исходников, числа незавершённых multipart; метрики стабильны |

## 13. Требования

| ID | Требование |
|---|---|
| VID-SC-01 | Видео-операции используют существующие классы очереди (`preview_frames` → `interactive`, остальные → `batch`) и пулы `video_light`/`video_heavy`; справедливость между арендаторами не нарушается. |
| VID-SC-02 | Число находящихся в системе заданий арендатора по группам ограничено значениями раздела 3.1; превышение — `VIDEO_TENANT_LIMIT` без побочных эффектов; проверка атомарна. |
| VID-SC-03 | Суточный бюджет стоимости ограничивает арендатора; повтор запроса не расходует бюджет дважды. |
| VID-SC-04 | При перегрузке пула новые задания (кроме `preview_frames`) отклоняются `VIDEO_CAPACITY_BUSY` с `Retry-After`; принятые продолжаются. |
| VID-SC-05 | Лимиты арендатора меняются оператором без релиза и видны клиенту в capabilities. |
| VID-SC-06 | Запись прогресса в БД ограничена `JOB_PROGRESS_DB_INTERVAL_MS` и порогом изменения; индексов по изменяемым столбцам нет. |
| VID-SC-07 | Трафик потока учитывается агрегатами и арендами; перерасход ограничен выданными арендами. |
| VID-SC-08 | Число потоков и их скорость ограничены (`STREAMS_PER_SESSION`, `STREAMS_PER_SHARE`, `STREAM_MAX_BYTES_PER_SECOND`) в режиме `proxy`. |
| VID-SC-09 | Автосохранение клиента не чаще `AUTOSAVE_MIN_INTERVAL_MS`; сервер отклоняет превышение `AUTOSAVE_SERVER_MAX_PER_MIN` без потери правок. |
| VID-SC-10 | Один узел скачивает исходник запуска не более чем ≈ один раз (≤ 1,2 ×). |
| VID-SC-11 | История, счётчики и незавершённые multipart очищаются по правилам 5.4 и 9.2; сирот нет. |
| VID-SC-12 | Исчерпание попыток переводит задание в `failed/VIDEO_JOB_ABANDONED` через dead letter с освобождением резервов; согласователь исправляет зависшие состояния. |
| VID-SC-13 | Метрики и оповещения раздела 10 реализованы; метки не содержат идентификаторов арендаторов и объектов. |
| VID-SC-14 | Режим доставки (`proxy`/`redirect`) переключается настройкой сервера без изменения клиента; отзыв доступа действует на следующем запросе в обоих. |
| VID-SC-15 | Все видео-таблицы удовлетворяют правилам шардирования раздела 11; нарушение выявляется автоматической проверкой. |
| VID-SC-16 | Нагрузочные и хаос-тесты раздела 12.2 выполняются ночью; результаты приложены к приёмке этапа. |
| VID-SC-17 | Формулы планирования раздела 9.3 заполнены измеренными значениями V0 и приложены к отчёту этапа V0. |
| VID-SC-18 | Предпросмотр кадров сглажен (debounce), один незавершённый запрос на монтаж, дедупликация на сервере (5.3a). |
| VID-SC-19 | Воспроизведение proxy владельцем идёт в режиме `redirect` и не проходит через Go-прокси. |
