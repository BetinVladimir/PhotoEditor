## 1. Хранилище объектов

| Оригинал видео | `video_original` | загрузка пользователя | да | ручное удаление |
| Оригинал аудио | `audio_original` | загрузка пользователя | да | ручное |

Правила:

1. Ключи объектов формирует только сервер (по образцу [`objectstore/original.go`](../../backend/internal/objectstore/original.go) и [`interchange_generation_key.go`](../../backend/internal/objectstore/interchange_generation_key.go)); имена пользователя в ключах отсутствуют; префикс класса `video/` позволяет lifecycle-правилам и очистке tenant работать по префиксу.
2. Бакет версионируемый: артефакт хранит `object_version`; чтение — всегда по версии.
3. CORS для прямой загрузки из браузера включает `PUT` и экспозицию заголовка `ETag` для `APP_ORIGIN` ([`compose.yaml`](../../deploy/compose.yaml), [`archive_cors.go`](../../backend/internal/objectstore/archive_cors.go)).
4. Воркеры читают и пишут через gateway ([`gateway/upload.go`](../../backend/internal/gateway/upload.go), [`gateway/download.go`](../../backend/internal/gateway/download.go)); прямого сетевого пути к MinIO у воркера нет. Крупные потоки идут потоково, без буферизации в памяти (требование из [`large_io_test.go`](../../backend/internal/gateway/large_io_test.go) распространяется на видео-пул).

### 1.2 Ограничения транспорта, найденные в исходниках

| Ограничение | Источник | Следствие для видео |
|---|---|---|
| Файл ≤ 512 МиБ, часть ≤ 16 МиБ в клиентской загрузке | [`upload.ts`](../../packages/api-client/src/upload.ts) | новый видео-контракт загрузки; старый путь не меняется |
| Не более 10 000 частей | там же | `part_bytes ≥ ceil(bytes / 9 000)` |
| Воркер: 20 ГиБ скачивания / 20 ГиБ загрузки на задание, scratch 12 ГиБ | [`compose.rtx-worker.yaml`](../../deploy/compose.rtx-worker.yaml) (`WORKER_MAX_DOWNLOAD_BYTES`, `WORKER_MAX_UPLOAD_BYTES`, `PHOTO_RTX_SCRATCH_BYTES`) | профиль «видео» поднимает scratch и лимиты; V1 ограничивает суммарный объём источников одного рендера значением ≤ 20 ГиБ; снятие ограничения — сегментный рендер (V2, [06](06-workers-and-models.md)) |
| `max_output_bytes`, `max_output_count` на операцию | [`operations.json`](../implementation-v2/contracts/operations.json) | видео-операции задают собственные пределы; рендер — `max_output_bytes` = размер резерва |
| `TaskResult.outputs ≤ 128`, прямых входов ≤ 127 + манифест | [19-runtime-protocol.md](../implementation-v2/19-runtime-protocol.md) | источники монтажа идут через манифест замыкания |

## 2. Загрузка

### 2.1 Параметры

- `part_bytes = max(32 МиБ, округлить_вверх(bytes / 9 000))` с округлением до МиБ; минимальный размер не последней части S3 (5 МиБ) соблюдён. Для 16 ГиБ это 512 частей по 32 МиБ.
- Параллельность частей на клиенте — 3 (настраивается политикой); URL частей выдаются пачками и живут ≤ 60 с.
- Просрочка простоя сессии — 7 суток; затем абортируется мультипарт и освобождается резерв (фоновая очистка по образцу [`interchange_drain.go`](../../backend/internal/objectstore/interchange_drain.go), [`recover.go`](../../backend/internal/objectstore/recover.go)).

### 2.2 Целостность

1. Клиент считает SHA-256 всего файла потоково до `begin`; значение входит в `request_sha256`.
2. Если собранная сборка MinIO поддерживает дополнительные контрольные суммы частей (`x-amz-checksum-sha256`), клиент их передаёт, а сервер проверяет при `complete`. Поддержка в закреплённом образе MinIO — **проверить до реализации**; без неё применяется п. 3.
3. При `complete` сервер проверяет размер и собирает объект; полный SHA-256 объекта вычисляет первый шаг ingest (`video.probe`) потоково при чтении и сравнивает с заявленным. Расхождение — `rejected` с кодом `UPLOAD_HASH_MISMATCH`, объект и производные удаляются, резерв освобождается.
4. Тип определяется по содержимому (probe), расширение и `Content-Type` клиента — подсказки.

### 2.3 Резерв на загрузку

В `begin` в одной транзакции создаётся резерв `holder_type = 'video_upload'` на `declared_bytes + оценка_производных`; оценка производных стартово = `min(0.15 × bytes, 4 ГиБ) + 128 МиБ` (калибруется по измерениям ingest). Нехватка места — отказ `VIDEO_QUOTA_EXCEEDED` до передачи. После успешного ingest резерв заменяется фактическими байтами артефактов, остаток возвращается. Неуспешный ingest освобождает всё, включая оригинал (`rejected` объект не хранится).

## 3. Модель квоты

Определения: `limit` — включённая ёмкость плана плюс купленные пакеты; `used` — сумма `bytes` всех готовых артефактов tenant (в том числе фото-артефакты проекта); `reserved` — сумма активных резервов. Допуск: `used + reserved + запрос ≤ limit`. Все проверки — на сервере внутри транзакции с блокировками в порядке, закреплённом в [worker-heartbeat-tenant-lock-order.md](../implementation-v2/runbooks/worker-heartbeat-tenant-lock-order.md).

### 3.1 Что считается

| Что | Как считается | Когда |
|---|---|---|
| Вход: оригиналы видео и аудио | фактический размер объекта | резерв при `begin`, фиксация при `verified` |
| Вход: производные (proxy, раскадровка, волна, probe) | фактический размер артефактов | при готовности ingest |
| Монтаж: документы ревизий | размер артефакта | при сохранении ревизии |
| Промежуточные результаты анализа (отчёты, превью-кадры) | размер артефакта | при готовности задания |
| Выход: рендеры и отчёты проверки | фактический размер | резерв при постановке, фиксация при `ready` |
| Scratch воркера | не считается в квоте tenant | ограничен ёмкостью воркера |

Это реализует требование «объём входного и выходного контента — в общий объём пользователя». Производные считаются как данные пользователя (Q-01 в [README](README.md)); если владелец продукта решит освободить proxy от квоты, меняется только таблица категорий, а не механизм.

### 3.2 Оценка выхода рендера

`оценка = ceil(duration_s × (maxrate_video + bitrate_audio) / 8 × 1.05) + 64 МиБ` для MP4. Рендер **всегда** выполняется с ограничением битрейта (`maxrate`/`bufsize`), поэтому оценка — верхняя граница. Воркер прерывает кодирование при превышении `max_output_bytes` и завершает задание ошибкой `OUTPUT_EXCEEDS_RESERVATION` (код задания, DS-24) без публикации результата. Профиль «качество по CRF без ограничения» в V1 запрещён.

### 3.3 Резервы заданий

1. `POST …/renders`, `…/cut-detections`, `…/color-analyses` и прочие создают резерв `holder_type = 'video_job'` в той же транзакции, что и run/outbox.
2. Завершение задания: в одной транзакции фактические артефакты переходят в `used`, остаток резерва освобождается, резерв обнуляется (образец — завершение `finish_semantic_target_*`, описанное в [03-database.md](../implementation-v2/03-database.md)).
3. Отмена и ошибка освобождают резерв целиком; частичные объекты помечаются на очистку (GC — [`00100_artifact_gc.sql`](../../backend/db/migrations/00100_artifact_gc.sql)).
4. Повтор после перезапуска воркера использует тот же резерв (без второго списания).
5. Просроченный резерв освобождается планировщиком; результат просроченного задания не принимается.

### 3.4 Исходящий трафик

- Считаются фактически отданные байты клиентам портала (стрим и скачивание) и скачивания владельца файлов-результатов. Проигрывание proxy внутри приложения владельцем в биллинговый счётчик не входит, но ведётся как служебная метрика.
- Учёт — событиями `video_egress_events` по байтам, реально записанным в ответ; прерванные передачи считаются по факту.
- Лимиты: общий (по плану, 10× включённого диска) и на ссылку (опционально). Исчерпание — отказ новым передачам `VIDEO_EGRESS_LIMIT`; клиент видит нейтральное сообщение, владелец — причину.
- Учёт использует тот же счётчик периода, что и фото-скачивания (B0–B4 биллинга); до его появления события накапливаются в таблице.
- Масштабирование учёта: поток агрегируется по часам и исполняется арендами бюджета, построчные события пишутся только для скачиваний — [20](20-saas-scaling-operations.md), 5.2.

### 3.5 Показ пользователю

Экраны V-01, V-02, V-09 и V-13 ([03](03-photographer-screens.md)) показывают `limit`, `used`, `reserved`, разбивку по категориям (исходники / производные / монтажи / результаты), трафик периода. До отправки пакета загрузок и перед рендером показывается потребность и нехватка; частичная отправка «сколько влезет» не выполняется молча.

## 4. Хранение и удаление

1. Оригиналы, монтажи и результаты хранятся до ручного удаления при оплаченной ёмкости; автоудаления нет (решение 18.10.2026 в billing-плане). Технические объекты (недозагрузки, превью-кадры, отчёты) очищаются автоматически и не считаются «пользовательским хранением».
2. Удаление медиа: владелец подтверждает; если медиа используется в монтажах, диалог перечисляет их; удаление оставляет в монтаже клипы с пометкой «источник удалён». Рендеры самостоятельны и удаляются отдельно.
3. Удаление идёт через состояние `withdrawing`: сначала недоступность для новых заданий, затем физическое удаление объектов с подтверждением, и только потом освобождается квота ([`remove_confirmed.go`](../../backend/internal/objectstore/remove_confirmed.go)). Опора — [project-asset-withdrawal-contract.md](../implementation-v2/project-asset-withdrawal-contract.md).
4. Удаление рендера, включённого в опубликованную выдачу, снимает его с выдачи; уже выданная подписанная ссылка живёт ≤ 60 с.
5. Очистка tenant и восстановление включают видео-префиксы ([`tenant_purge.go`](../../backend/internal/objectstore/tenant_purge.go), [v32-tenant-purge-buckets-runtime.md](../implementation-v2/v32-tenant-purge-buckets-runtime.md), [restore-контуры воркера](../../workers/photo_worker/runtime/restore_cleanup.py)). Политика резервного копирования больших оригиналов (включать или нет, срок) — решение владельца ([10](10-testing-acceptance-rollout.md#открытые-вопросы)); без решения видео-префиксы явно помечены «не входят в backup» в документации эксплуатации.
6. Ревизии монтажа с меткой `autosave` старше 30 дней и не связанные с рендером сворачиваются (остаётся последняя за сутки); ревизии с рендерами и ручные сохраняются.

## 5. Учёт использования для будущего тарифа

С первого релиза пишутся события использования (без тарификации): `video_compute_seconds{operation, backend}`, `video_output_bytes`, `video_egress_bytes`, `video_storage_bytes_by_category`. Режим `video_billing_mode` в capability: `beta_free` (по умолчанию) → `metered` после замеров себестоимости. Видеообработка не списывает «фото» и не входит в стандартный пайплайн до решения по замерам ([billing-prelaunch-plan](../implementation-v2/billing-prelaunch-plan-2026-10-18.md), раздел 2).

## 6. Требования

| ID | Требование |
|---|---|
| VID-Q-01 | Загрузка видео до 16 ГиБ возможна с возобновлением; максимальная память клиента не растёт с размером файла. |
| VID-Q-02 | Нехватка места обнаруживается до передачи данных (на `begin`) и до постановки задания; частичных побочных эффектов нет. |
| VID-Q-03 | Входные оригиналы, производные, документы монтажа и результаты учитываются в `used`; разбивка по категориям доступна API и UI. |
| VID-Q-04 | Резерв и состояние объекта меняются в одной транзакции; повтор запроса и перезапуск воркера не дублируют списание. |
| VID-Q-05 | Результат рендера не превышает резерв; превышение прерывает задание без публикации результата. |
| VID-Q-06 | Освобождение квоты при удалении происходит только после подтверждённого физического удаления объектов. |
| VID-Q-07 | Исходящий трафик клиентов портала учитывается по фактически отданным байтам; лимит исполняется. |
| VID-Q-08 | Ошибка загрузки/ingest/рендера не оставляет объектов, учитываемых в квоте, и не оставляет висящих резервов (проверка планировщиком и тестом GC). |
| VID-Q-09 | События использования пишутся с первого релиза; переключение на тарификацию не требует миграции данных. |
