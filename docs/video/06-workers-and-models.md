## 2. Каталог операций

Все операции регистрируются в реестре операций с версией `1`, пакетом `VID1` и ролями выхода из таблицы. Лимиты — стартовые.

| Операция | Класс / бэкенды | Назначение | Вход | Выход (роли) | Таймаут |
|---|---|---|---|---|---|
| `video.probe` | cpu | ffprobe, проверка допустимости, потоковый SHA-256 объекта, сводка; решает `ready/rejected` | оригинал | `video_probe` (JSON) | 900 с |
| `video.proxy` | gpu (`cuda`, `mlx`-хост с VideoToolbox) или cpu | proxy 540p/720p: CFR, короткий GOP, H.264, AAC, `faststart`; таблица соответствия времени оригинала | оригинал | `video_proxy`, карта времени | max(900, 0.6 × длительность) |
| `video.thumbs` | cpu | раскадровка: спрайты 160×90, адаптивный шаг, индекс; постер | оригинал | `video_filmstrip` | max(600, 0.3 × длительность) |
| `audio.waveform` | cpu | пики в двух разрешениях | оригинал | `video_waveform` | 600 с |
| `video.detect_cuts` | gpu (`cuda`, `mlx`, `mps`) и cpu (классический метод) | границы склеек | оригинал или proxy-эквивалент | `video_cut_report` (JSON + спрайт кадров «до/после») | max(900, 0.35 × длительность + 300) |
| `video.color_analyze` | gpu или cpu | статистика кадров, оценка баланса белого/экспозиции, предложение параметров | оригинал, диапазон | `video_color_report` | max(600, 0.2 × длительность) |
| `video.preview_frames` | gpu (быстрый пул) или cpu | ≤ 16 кадров ревизии с эффектами (JPEG) | документ монтажа, источники (замыкание) | `video_preview_frame` | 120 с |
| `audio.analyze` | cpu | BPM, сетка битов, интегральная громкость | аудио/видео | отчёт JSON | 600 с |
| `video.lut_validate` | cpu (пул `video_light`) | проверка загруженного `.cube` строгим разбором (`FN-L-06`); решает `ready/rejected` для `kind=lut` | `.cube` ≤ 20 МиБ | `video_probe` (JSON `LutValidateResult`) | 120 с |
| `video.render` | gpu (`cuda` NVENC; `mlx`-хост с VideoToolbox) или cpu (`libopenh264`; образ `gpl_internal` — `libx264`, см. [22](22-tools-models-licenses.md)) | финальный рендер ревизии | документ монтажа, манифест источников, пресет | `video_render`, `video_qc_report` | max(1800, 3 × длительность), не более 6 ч |

Граф ingest: `video.probe` → параллельно `video.proxy`, `video.thumbs`, `audio.waveform` → завершающая стадия, переводящая медиа в `ready` одной транзакцией (образец многостадийных графов — [09-workflow-transactions.md](../implementation-v2/09-workflow-transactions.md)). Для `kind=lut` граф состоит из одной операции `video.lut_validate`; для `audio` — `video.probe` и `audio.waveform`. Остальные задания — одиночные задачи.

**Проверка в реестре**: значения `timeout_seconds` до 6 часов превышают встречающиеся сейчас (1800 с); перед реализацией нужно проверить предельные значения lease/heartbeat в gateway и планировщике и при необходимости ввести продление lease по heartbeat. Это отдельный пункт работ `VID-WP-02`.

## 3. Аппаратные бэкенды

| Бэкенд | Что есть | Что требуется для видео |
|---|---|---|
| `cpu` | везде | классический детектор, `libopenh264` либо образ `gpl_internal` с `libx264` (только внутренние образы, [22](22-tools-models-licenses.md)), probe/thumbs/waveform, probe/thumbs/waveform |
| `cuda` | RTX-хост, `onnxruntime-gpu`, PyTorch CUDA ([`requirements-cuda.txt`](../../workers/requirements-cuda.txt)) | ffmpeg с NVDEC/NVENC, драйвер и лимиты одновременных NVENC-сессий, модель детектора для CUDA, бюджет VRAM |
| `mps` | PyTorch MPS, [`metal_budget.py`](../../workers/photo_worker/runtime/metal_budget.py) | допустим как переходный бэкенд для модели детектора; кодирование — VideoToolbox |
| `mlx` | **отсутствует** | новый бэкенд: зависимость `mlx`, адаптер модели детектора, `runtime/mlx_budget.py` (по образцу `metal_budget.py`), запись в `MODEL_BACKENDS`, проверка в `doctor.py`, запись квалификации воркера |

Решение D-06: `mlx` вводится как отдельное значение `PHOTO_WORKER_BACKEND`; на Mac-хосте кодирование и декодирование выполняются VideoToolbox, а ML-часть — MLX. Каждая пара «операция × бэкенд» имеет собственную квалификацию; отсутствие квалификации делает операцию недоступной на этом бэкенде с причиной в capability. Точки изменения для нового значения бэкенда (перечисляются в `VID-WP-03`): `runtime/service.py` (валидация конфигурации), `models/pool.py`, `models/backend_support.py`, `models/doctor.py`, схема квалификации воркера в БД и `deploy/*worker*.sql`, реестр операций.

Выбор бэкенда: запрос `auto` выбирает доступный квалифицированный бэкенд по политике ёмкости; пользователь может явно запросить `cuda`, `mlx` или `cpu` (если квалифицирован). Результат хранит `backend_used`; различия между бэкендами документируются в метриках качества, а не скрываются.

## 4. Модели

Кандидаты перечислены для бенчмарка фазы V0; выбор фиксируется записью в замке моделей с хешем весов и тремя лицензиями (код, веса, данные обучения). Загрузка в рантайме из сети запрещена (установка офлайн, как у остальных моделей). **V1 не зависит от сторонних весов:** границы склеек определяет классический метод; нейросетевой метод включается только утверждённой записью замка ([22](22-tools-models-licenses.md), D-18).

### 4.1 Детекция границ склеек

| Кандидат | Тип | Плюсы | Что проверить |
|---|---|---|---|
| TransNet V2 | компактная 3D-CNN, выход: вероятности резких и плавных границ по кадрам | малый размер, высокая скорость, известные метрики; подходит для переноса на MLX | **код MIT; готовые веса не берём:** обучены на IACC.3 и ClipShots (ролики без подтверждённой лицензии на такое применение, [22](22-tools-models-licenses.md), 3.1). Архитектура используется с **собственными весами** (`VID-WP-18`); перенос на ONNX/MLX; качество на плавных переходах |
| AutoShot (2023) | поиск архитектуры, обобщённее по типам видео | потенциально точнее на пользовательском видео | **исключён:** код, веса и лицензия не найдены (в статье «will be released») |
| PySceneDetect (content/adaptive) | классический, CPU | резервный метод без GPU, прозрачные пороги | BSD-3-Clause подтверждена; используется как **эталон бенчмарка V0**, в образ воркера не входит; качество на затемнениях и вспышках |

Решение (D-18): V1 использует классический метод ML-02 на всех бэкендах. Нейросетевой метод — TransNet V2 по архитектуре (код MIT) с собственными весами, обученными на данных с разрешающими лицензиями ([22](22-tools-models-licenses.md), раздел 8); готовые веса из репозитория и портов Hugging Face не используются без письменного исключения. Метод `model` попадает в capability только при утверждённой записи замка. Не выбирается кандидат, чьи веса или данные обучения имеют несовместимую с коммерческим применением лицензию.

Конвейер детекции:

1. Декодирование ffmpeg (аппаратное, если доступно) в RGB небольшого размера с фиксированной частотой исходного ряда кадров; для VFR используется карта времени, а не усреднённая частота.
2. Скользящее окно с перекрытием, объединение прогнозов, пороги из параметров (чувствительность 1–5 → калиброванные пороги).
3. Постобработка: слияние близких событий (минимальная длина плана по умолчанию 8 кадров), подавление вспышек (однокадровая яркостная аномалия — тип `flash`, не `cut`), распознавание затемнения/появления из чёрного классической проверкой яркости как дополнение модели.
4. Отчёт `CutReport` (схема): `schema_version, media_id, source_sha256, model {id, lock_sha, backend}, method ('model'|'classic'), params, fps {num, den}, frame_count, boundaries[ {id, kind ('cut'|'dissolve'|'fade_in'|'fade_out'|'flash'), frame_in, frame_out, start_ticks, end_ticks, confidence} ], thumbnails_ref`. Границы отсортированы, `id` стабилен для одного отчёта. Уверенность откалибрована на проверочном наборе и документирована как оценка, а не вероятность гарантии.
5. Спрайт кадров «до/после» на каждую границу выпускается тем же заданием, чтобы UI V-04 не запускал декодирование.

Точность и скорость (цели для калибровки, не измерения): F1 по резким границам ≥ 0.9 и по плавным ≥ 0.7 на согласованном проверочном наборе (синтетика с известной разметкой плюс лицензионно чистые ролики); пропускная способность ≥ 20× реального времени для 1080p на RTX-классе и ≥ 8× на Apple Silicon. Разница F1 между бэкендами ≤ 1 пункта — условие квалификации.

### 4.2 Цвет и звук

- **Цветоанализ**: без новой нейросети в V1. Статистика кадров (перцентили яркости, оценка нейтральной точки по средним тонам, дисбаланс каналов, оценка контраста), предложение параметров из них. Используются существующие численные модули ([`algorithms/color.py`](../../workers/photo_worker/algorithms/color.py), [`algorithms/statistics.py`](../../workers/photo_worker/algorithms/statistics.py), [`algorithms/torch_color.py`](../../workers/photo_worker/algorithms/torch_color.py), [`algorithms/style.py`](../../workers/photo_worker/algorithms/style.py)); «подбор по эталону» — перенос статистик в Lab с ограничением силы, результат оформляется параметрами эффектов, а не скрытой обработкой.
- **Анализ звука**: темп и биты — собственный алгоритм ML-04 на `numpy`/`scipy` по звуку, декодированному `ffmpeg` (`librosa` в рабочий образ не входит, [22](22-tools-models-licenses.md), D-19); громкость — `ffmpeg ebur128`/`loudnorm`. Библиотеки и модели с некоммерческими весами или сетевым копилефтом (`madmom`, `Essentia` и подобные) не используются без отдельного решения; Beat This! — кандидат V2 после проверки лицензий чекпойнта и обучающей музыки.
- **Люди и лица**: в видео не обнаруживаются и не распознаются (решение вне объёма, см. [09](09-security-privacy.md)).

## 5. Рендер

### 5.1 Двигатель V1: граф ffmpeg

1. Воркер получает: документ монтажа (ревизия), манифест замыкания источников, пресет. Проверяет хеши документа и источников по манифесту, схему и лимиты ([07](07-timeline-edl-and-render-spec.md)).
2. Чистая детерминированная функция `compile_graph(document, preset, runtime)` строит `filter_complex` и командную строку; результат — канонический JSON-«план рендера» (хешируется в `render_fingerprint`). Функция не обращается к файловой системе и покрыта golden-тестами.
3. Цвет всех пиксельных эффектов клипа сворачивается в **одну 3D-LUT** (65³, float32, детерминированная генерация на CPU/GPU по общей формуле), применяемую фильтром `lut3d` с тетраэдрической интерполяцией; промежуточное представление 10 бит и выше, финальное квантование с дизерингом. Так поведение не зависит от бэкенда (только от математики LUT), а предпросмотр кадров и рендер используют один и тот же генератор.
4. Переходы: `cut`, `crossfade` (`xfade=fade`), `dip_to_black`, `fade`. Фото: масштабирование с суперсэмплингом и движением (Ken Burns) через `crop`/`scale` с детерминированной функцией замедления — не `zoompan` с его дрожанием на субпикселях.
5. Звук: на клип `atrim/asetpts/volume/afade/aresample=48000`; микс `amix` без автонормализации; ducking `sidechaincompress` от дорожки речи; итоговая громкость — двухпроходный `loudnorm` до цели с `alimiter`.
6. Кодирование: `h264_nvenc` (cuda), `h264_videotoolbox` (mlx/mps-хост), `libopenh264` (cpu); `libx264` — только в образе профиля `gpl_internal` ([22](22-tools-models-licenses.md), D-20, D-21). Кодировщик выбирает `pick_h264_encoder` (TK-922), всегда с `maxrate/bufsize`, `-pix_fmt yuv420p`, тегами `bt709`, `-movflags +faststart`, `-map_metadata -1`.
7. Проверка результата (`video_qc_report`): ffprobe (контейнер, потоки, длительность в пределах ±1 кадра от ожидаемой), полное декодирование без ошибок, детектор чёрных кадров/тишины как предупреждения, SHA-256 и размер ≤ резерва. Без успешной проверки результат не публикуется.

Двигатель V2 (`tensor-pipeline`): покадровая обработка тензорами на GPU (PyTorch CUDA / MLX) с аппаратным кодированием; включается отдельным решением после сравнения скорости и точности с V1; выбор двигателя записывается в `render_fingerprint`.

### 5.2 Детерминизм и допуски

Побайтовое совпадение между бэкендами не обещается (NVENC и VideoToolbox дают разные потоки). Обещается: одинаковая длительность в пределах ±1 кадра, одинаковая раскладка потоков, цветовое расхождение с эталонным CPU-рендером не выше порога (ΔE по контрольным кадрам, стартово ≤ 1.5 в среднем и ≤ 4 в 99-м перцентиле), громкость в пределах ±0.5 LU от цели. Тесты проверяют эти допуски, а не равенство байтов.

### 5.3 Рендер по сегментам (V2)

Разбиение на сегменты по жёстким склейкам с независимым рендером на нескольких воркерах и последующим `video.concat` без перекодирования снимает ограничения 20 ГиБ и ускоряет длинные работы. Ограничения: переходы лежат внутри сегмента; число выходов ≤ 128 на задачу (шардирование через документы-манифесты); общая нормализация громкости требует отдельного прохода анализа. Включается после стабилизации V1.

## 6. Среда выполнения ffmpeg

Требования безопасности к `runtime/ffmpeg.py` (новый), дополняющие [09](09-security-privacy.md):

1. Запуск как подпроцесс без оболочки, со списком аргументов; пути только внутри каталога задачи; вход — только файлы, подготовленные gateway.
2. `-nostdin`, `-protocol_whitelist file,pipe`, ограничения `-probesize`, `-analyzeduration`, `-max_alloc`; запрет сетевых протоколов, `concat`-демультиплексора с произвольными путями, внешних субтитров и вложений; нужные потоки выбираются явно (`-map`), остальные игнорируются.
3. Лимиты ресурсов: CPU, память (`ulimit`/cgroup), число потоков, время; запуск в отдельной группе процессов для надёжного завершения.
4. Корневая файловая система контейнера только для чтения, `cap_drop: ALL`, `no-new-privileges`, сеть — только к gateway (как у [`compose.rtx-worker.yaml`](../../deploy/compose.rtx-worker.yaml)).
5. Парсинг `-progress pipe:1` в проценты и стадии; stderr ограничен по объёму и санитизируется перед записью в журнал.
6. Версия ffmpeg, список включённых кодеков и лицензионный режим сборки фиксируются в образе и попадают в `render_fingerprint`. Образы, уходящие в эксплуатацию, содержат только LGPL-сборку; проверки FN-X-02, обязательный набор фильтров и сканирование образа — [22](22-tools-models-licenses.md), раздел 7.3–7.4.

## 7. Прогресс, отмена, повтор

- Воркер публикует стадию и прогресс не реже раза в 5 с (heartbeat продлевает lease); бэкенд пишет в БД не чаще раза в 2 с и рассылает `video.job.progress`.
- Отмена: сигнал отмены доставляется как отзыв lease; воркер завершает группу процессов за ≤ 10 с, удаляет scratch, не публикует частичные объекты; состояние — `cancelled`.
- Потеря воркера: lease истекает, задача выдаётся другому воркеру; промежуточных результатов между попытками нет, публикация артефактов атомарна в конце.
- Повторяемые детерминированные ошибки (`VIDEO_CORRUPT`, падение декодера на том же месте) после двух попыток переводят задание в `failed` без бесконечных повторов; медиа получает `failed` с кодом.
- OOM: одна повторная попытка на квалифицированном малом профиле (меньше потоков, без аппаратного декодирования), затем `RESOURCE_EXHAUSTED`.

## 8. Ёмкость и ресурсные профили

1. Допуск вычисляет оценку ресурсов из probe и пресета: RAM, VRAM, scratch (источники в обработке + выход + запас 20 %), число декодеров/кодировщиков, ожидаемое время. Профили учитывают удерживаемые промежуточные данные (правило из [metal-alternatives-implementation.md](../implementation-v2/metal-alternatives-implementation.md)).
2. Видео-операции исполняются отдельными пулами `video_light`/`video_heavy` и в существующих классах очереди (`preview_frames` → `interactive`, остальные → `batch`); справедливость между арендаторами обеспечивает уже существующая ротация внутри класса, стоимость задания считает `FN-Q-09`. Решение и числа — [20](20-saas-scaling-operations.md), разделы 1–4. Проверка того, что реестр операций (`execution_pool`) допускает новые пулы, — допущение A-4 (`TK-001`).
3. Профиль воркера «видео»: NVMe-scratch по расчёту (минимум 2 × размер самого большого допустимого задания), лимиты скачивания/загрузки ≥ 20 ГиБ, учёт лимита одновременных сессий NVENC, бюджет VRAM через `cuda_budget`/`mlx_budget`.
4. Лимиты на tenant (находящиеся в системе задания по группам, суточный бюджет стоимости, порог перегрузки пула) заданы в [20](20-saas-scaling-operations.md), раздел 3, меняются оператором без релиза и показываются в capability (`DS-30`).

## 9. Квалификация

Каждая операция × бэкенд проходит квалификацию по существующей процедуре ([render-qualification-operator.md](../implementation-v2/runbooks/render-qualification-operator.md), [processing-worker-requalification.md](../implementation-v2/runbooks/processing-worker-requalification.md)): установка моделей по замку, `doctor`, прогон набора проверок (детекция — метрики на размеченном наборе; рендер — допуски раздела 5.2; probe — негативные/злонамеренные образцы), запись доказательств. Только после этого флаг операции включается. Исторические результаты на другой сборке не переносятся.

## 10. Требования

| ID | Требование |
|---|---|
| VID-W-01 | Все операции из раздела 2 зарегистрированы в реестре операций с ролями выхода, лимитами и таймаутами; операции без квалификации недоступны. |
| VID-W-02 | Воркер читает и пишет объекты только через gateway; результаты задачи публикуются атомарно в конце. |
| VID-W-03 | Детекция границ работает на `cuda` и `mlx` (после квалификации) и на CPU классическим методом; выбранный метод и бэкенд записаны в отчёте. |
| VID-W-04 | Рендер по зафиксированной ревизии воспроизводим в допусках раздела 5.2; `render_fingerprint` сохраняется. |
| VID-W-05 | Прогресс, стадия, отмена и повтор работают для всех долгих операций; отмена завершается ≤ 10 с и не оставляет объектов. |
| VID-W-06 | Недоверенные файлы обрабатываются в ограниченной среде по разделу 6; набор злонамеренных образцов проходит без выхода за каталог задачи и без сетевых вызовов. |
| VID-W-07 | Рендер не превышает резерв по размеру; превышение прерывает задание. |
| VID-W-08 | Видео-нагрузка не ухудшает время фото-операций сверх заданного порога (измеряется нагрузочным тестом). |
| VID-W-09 | Новый бэкенд `mlx` не включается, пока для него нет записи `MODEL_BACKENDS`, проверки `doctor` и квалификации воркера. |
