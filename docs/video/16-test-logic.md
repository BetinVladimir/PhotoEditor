# 16. Логика тестирования

Статус: спроектировано, не реализовано (2026-10-22). Начало: [README](README.md). Тесты ниже **описаны, но не написаны и не запускались в репозитории**; запускались только эталонные скрипты, которые породили [`vectors/`](vectors/) (раздел 2). Задачи — [15](15-task-cards.md); критерии приёмки — [17](17-acceptance-and-dod.md).

## 1. Принципы

1. **Спецификация раньше кода.** Ожидаемые значения берутся из [`vectors/`](vectors/) и таблиц этого документа, а не из вывода тестируемого кода.
2. **Пропуск ≠ приёмка.** Тест, который пропущен (`skip`, `xfail`, нет `ffmpeg`, нет GPU), не считается пройденным. В отчёте он значится отдельной строкой «не выполнено: причина».
3. **Детерминизм.** Нет обращения к текущему времени, сети, случайным числам без зерна. Property-тесты используют генератор из раздела 4.3 с зерном `12345`.
4. **Один тест — одна причина падения.** Имя теста содержит ID кейса (`SP-04`, `TC-T-VAL-08`).
5. **Тест не подстраивается под код.** Если вектор противоречит реализации — сначала выяснить, чей он дефект (п. 5.4 документа 12).
6. **Независимость слоёв.** Чистые функции тестируются без базы, сети и файловой системы; интеграционные тесты — на реальных PostgreSQL, MinIO, RabbitMQ стенда.
7. **Общий стенд** (БД, MinIO, брокер) один; тесты, которые его меняют, не запускаются параллельно друг с другом.
8. **Мутационный контроль.** Для функций с векторами исполнитель обязан убедиться, что тест **краснеет** при намеренной порче (например, `<` заменить на `<=`), и приложить вывод (раздел 12.2, пункт 4).

## 3. Правила сравнения

| Величина | Сравнение |
|---|---|
| Целые (тики, кадры, байты, номера) | точное равенство |
| Документ монтажа | равенство **канонических байт** (JCS), а не `deepEqual` |
| Хеш | точное равенство строки из 64 hex |
| Вероятности `confidence` | равны после округления до 4 знаков (точно) |
| Цвет `exposure`, `cdl`, `srgb_to_linear`, `pchip`, LUT-узлы | `abs(a−b) ≤ 1e-6` |
| `lab`, `delta_e76` | `abs(a−b) ≤ 1e-3` |
| ΔE76 между кадром превью и кадром рендера | ≤ 1.0 (среднее по кадру) и ≤ 3.0 (максимум по 99-му процентилю) — после потерь кодека |
| Число кадров файла | точное (`ffprobe -count_frames`) |
| Длительность файла | `abs(d − ожидаемое) ≤ 0.02 с` |
| Громкость (интегральная, LUFS) | `abs(измерено − цель) ≤ 0.5 LU` |
| Границы детекции на фикстурах | `frame_in`, `frame_out` в пределах ±2 кадров; точность — F1 (раздел 6) |
| Время ответа API в тестах | не проверяется (нагрузочные — отдельно, раздел 9) |

## 4. Чистые функции: кейсы и способ проверки

### 4.1 Команды монтажа (FN-T-05…10)

Алгоритм теста (одинаковый в TS и Go), для каждого элемента `commands.json.cases`:
1. Взять `commands.json.base` (для `SP-06` — результат `set_speed(base, 'c2', 2, 1)`; для `AC-03` — результат `AC-01`).
2. Вызвать функцию по полю `op` с `args` (имена в [15](15-task-cards.md), TK-303).
3. Если `expect.error` — результат должен быть ошибкой с этим кодом. Иначе — канонические байты результата равны каноническим байтам `expect.doc`; для `apply_cuts` дополнительно `applied` равен `expect.applied` (порядок и поля).
4. Входной документ не изменён (канонические байты до и после вызова равны).

### 4.2 Валидатор (FN-T-12)

Файл `validate_cases.json`: `base_doc`, `base_ctx`, `cases[]` с полями `patches[]` (`{"op":"set","path":"<JSON Pointer>","value":…}` — заменить значение по указателю; `{"op":"append","path":…,"value":…}` — добавить в массив), `ctx_patch` (верхнеуровневая замена ключей контекста) и `expect[]` (список `{rule, pointer, code}`). Тест: применить патчи к **глубокой копии** `base_doc`, контекст = `base_ctx` с `ctx_patch`, вызвать валидатор и сравнить список целиком (порядок значим). Для Go/Python контекст имеет те же имена полей (`sourceDurations`, `sourceStates`, `sourceHashes`, `musicClipIds`, `forRender`).

### 4.3 Property-тесты (только TS, `video-timeline-store.test.ts`)

Генератор: `state = 12345`; `next() = (state = (state × 1664525 + 1013904223) mod 2³²) / 2³²`. Последовательность из 200 шагов; на каждом шаге: `k = floor(next() × 5)` → операция [`split`, `trim`, `move`, `delete`, `speed`]; клип = `clips[floor(next() × clips.length)]` (по порядку обхода дорожек); параметры: `split.at` = `clip.at + FT × (1 + floor(next() × max(1, dur/FT − 1)))`; `trim.pos` = `clip.at + FT × floor(next() × (dur/FT))`, край = `next() < 0.5 ? 'in' : 'out'`; `move.new_at` = `FT × floor(next() × 500)`; `speed` = случайная из [`1/2`, `2/1`, `3/2`, `1/1`]; `delete.ripple = next() < 0.5`. Ошибочные результаты пропускаются (не считаются). Проверяемые свойства: (П1) после каждого успешного шага `validateDocument` не выдаёт VT-04/VT-05 (при `sourceDurations` = 20 с на источник); (П2) 200 раз `undo` возвращает исходный документ (канонически); (П3) `redo` ×N восстанавливает конечный документ; (П4) `canonicalize` двух равных документов с разным порядком ключей совпадает. Дополнительно (TK-621, TK-622): (П5) 200 случайных команд FN-T-15…27 тем же генератором (операция `k = floor(next() × 13)` по порядку FN-T-15…27, аргументы — из множества кейсов `editor.json → commands` с `expect.doc`, подставленных к текущему документу) — после каждой успешной команды `validateDocument` не выдаёт VT-03, VT-04, VT-07; (П6) `inverse` каждой успешной команды возвращает предыдущий документ канонически; (П7) `undo` ×N после N успешных команд возвращает исходный документ.

### 4.4 Файлы `.cube` (FN-L-06, FN-U-09)

`cube_cases.json`: `gen` описывает, как построить текст (`identity` — единичная LUT размера N; `drop_rows`, `replace_row`; `header_only`; `pad_comment` — комментарий до заданного размера; `text` — литерал). Ожидание: `TC-L-CUBE-00` разбирается (размер 17, 4913 узлов, узел `r=16,g=0,b=0` равен `(1,0,0)`), `01…10` — ошибка `LUT_INVALID`.

### 4.5 Range-прокси (FN-G-12)

`range_cases.json`: функция `ParseRange(header, size)` возвращает `(status, start, end)`; `status ∈ {200, 206, 416}`; для 200 — весь объект (`start=0`, `end=size−1`); для 416 `start/end` не определены (тест проверяет `null`/`-1`). Обработчик дополнительно: заголовки `Content-Range: bytes start-end/size` (для 206), `Content-Length = end−start+1`, `Accept-Ranges: bytes`; для 416 — `Content-Range: bytes */size`.

### 4.6 Время, квота, цвет, канонизация

Тест — цикл по всем элементам соответствующей секции JSON с допусками раздела 3. Для `canonical.json` в TS, Go и Python вычисляется `canonical` и `sha256` — **три языка обязаны дать одинаковые строки** (это и есть межъязыковая фикстура VID-T-02). Для `quota.json` отдельно проверить: `render_estimate` для `duration_ticks = 7620480000000` совпадает с вектором (проверка отсутствия переполнения 64-битных целых: в Go — `math/big`, в TS — `BigInt`).

## 6. Качество детекции границ

### 6.1 Метрика

Функции FN-C-03…05 ([14](14-function-catalog.md)). Две группы: резкие (допуск ±2 кадра) и плавные (IoU ≥ 0.3), `flash` не оценивается. Итоговая F1 по фикстуре = `prf(tp, fp, fn)` суммарно по группам.

### 6.2 Пороги приёмки

| Набор | Метод | Порог |
|---|---|---|
| `hard_cuts.mp4` | классический | F1 = 1.0 (2 из 2, без лишних) |
| `dissolve.mp4` | классический | F1 = 1.0 |
| `fades.mp4` | классический | F1 = 1.0 (`fade_out` и `fade_in`) |
| те же три файла | модель (`cuda` / `mps` / `mlx`) | F1 ≥ 0.9 по резким, ≥ 0.7 по плавным (цели S2 из [10](10-testing-acceptance-rollout.md)) — измеряется на каждом квалифицируемом бэкенде |
| размеченный набор реальных роликов (V0) | модель | пороги задаёт отчёт V0; до него — «не измерено» |
| паритет бэкендов | модель | макс. модуль разности `p_cuda − p_mlx` ≤ 0.02 на `hard_cuts.mp4`; множества границ совпадают по классу и `±2` кадра |

Классический детектор проверен эталоном (`ref_classic.py`): `hard_cuts` → `cut 50`, `cut 100`; `dissolve` → `dissolve 45–54`; `fades` → `fade_out 34–49`, `fade_in 51–66`. Это — **ожидаемый вывод в пределах ±2 кадров** (`fixtures_expect.json`).

### 6.3 Что НЕ доказывает эта проверка

Синтетические фикстуры простые: на реальных роликах (быстрое движение, вспышки, титры) качество будет ниже. Поэтому приёмка модели обязательно включает размеченный набор реальных роликов (V0); без него заявление «детекция работает» не делается.

## 7. Тесты БД (SQL)

Стенд: PostgreSQL из `make dev-infra`; применять миграции так, как это делают существующие интеграционные тесты (открыть любой из [`tests/integration`](../../tests/integration)). Обязательные категории:

1. **Применение**: на пустой БД; на БД с данными (счётчики строк существующих таблиц до/после равны).
2. **Ограничения**: для каждого `CHECK` из DS-02…06 — вставка строки, нарушающая его, даёт ошибку, а допустимая — проходит (таблица кейсов в [15](15-task-cards.md), TK-101…105).
3. **ACL**: для каждой новой таблицы и каждой роли (`photo_api, photo_worker, photo_scheduler, photo_auth, photo_portal, photo_publisher, photo_maintenance, photo_gateway`) `SELECT/INSERT/UPDATE/DELETE` → `permission denied`; для каждой функции — `EXECUTE` разрешён только ролям из FN-D.
4. **Конкурентность** (барьерная схема): N соединений открывают транзакции, ждут общий барьер (`pg_advisory_lock` либо `threading.Barrier`), одновременно вызывают функцию; проверка итогового состояния.
   - Резерв квоты: `limit = 100 ГиБ`, 8 параллельных `begin` по 20 ГиБ → успешны **ровно 5**, остальные 3 получают `VIDEO_QUOTA_EXCEEDED`; сумма резервов = 100 ГиБ; `used + reserved ≤ limit` в каждый момент (проверка после каждой транзакции).
   - CAS ревизии: два параллельных `save` с `expected_revision=3` → одна ревизия 4, один конфликт; `head_revision = 4`; в `video_sequence_revisions` одна строка с `revision=4`.
   - Завершение ingest: два параллельных `finish_video_ingest` → одно изменение состояния, резерв закрыт один раз.
5. **Идемпотентность**: повтор каждой мутирующей функции с тем же ключом возвращает тот же результат и не меняет состояние (`revision` не растёт).
6. **Сбои**: исключение внутри функции после частичных вставок откатывает всё (искусственный `RAISE EXCEPTION` через тестовый флаг сессии либо через неверный аргумент в конце функции).

## 8. Интеграция и сценарии (бэкенд + MinIO + воркер)

| ID | Сценарий | Шаги и проверки |
|---|---|---|
| TC-INT-01 | Загрузка 1 ГиБ с обрывом | сгенерировать файл (`байт i = i mod 251`); `begin`; загрузить 10 частей; оборвать клиент; создать новый контроллер; продолжить; `complete`; проверить `state=verified`, SHA-256 объекта = SHA-256 файла |
| TC-INT-02 | Нехватка места | лимит 1 ГиБ, `begin` на 2 ГиБ → `VIDEO_QUOTA_EXCEEDED`, нет ни сессии, ни резерва, ни объекта |
| TC-INT-03 | Ingest `hard_cuts.mp4` | после `complete` медиа `ready` ≤ 60 с; `probe` содержит 150 кадров/25 к/с; есть proxy, filmstrip, waveform; квота: `used` вырос на сумму фактических байт |
| TC-INT-04 | Отклонённый файл | случайные байты → `rejected`, код `VIDEO_UNSUPPORTED_FORMAT`; квота вернулась; объект удалён |
| TC-INT-05 | Детекция | на `hard_cuts.mp4`: задание → отчёт содержит `cut 50`, `cut 100`; применить обе → 3 клипа |
| TC-INT-06 | Рендер G1 | монтаж из двух клипов `srcA`/`srcB` → рендер `ready`; `qc.verdict=pass`; длительность 5.000 с ±1 кадр |
| TC-INT-07 | Отмена рендера | отмена через 2 с после старта → состояние `cancelled` ≤ 10 с; нет объекта `video_render`; резерв освобождён |
| TC-INT-08 | Падение воркера | убить процесс воркера в середине рендера; после перезапуска задание завершается один раз; рендер ровно один; квота списана один раз |
| TC-INT-09 | Выдача | опубликовать; запрос Range из портала возвращает 206 и `Content-Range`; `unpublish` → следующий запрос 410; событий трафика = сумме отданных байт |
| TC-INT-10 | Удаление | удалить медиа, используемое в монтаже → без `confirm_in_use` 409 со списком; с ним — удалено, клип помечен «источник удалён»; квота освобождается **после** физического удаления (проверка: до подтверждения удаления объекта `used` не уменьшился) |
| TC-INT-11 | Изоляция tenant | пользователь tenant B запрашивает медиа/монтаж/рендер/выдачу tenant A → везде ответ как «не найдено» (404), тело одинаково |
| TC-INT-12 | Восстановление SSE | оборвать поток событий; клиент возобновляет по курсору; события не потеряны и не дублированы |

Крупный файл 16 ГиБ (TC-INT-13) — ночной/релизный прогон: генератор записывает файл потоком; хеш считается тем же потоком; тест подтверждает, что память клиента не превышает 256 МиБ (измерение пикового RSS процесса) и что возобновление работает после принудительного завершения на 50 %.

## 10. Тесты интерфейса

Шаблон DOM-теста (для каждого экрана, образцы — существующие `*.dom.test.tsx`): 1) отрисовка состояний: `loading`, `empty`, `error`, `forbidden`, `offline`, `unavailable`, `cancelled`, `recovering` — для каждого проверить наличие ожидаемого локализованного текста по ключу; 2) основное действие вызывает ровно один запрос (поддельный `fetch`/API-клиент, счётчик вызовов); 3) повторное нажатие до завершения не создаёт второй запрос; 4) ответ другого tenant отвергается (экран показывает ошибку, а не данные); 5) после неоднозначного ответа выполняется GET-сверка, а не повторный POST; 6) `AbortController` срабатывает при уходе с экрана (размонтирование) — проверка `signal.aborted`.

Сквозные UI-тесты: `paper-ui-policy.test.ts` (в нём перечислены запрещённые импорты; новые файлы подпадают автоматически — **проверить**, что список сканируемых каталогов включает `screens/video` и `src/video-*`; если нет — расширить тест в TK-600); `video-locale.test.ts` (TK-005); доступность: для каждого экрана замерить размер шрифта и контраст по существующей методике (источник — `grep -rn "contrast" apps/photographer/src --include=*.test.*`, использовать найденный образец).

Реальный браузер (ручной/автоматизированный чек-лист, фиксируется в отчёте): S1…S8 из [10](10-testing-acceptance-rollout.md), раздел 5, с шагами: открыть `/video` → загрузить `hard_cuts.mp4` → дождаться `ready` → запустить детекцию → принять границы → открыть монтаж → разрезать, добавить `srcB`, добавить цветовой эффект, добавить музыкальный клип с декларацией → рендер → скачать/просмотреть результат → создать выдачу → открыть ссылку в портале в отдельной сессии → снять с публикации → проверить отказ.

## 11. Безопасность

TK-801 (злонамеренные образцы) и: межтенантные запросы (TC-INT-11); подпись URL частей — просроченный URL (61 с) → 403; запрос части чужой сессии → 404; попытка `Range` на чужой рендер → 404; инъекция аргументов ffmpeg (`;`, `&&`, `concat:`, `file:`) в имя файла/параметры → отклонено, процесс не запущен; логи и SSE не содержат имён файлов и секретов (поиск по журналам тестового прогона по маркерному значению имени файла `SECRET_NAME_9f3a`).

## 12. Порядок запуска и отчёт

### 12.1 Команды (из корня репозитория)

| Слой | Команда |
|---|---|

| SQL | `python -m pytest tests/integration/test_video_*.py -q -p no:cacheprovider` |
| Всё | `make test` и `make test-db` |

### 12.2 Формат отчёта о тестах

Для каждой задачи исполнитель прикладывает (раздел 7 документа [17](17-acceptance-and-dod.md)): команду; последние 20 строк вывода с итоговой строкой `N passed, 0 failed`; число пропущенных (должно быть 0, иначе список с причинами); результат мутационного контроля (какую порчу внёс, какой тест покраснел, что вернул код в исходное состояние).

### 12.3 Нестабильные тесты

Тест, который хотя бы раз упал без изменения кода, считается дефектом. Запрещено «лечить» повтором или увеличением таймаута без выяснения причины. Для сетевых/временных зависимостей использовать поддельные часы и поддельный транспорт.

Сквозные (e2e) сценарии и потоки: [18](18-use-cases.md), [19](19-user-flows-e2e.md).
