## Приоритет и границы

ТЗ 4.1 — источник продуктовых требований. Этот комплект закрывает его неоднозначности решениями ADR в 01. Старые `architecture.md`, `current-pipeline.md`, `implementation.md`, e2e-документы описывают legacy и не переопределяют целевую архитектуру. Исправление утверждённого решения требует изменения ADR, соответствующих контрактов, миграций и проверок одним изменением. Нельзя молча подменять модели, пропускать функции или объявлять stub завершённой функцией.

Интерфейсы и алгоритмы здесь заданы до уровня публичных функций/методов, их входов, выходов, транзакций и ошибок. Приватные вспомогательные функции можно выделять при реализации без изменения контрактов. Подписи в таблицах используют типы из 15 и общие правила соответствующего языка; все ошибки типизированы.

Точные хеши ещё не скачанных моделей, совместимые patch-версии библиотек и аппаратные результаты не выдумываются. Их получение — обязательный пакет P01 с автоматическими критериями завершения. Архитектурный выбор от этого не откладывается. Аналогично отсутствующие фотографические эталоны блокируют заявление о качестве, но не реализацию функций.

## Протокол работы модели-разработчика

Выбрать первый незавершённый пакет из 13, проверить зависимости, прочитать связанные документы и актуальный код. Реализовать контракт вместе с негативными и интеграционными проверками. Сгенерировать схемы и SDK из единственного источника, выполнить проверки пакета, сохранить результат в `docs/implementation-progress/<package>.json`: status, commit, files, checks с exit codes, evidence paths, deviations. Создание этих записей начинается при разработке; в текущем комплекте ни один новый компонент не помечен реализованным.

При сбое теста исправить причину; не снижать пороги для получения PASS. При недоступном оборудовании/данных записать `blocked_external` для соответствующей проверки и продолжить независимые пакеты. Нельзя заменять такую проверку вымышленными результатами. Релиз разрешён только после всех gates P18.

Дополнительный нормативный документ: [16 — внутренние API, SQL-функции и границы сервисов](16-internal-contracts.md). Читать вместе с02–06.

Проверка этого комплекта: `python3 validate-docs.py` (нужен пакет jsonschema). [Протокол проверки](validation-report.json) отделяет валидацию документации от будущей приёмки системы. Проверка source snapshot по абсолютному исходному пути применима на этой машине; при переносе репозитория обновить root явно, не hashes.
