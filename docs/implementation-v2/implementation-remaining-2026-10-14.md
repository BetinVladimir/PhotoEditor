# Остаток реализации перед глубоким тестированием

Дата среза: 2026-10-14. Цель остаётся V20–V32 целиком. Этот документ задаёт порядок закрытия кода, а не принимает пакеты: последние миграции и написанные unit-сценарии не выполнялись в рамках текущего implementation-first этапа. Нормативные критерии — `07-execution-acceptance.md`; исходные пакеты — `work-packages.json`.

## Правила учёта

- Считать завершённым кодирование операции только при трассе `клиент/публичный API → авторизованный request → frozen plan/Params → долговечный admission и dispatch → worker → канонический result → transactional adoption → доступный review/Apply/download`, включая отказ, отмену, повтор и GC.
- Код, упомянутый в аудите 2026-10-07 как отсутствующий, повторно искать в текущем дереве. В частности, V30 delivery public create и mixed watermark scheduler constructor уже существуют; это не доказательство полного lifecycle.
- Для каждой новой миграции сохранить forward-only порядок, владельца/ACL/RLS и свежий/upgrade сценарии. До перехода к тестовой фазе сценарии написать, но не объявлять PASS и не применять миграции.
- Для каждой операции, зависящей от весов, камеры, ключей или измерений, отсутствие установленной квалификации даёт явное `unavailable`. Не заменять её synthetic fixture или конфигурационным SHA.
- Отмечать отдельно `coding_closed`, `configured`, `qualified`, `accepted`. Первое не подразумевает остальные три.

## Очередь реализации

### P0: основа первого MVP и всей системы

1. **Реестр трасс V20–V32.** Для каждой операции из `contracts/operations.json` и каждого HTTP route составить current-state строку: request/client, service, SQL, worker, result, adoption, UI, unit-сценарии, объектные роли, cleanup. Обновить старый `completion-audit-2026-10-07.json` только после проверки фактических связей. Блокер считается кодовым, если компонента нет или он не установлен; отсутствие запуска теста учитывать отдельно.
2. **V20/V21 инварианты.** Сверить capability/qualification и model locks для всех реально включённых операций; довести RLS, ACL, идемпотентность, quota, cancellation, output registry, GC и purge до новых V28–V31 артефактов. Проверить, что `photo_fn_owner` сохраняет DELETE только на разрешённом tenant-scoped allowlist для `finish_tenant_deletion`.
3. **Базовый маршрут V22/V25/V26/V30.** Замкнуть `import → session → editor/Apply → review → export → delivery/download` на поддерживаемых входах. Клиент должен показывать статус/ошибку/повтор и не обещать неподдерживаемую камеру/модель. Сохранить старые Apply v4, ICC, alpha, RAW и protected-pixel инварианты.
4. **Обычная V30 delivery.** Проверить установленную цепочку create, selected source, child admission, encoded output, assembly, CAS publish, read/download/revoke и recovery после сбоя. Разделить обычную, metadata и watermark ветки; общая сборка не должна публиковать неполный required bundle. Дописать unit-сценарии каждой ветки и ошибочного/повторного перехода.
5. **Минимальный V32 runtime.** Установить и связать startup-проверки, scheduler capacity, maintenance/reconciliation, безопасный restore и readiness для включённых функций. Не объявлять готовность по одному сформированному probe report.

### P1: обязательное для полного V20–V32, после P0 по зависимостям

6. **V23/V24.** Довести learning `fit → evaluate → safety review → promote/rollback` и consent epoch до runtime; camera/watch-folder capture — до restart/dedup, rotation и public QA. Эти возможности можно не открывать в первом MVP, но их код обязателен для полного плана.
7. **V27 semantic.** Подключить реальный downstream FAN/BiSeNet/skin result, долговечную родительскую оркестрацию, per-target review и Apply. Успешный receipt подготовительной задачи не равен успеху пользовательского workflow.
8. **V28/V29 операции.** Для open-eyes, glare, hair, clothing, reflection, relight, panorama, focus stack, negative и perspective последовательно проверить и дописать точную трассу из правила выше. Сопоставить каждый worker handler с регистрацией, admission, result adoption, GC и UI. Завершить real model/donor authority, а не только локальный compiler или синтетическое принятие.
9. **V30 interchange.** Проверить установленный scheduler export adoption по всей физической closure: executable вызывает `prepareSchedulerInterchangeExport`, строит `BuildSchedulerExportAdoptionFromDeployment`, claim heartbeat ведёт `SchedulerExportAdoptionProcessor`, а `AdoptScheduler` атомарно публикует evidence. Foreground `ExportResultAdoptionService.AdoptCurrentExportResult` не служит единственным production caller. Остаются квалификация каждого разрешённого формата и policy, replay, run finalization и проверка реальных ролей/объектов. Для импорта закрыть parse → canonical ingest → review → final continuation/adoption; `FrozenInterchangeImportEvidence` уже включён в Params, closure, transport и SQL admission, поэтому нужно доказать его физическую сквозную проверку и replay. Отдельно довести archive multipart, person-origin и metadata/watermark ветки до полного lifecycle.
10. **V31 provenance.** Установить реальный signer SDK/key/trust/TSA authority и процесс dispatch/adoption/public SignExport. Проверять итоговый подписанный файл после encode/watermark, rotation/revocation и privacy redaction; локальные CBOR/JUMBF и fake SDK тесты не равны production подписи.

V31 private signer bootstrap: действующий mTLS signer listener получил отдельный `/internal/v1/operator-native-check`. Он принимает только canonical policy/certificate SHA, проверяет exact policy в установленном process catalogue и вызывает live `InstalledSigningOperator.check_installation` (native SDK/key authority) до ответа; клиент ограничен прежним TLS chain и leaf-pin allowlist, request и время ограничены. Unit-сценарии чужого клиента, policy/certificate подмены, некорректного запроса и native revoke написаны, не запускались. Go process consumer для off-TSA политик теперь установлен; TSA callback и физически provisioned SDK/key всё ещё нужны, поэтому endpoint сам по себе не закрывает V31.

Go `HTTPSigningNativeCheck` теперь использует уже установленную pinned TLS1.3/mTLS конфигурацию challenge-клиента для `/internal/v1/operator-native-check`. Он валидирует policy, сравнивает SHA фактической certificate chain, ограничивает ответ и требует exact canonical echo обоих SHA от того же server leaf. Метод `Check` имеет сигнатуру `SigningTrustCheck`; отдельная X.509/CRL/TSA authority остаётся обязательной. Unit-сценарии mTLS, wrong pin/chain, отказа signer, подменённого ответа и cancellation написаны, не запускались. Process bootstrap для off-TSA политик добавлен ниже; live TSA ещё не подключён.

V31 native mTLS client получил явный lifecycle: `Close` идемпотентно отзывает дальнейшие `Check`, отменяет уже выполняемые HTTP запросы и закрывает idle transport. Unit-сценарии закрытого клиента и остановки во время запроса написаны, не запускались. TSA нельзя подменять ping endpoint: требуется независимая проверка RFC 3161 либо другой квалифицированный timestamp authority, поэтому required-TSA policy пока остаётся недоступной без такого процесса.

V31 process bootstrap: исполняемые роли API/scheduler теперь читают pinned `PHOTO_SIGNING_DEPLOYMENT_FILE`/`PHOTO_SIGNING_DEPLOYMENT_SHA` и process-owned `PHOTO_SIGNING_API_CERT_FILE`/`PHOTO_SIGNING_API_KEY_FILE`, строят `SigningTenants` из точных tenant/worker/qualification записей и подключают `HTTPSigningNativeCheck` к существующей X.509/CRL authority. `api_identity_id` равен lowercase SHA256 DER leaf-сертификата API mTLS identity; ключ должен быть в обычном файле без symlink/hardlink и без group/world доступа. При завершении процесса native clients закрываются. Required-TSA policy останавливает bootstrap до установки независимого timestamp verifier; наличие Python signer/SDK, сертификатов, CRL и positive physical signing ещё должно подтверждаться конфигурацией и тестовой фазой. Unit-сценарии обязательных деклараций и прав файла написаны, не запускались.

Bootstrap дополнительно проверяет срок каждого сертификата mTLS цепочки, требует у leaf явные ClientAuth EKU и DigitalSignature KeyUsage, запрещает CA leaf и требует корректный CA/CertSign у intermediate. Заведомо неработающее identity теперь не создаёт runtime даже до первого сетевого запроса. Unit-сценарии valid/expired/future/server-only/несоответствующих usage/CA leaf написаны, не запускались.

V31 установка tenant signing service теперь до объявления runtime запускает live preflight каждой активной policy через полный `InstalledChallengeSigningAuthority.CheckSigningOperator`: possession challenge, SQL registration, native SDK/key, X.509, требуемые CRL/TSA проходят с bounded timeout. Будущие и истёкшие версии не блокируют запуск только из-за своего окна; live gate при каждом `Resolve` сохраняется. Ошибка signer закрывает установку и освобождает transport. Unit-сценарии активной/будущей/истёкшей policy, native отказа, cancellation и некорректного input написаны, не запускались. Это startup-проверка, не физическая квалификация подписанного файла.

Для независимого TSA слоя добавлен `NewRFC3161Request`: DER TimeStampReq v1 с SHA-256 messageImprint точных входных bytes, fresh положительным 160-битным nonce и `certReq=true`. Вход, entropy и размер запроса ограничены; unit-сценарии ASN.1 полей, imprint/nonce и отказов написаны, не запускались. Это только запрос: transport, проверка TimeStampResp/TSTInfo, CMS-подписи, ESSCertID, TSA EKU/цепочки/отзыва и привязки ответа к nonce/imprint ещё требуются. Required-TSA policy остаётся fail-closed.

Внутренний `parseRFC3161GrantedResponse` теперь ограничивает DER ответ 2 MiB, принимает только status `granted(0)` и обязательный `ContentInfo` типа CMS SignedData, отвергает trailing bytes, отказ/waiting/modified grant и чужой тип. Возвращаемый token специально остаётся недоверенным и не подключён к `SigningTrustCheck`: следующий слой обязан проверить eContent TSTInfo, CMS signature/ESSCertID, nonce/imprint, TSA chain/EKU/revocation. Отрицательные unit-сценарии написаны, не запускались.

Внутренний `parseRFC3161TSTInfo` теперь разбирает DER eContent и требует version 1, SHA-256 imprint точного запроса, тот же положительный 160-битный nonce, корректный serial и GeneralizedTime. Он ограничивает поля и отвергает неподдерживаемые TSA name/extensions; возвращаемый policy/serial/time остаётся недоверенным до CMS и certificate проверки. Unit-сценарии точной привязки, чужого imprint/nonce и отсутствующего nonce написаны, не запускались. Required-TSA по-прежнему не подключён к этому parser.

Внутренний `parseRFC3161CMSParts` теперь извлекает из CMS SignedData v3 единственный DER TSTInfo eContent, явную ограниченную цепочку certificate choices и ровно один SignerInfo. Он принимает только digestAlgorithms SHA-256, тип `id-ct-TSTInfo`, вложенный content и отсутствие лишних trailing/CRL/неподдерживаемых choice. Возвращаемые части остаются недоверенными; проверка signer identifier, signedAttrs/messageDigest, ESSCertID, самой подписи, TSA EKU/цепочки/отзыва и HTTPS transport ещё нужна. Unit-сценарии одного signer, чужого типа, версий и кратности написаны, не запускались.

`verifyRFC3161CMSSignature` добавляет криптографическую проверку поддержанного CMS-профиля ECDSA-SHA256/RSA-SHA256: SignerInfo issuer/serial однозначно выбирает встроенный сертификат, signedAttrs содержит ровно один contentType TSTInfo, SHA-256 messageDigest exact eContent и SigningCertificateV2/ESSCertIDv2 SHA-256 выбранного сертификата; DER SET signedAttrs проходит проверку подписи сертификатным public key. Чужие/дублированные атрибуты, иные алгоритмы и отсутствие ESS отвергаются. Сгенерированные ECDSA unit-сценарии valid/tamper/missing ESS/wrong certificate написаны, не запускались. Успех этого метода доказывает лишь подпись конкретного ключа, не доверие к TSA: root, EKU, отзыв, окно времени, policy, HTTPS и связывание со всем SigningTrustCheck ещё открыты.

`RFC3161TSATrust.Verify` теперь связывает response → CMS подпись → TSTInfo nonce/imprint с pinned TSA policy/root, проверяет живое окно времени, полный X.509 путь без system roots и критичный единственный EKU timeStamping у не-CA leaf. Процессный revocation callback обязателен и вызывается с exact DER path, после внешнего IO время и путь проверяются повторно. Unit-сценарии с сгенерированным CA/TSA ключом покрывают valid, noncritical EKU, чужой nonce, stale genTime и отказ revocation; не запускались. До production required-TSA остаются конкретный qualified CRL/OCSP source с durable anti-rollback, HTTPS TSA transport с pinning, процессное provision и физическая проверка; callback без такого источника нельзя считать установленным trust.

`NewDurableRFC3161TSARevocationCheck` теперь связывает verified TSA path с уже существующим `NewDurableSigningCRLCheck`: каждый сертификат пути повторно разбирается, root обязан совпасть с pinned anchor, последовательные issuer/signature проверяются, полный PEM path идёт в signed full-CRL validator с обязательным durable issuer checkpoint. Входные URL не берутся из ответа; CRL source остаётся process-owned. Unit-сценарии с настоящим CA CRL покрывают clean, revoked, unanchored и missing checkpoint; не запускались. Для рабочего подключения остаются pinned HTTPS CRL endpoints и SQL installation check, TSA transport/deployment и физический прогон.

`HTTPSigningTSAClient` теперь отправляет RFC3161 DER query по process-pinned HTTPS endpoint через TLS1.3 с отдельным CA pool и точным server leaf SHA. Proxy, redirect и compression выключены; время, headers, соединения и response ограничены. Только ответ `application/timestamp-reply` с кодом 200 передаётся в `RFC3161TSATrust.Verify`, так что TLS не заменяет token signature/chain/CRL. `Close` отменяет текущий exchange и запрещает новые. Unit-сценарии valid pinned TLS, wrong pin/status/redirect/MIME/encoding/oversize/cancel/close написаны, не запускались. Следующий кодовый барьер — pinned TSA/CRL deployment и интеграция в `SigningTrustCheck`; required-TSA пока не включён.

Pinned `signing-api-deployment/v1` расширен необязательным `timestamp_services` на tenant. Для каждой required policy теперь обязателен ровно один service с совпадающим ID; лишний service запрещён. Запись фиксирует TSA URL/server SHA/HTTP roots, отдельные TSA trust roots и policy OID, timeout/skew, CRL roots/max-age и полный allowlist CRL issuer/endpoints; все URL, PEM, SHA, OID, границы и уникальность проверяются до runtime. Старый off-TSA документ без поля сохраняет прежние canonical bytes. Unit-сценарии required с service, missing/unused service и ошибочных OID написаны, не запускались. Следующий шаг — process-owned сборка SQL checkpoint, HTTPS CRL и TSA клиентов из этих pinned значений.

`InstallSigningTimestampServices` и обычный API/scheduler bootstrap теперь создают отдельный `photo_api` SQL pool только при наличии required-TSA сервисов, подтверждают через `SQLSigningCRLCheckpoint.CheckSigningCRLInstallation` роль/ACL/issuer allowlist, собирают pinned HTTPS CRL source, durable signed-CRL verifier, TSA trust и HTTPS TSA client. Полученный `SigningTrustCheck` запускает fresh RFC3161 запрос с доменно отделённым policy SHA/chain SHA и требует полный verified ответ; `SigningTimestampRouter` дополнительно привязывает его к exact установленной policy. Ошибка любого tenant/service закрывает уже созданные transports и SQL pool. Unit-сценарии отсутствующей SQL authority/cancellation написаны, не запускались; real-role SQL/HTTP/CRL и физический qualified TSA corpus остаются для глубокой тестовой фазы. Worker C2PA Reader по-прежнему обязан проверить timestamp именно подписанного export, поскольку этот callback проверяет live доступность независимой TSA для policy/chain.

CMS `SigningCertificateV2/ESSCertIDv2` verifier теперь принимает стандартный optional `issuerSerial`, но только с одним directoryName и serial, точно совпадающими с выбранным signer certificate; чужое имя/serial и дополнительные значения остаются отказом. Это закрывает совместимость с TSA, которые включают рекомендованный RFC 5035 issuerSerial, не ослабляя signer binding. Unit-сценарии valid и чужого serial написаны, не запускались.
11. **V32 полный lifecycle.** Завершить role matrix, restore, multi-bucket physical purge reconciliation, mixed workload/admission/fairness и acceptance-пробы для V20–V31. Production cutover требует независимо прочитанного физического evidence.

P0.1: `audit/trace_inventory.py` теперь воспроизводимо перечисляет все 30 нормативных операций и 79 endpoint-контрактов в `audit/trace-inventory.json`, собирает текущие кандидаты API, service, SQL, worker, client и unit-файлов без переноса исторических PASS. Для всех endpoint найдена статическая route-декларация (две через динамическую таблицу), но это ещё не доказательство mounted runtime или сквозной трассы. У `identity.compare` нет точного литерала операции в production Go service при существующем worker adapter; миграция `00223` сознательно держит dispatch disabled до квалификации модели и output validation. Само отсутствие Go-литерала не доказывает ошибку, а включать операцию без qualified weights нельзя. Реестр не ставит `coding_closed` автоматически; ручная квалификация каждого слоя, GC/purge и физические сценарии остаются обязательными.

V23 identity pixel guard теперь учитывает alpha в том же точном outside-mask/protection сравнении, что RGB. Он нормализует допустимый legacy `uint16` alpha к float32, как changed-mask worker, отвергает неверную форму/тип/NaN и принимает отсутствие alpha как непрозрачность. Standalone `identity.compare` и learning Evaluate передают реальные before/after alpha; alpha-only правка вне эффективной маски либо внутри protection больше не может получить `pass`. Unit-сценарии для обоих путей написаны, не запускались. Это не включает отключённый dispatch и не заменяет модельную квалификацию V23.

V23 `identity.compare` получил серверный точный `IdentityCompareParams`: оба version binding, effective/protected MaskRef, model lock, calibration и consent refs; все refs независимы, версии и source различны. Компилятор выдаёт canonical bytes и SHA-256 для неизменяемого Params, декодер отвергает дополнительные/отсутствующие/null поля, алиасы и неканоническую сериализацию. Unit-сценарии написаны, не запускались. Это граница формата; ещё нужны scoped source/mask/consent authority, квалифицированный профиль, публикация/SQL admission, result adoption и включение dispatch только после реальных model checks.

Для `identity.compare` добавлен `CompileIdentityCompareClosure`: он принимает только точные canonical bytes шести independently authorized документов, сверяет SHA Params и каждого документа, общий canvas/color/transform, float32 WorkingImage и protected disposition двух MaskRef. Child NPY refs и geometry извлекаются только из документов; immutable transport объявляет оба изображения, их пиксели/alpha/warp, обе маски и пиксели, Calibration, ConsentSnapshot и Params. Подменённые bytes, mask role, foreign Params и конфликтующие artifact identities отказывают до регистрации. Unit-сценарии написаны, не запускались. Этот closure не выдаёт source/consent/model authority и не включает отключённый dispatch.

`CompileIdentityCompareTask` теперь строит детерминированные task/node ID, GPU DraftTask и опубликованный input transport из этого closure; `CompileIdentityCompareProfileFromInputs` требует точные independently authorized размеры каждого входа, доверенные дополнительные RAM/VRAM/scratch peaks оператора и границы ресурса/вывода. Профиль учитывает два изображения, полный pixel guard и changed-mask NPY, но остаётся capacity bound, а не доказательством качества/доступности модели. Авторские unit-сценарии границ, инвентаря и DraftTask не запускались. Следующий кодовый барьер — source/consent/qualification authority и SQL admission/adoption; registry всё ещё выключен.

V23 identity input closure дополнительно вызывает общий `VerifySemanticCalibration` с ожидаемым dataset SHA из доверенного qualification pin и exact model lock, а также `ValidateSessionConsentSnapshot` для полной структурной проверки grant/confirmed-face связей. Самостоятельно перехешированные `qualified=false` Calibration и некорректные consent grants теперь отказывают до публикации; unit-сценарии написаны, не запускались. Это не заменяет живую SQL-проверку эпох согласий и trusted qualification source, которые остаются обязательными перед admission и result adoption.

V23 worker-регистрация `identity.compare` теперь требует для SFD, FAN2D и identity512 одновременно `approved_for_install` и `passed` qualification в точном backend. Одних ID в model lock недостаточно для объявления operation capability; `ModelPool.acquire` сохраняет независимую проверку непосредственно перед inference. Unit-сценарии отсутствующей/неодобренной/untested модели и неподдерживаемого backend написаны, не запускались. SQL registry остаётся выключенным до полной admission/qualification цепочки.

V23 CPU verification path: ONNX identity512 не имеет нативного MPS provider, поэтому worker явно отвергает MPS capability даже при ошибочно выставленном `passed` в model lock. Компилятор task/profile теперь допускает CPU с VRAM=0 и CUDA с положительным trusted VRAM peak; MPS остаётся недоступным. Forward-only `02149_v23_identity_cpu_backend.sql` добавляет CPU в allowlist выключенной `identity.compare` registry без включения dispatch. Так CPU-проверку можно позднее проводить на текущем Metal-хосте, а MPS объявлять только после отдельного backend adapter и физической квалификации. Unit-сценарии CPU/CUDA/ложного MPS написаны, миграция и тесты не запускались.

V23 holdout triplet теперь отвергает несовпадающие frozen background до обращения к workspace/буферам; равенство background является необходимым условием общего alpha для трёх сравнительных ветвей. Существующий unit-сценарий раннего отказа покрывает границу, а соседние platform fixtures приведены к полному текущему `HoldoutWorkspace` контракту (alpha, protection, effective mask, region masks). Сценарии пока не запускались.

P0/V30 scheduler admission: import, export и delivery loop теперь при ошибке `ProcessOne` немедленно сбрасывают health и в независимом ограниченном контексте отзывают собственную SQL runtime lease до обычного backoff. Maintainer после `announce` повторно проверяет здоровье loop и отзывает lease при отказе либо потере состояния во время SQL-вызова. Это сокращает окно принятия новых задач после подтверждённой ошибки; при недоступной БД остаётся конечная 30-секундная lease expiry, которую нельзя заменить локальным флагом. Unit-сценарии порядка отзыва, ограничения времени, успеха и shutdown написаны, не запускались; реальная гонка нескольких scheduler instances остаётся для глубокой тестовой фазы.

P1/V30 import closure: `ResolveImportInputInventory`, `FreezeImportInputs` и transport registration теперь сравнивают `Params.evidence` с отдельно опубликованным `FrozenInterchangeImportEvidence` ref до обхода объектов и до SQL регистрации. Старый storage helper без evidence остаётся допустимым только как промежуточный документ; смешанный Params/owned evidence больше не может стать input inventory. Unit-сценарий подмены и несоответствия ref написан, не запускался.

Публичный executable `ImportExecutionPreparation.Prepare` теперь также отклоняет legacy Params без evidence и несовпадающий owned evidence до публикации первого документа. Production SQL factory уже требовал evidence; дополнительный preflight исключает обход через вручную собранный generic preparation. Положительный unit-сценарий переведён на четырёхкорневой executable input, отрицательные сценарии для старого Params и чужого evidence написаны, не запускались.

`FreezeImportInputs` теперь владеет копиями Plan/Params/evidence bytes и структурой evidence, а не сохраняет ссылки на буферы вызывающего кода. После расчёта input digest последующая мутация исходных документов не меняет содержимое inventory, передаваемого в publication и registration. Unit-сценарий мутации всех трёх документов и evidence ref написан, не запускался.

### Уточнение текущего кода P0 (2026-10-14)

Для обычной V30 delivery написан bucket-bound admission (`02121_v30_delivery_runtime_admission.sql`). Только запущенный и здоровый delivery-loop scheduler публикует 30-секундный lease для своего object bucket; SQL создания нового draft проверяет lease внутри той же транзакции. Повтор существующего draft по прежнему допускается до проверки lease. Старый шестипараметрический SQL-вход отозван у `photo_api`, новый семипараметрический получает bucket из установленного API storage. Scheduler проверяет ABI при запуске, отзывает lease при ошибке и shutdown, readiness включает lease; отсутствие runtime на нужном bucket возвращает `DELIVERY_UNAVAILABLE` 503. Написаны unit-проверки привязки bucket и отказа некорректного bucket, но миграция и тесты по принятому implementation-first порядку не запускались. Этот admission не подтверждает физическую публикацию, подпись и download; пункт P0.4 остаётся открытым до полной трассы и общей фазы тестирования.

Миграция `02122_v30_delivery_activation_runtime.sql` закрывает гонку между draft и финальным `queued`: после проверки готового `task_params` она сверяет bucket физического artifact/document с bucket API и повторно требует live lease перед атомарным seal. Успешный сохранённый ticket воспроизводится до этого gate; старый activation ABI отозван у `photo_api`. Потеря runtime классифицируется как `DELIVERY_UNAVAILABLE` 503. Unit-сценарии для точной привязки bucket и ошибки lease написаны, но не запускались.

`runtime_admission_sql_integration_test.go` добавляет проверку реальных ACL новых/отозванных функций и живой lease-цикл под ролями `photo_scheduler`/`photo_api`: совпадающий bucket допускается, чужой и отозванный — нет. Сценарий пишет только внутри откатываемой транзакции на изолированной БД. Он также пока не запускался.

Delivery scheduler теперь выполняет обычный child/assembly проход даже при ошибке независимой metadata-ветки. Обе ошибки возвращаются вместе, поэтому health/lease остаются в отказе, но ранее принятые обычные задачи не голодают из-за постоянной metadata-ошибки. Unit-сценарии для error/fairness и совместных отказов написаны, не запускались.

Формулировки ниже о том, что фоновая V30 export adoption **не подключена к executable**, описывают промежуточные стадии, а не текущее дерево. В `backend/cmd/photo/main.go` scheduler вызывает `prepareSchedulerInterchangeExport`, затем `RunSchedulerWithInterchangeExport`; `backend/cmd/photo/interchange_export_scheduler.go` загружает pinned deployment, проверяет native authority и person-origin trust и строит `BuildSchedulerExportAdoptionFromDeployment`. SQL source/mask origin (`02059`) и `SQLSchedulerExportInputCatalog.LookupExportSeriesMaskOrigin` также уже написаны. Это переводит задачу из «написать bootstrap» в «статически сверить полную closure для каждого разрешённого формата, затем в общей фазе проверить реальные роли, объекты, миграции, lease/replay и terminal adoption». Наличие wiring не доказывает работающий lifecycle; до этих проверок V30 не считать принятым.

Повторная сверка V30 import production path обнаружила, что `main.go:run()` вызывает `runWithAPIDependencies(apiProcessDependencies{})`, а обычный scheduler ранее не создавал требуемые `ImportEntryBase` и `ImportPersonAcceptance`. Без операторской конфигурации import factory остаётся отсутствующей. Уже написанные `NativeImportSchedulerContinuation`, рецепты и `FrozenInterchangeImportEvidence` сами по себе не доказывают полный `parse → ingest → review → adoption` lifecycle. Подмена acceptance заглушкой недопустима.

Следующее изменение закрывает часть этого запуска: если обычный scheduler получил pinned `PHOTO_V30_IMPORT_OPERATOR_CONFIG` без внешней injection, `schedulerImportFactories` создаёт process-owned базу с ручной mask policy и `SQLImportPersonAcceptanceBinder`. Binder не принимает маску в несвязанном состоянии; после exact claim он строит `SQLImportConfirmedMaskAuthority` с tenant/run/workflow и pinned parsed bytes, которая повторно читает текущее пользовательское подтверждение и person-origin gate. Операторский файл по-прежнему обязателен для native/style/model policies и публичного trust. Частично переданная внешняя injection остаётся ошибкой. Написаны unit-сценарии для scope, отсутствующей БД, чужого parsed SHA и default bootstrap; тесты не запускались. Полный импортный lifecycle, установка на реальном deployment и физическая qualification ещё не доказаны.

Миграция `02110_v30_import_runtime_admission.sql` добавляет глобальный 30-секундный lease только для полностью установленного import processor. Scheduler обновляет его отдельным 10-секундным циклом во время долгого object IO, отзывает через `UPDATE` при потере готовности и при штатном shutdown; истечение lease покрывает аварийный выход. Старые истёкшие строки переиспользуются при новом запуске без явного `DELETE` grant. `begin_v30_interchange_parse_run` требует живой lease лишь перед созданием нового draft и оставляет повтор существующего draft доступным. Без настроенного processor новый импорт получает `INTERCHANGE_UNAVAILABLE` (503), вместо бесконечно ожидающего run. Startup проверяет SQL role/function ABI; написаны unit и real-role сценарии, они не выполнялись. Lease подтверждает живой кодовый путь, но не заменяет физический import/export acceptance или модельную qualification.

### Решение для фонового V30 export adoption

Текущий `ExportResultAdoptionService` использует `tenant.WithTenant(..., domain.Editor)` и `RecoverExportPending`, которые требуют текущую пользовательскую сессию. Она может истечь до завершения export worker. Поэтому этот сервис годится для авторизованного foreground восстановления, но не должен вызываться scheduler с выдуманным либо произвольно выбранным `session_id`. `photo_scheduler` не имеет права на `v30_export_adoption_root` и `adopt_v30_interchange_export`; простое расширение их EXECUTE также не является решением.

Кодовый путь реализации:

1. Добавить forward-only SQL claim для `photo_scheduler`, выбирающий только canonical succeeded `v2.interchange.export` без evidence/terminal completion; вернуть tenant/run/task/result/attempt/fence, исходные actor/key/request SHA из сохранённого pending ledger и точную frozen request. Claim имеет lease/token/cooldown, tenant-first порядок блокировок и не возвращает object URL или произвольный root из запроса.
2. Добавить scheduler-scoped read functions для frozen документов и exact output/result inventory. Они повторно проверяют active tenant/project, неизменный pending ledger, source snapshot, task result, output role/producer/attempt/fence и объектные версии. Не использовать user-session-gated `v25_lens_snapshot_ready` без специально определённой фоновой authority.
3. Установить результатный native validator из того же pinned deployment, что export creation, в scheduler bootstrap. Прочитать ZIP/sidecar/closure через точные versioned objects вне SQL-транзакции, затем recheck claim/fence и object identity.
4. В одной транзакции сохранить evidence, links/inbox/events и финализировать run либо передать его existing finalizer по явно зафиксированному барьеру. Повтор того же claim возвращает прежний результат; заменённый canonical result, отзыв доступа, отмена, истёкшая lease или mismatch SHA отказывают без частичной публикации.
5. Подключить processor к scheduler readiness/shutdown и написать unit-сценарии для каждого перехода, stale lease, logout до worker completion, unknown commit, replay и конфликтующей версии объекта. На тестовой фазе проверить real-role ACL и физические PostgreSQL/MinIO сценарии.

Начат кодовый путь: миграция `02034_v30_export_adoption_claim.sql` и `SQLExportAdoptionClaimStore` дают только приватный lease/discovery с исходным request и deterministic identity; они не читают объекты и не принимают результат. Пока нет scheduler-scoped reader, adoption transaction, processor и runtime installation, V30 export adoption остаётся незавершённым. Миграция и unit-сценарии написаны, но не выполнялись.

Миграция `02035_v30_export_adoption_claim_current.sql` добавляет read-only lease/result fence для повторной проверки перед следующим шагом; Go store и real-role negative fixture написаны. Этот predicate не заменяет snapshot/source, output и object-version authority. Ни 02034, ни 02035 не применялись; fixture не запускался.

Миграция `02036_v30_export_adoption_source_root.sql` добавляет отдельную проверку текущих actor/project прав и V25-эквивалентного snapshot/source inventory без зависимости от истёкшей HTTP-сессии, а также выдачу только точного первого canonical output с versioned object pin. Go reader повторяет claim до и после SQL lookup. Это пока root-only стадия: остальные outputs, transitive closure и финальный commit не установлены; 02036 и сценарии не запускались.

Его результат — только подготовленное структурное evidence, не adopted ticket. ZIP/portable closure, commit и runtime loop по-прежнему отсутствуют; сценарии не запускались.

Это источник для будущей фабрики, но ещё не сама фабрика: в ней нужно переиспользовать проверку подписи, маски и текущего producer authority без пользовательской сессии, затем снова сверить object pins перед adoption.

## Переход к фазе тестирования

### V23 series learning: текущая граница кода

`learning.fit` теперь объявляет frozen series evidence, исходный stage image, `SeriesParams` и `SeriesCorrections` по точным ссылкам из сохранённого recovery. Go требует совпадение tenant/event/asset/source с manifest и детерминированный ID документа; worker дополнительно сверяет ID с training run и проверяет scene, число и уникальность элементов, reference item и наличие выбранного item в коррекциях. Написаны Go/Python unit-сценарии; согласно принятому порядку они ещё не выполнялись.

Первоначальная миграция `02093_v23_series_freeze_gate.sql` запрещала admission manifest с `series_evidence`. Последующие `02102–02103` заменили абсолютный запрет условным gate: admission остаётся закрытым по умолчанию и открывается только при выбранной доверенной qualification, полной проверке frozen inventory и совпадении lock-пинов producer. До фактического включения нужны физическая проверка источников `SeriesStats`, одинаковый replay в baseline/candidate/approved ветвях Evaluate и квалификация метрик. Наличие прямых входов Fit не доказывает эти требования.

Миграция `02096_v23_series_stats_locator.sql` даёт event-scoped локатор каждой статистики из того же запечатанного Apply balance: она сверяет вход balance, результат `series.measure`, исходный stage от `image.color`, snapshot item и pinned object version. `PrepareSeriesHoldoutForCandidate` повторяет lookup до/после физического чтения каждого `SeriesStats` и проверяет ID item/image из тела против SQL. Новый валидатор всего агрегата требует SHA/JCS каждого элемента, уникальные item, соответствие выбранному stage image и точное пересечение общих регионов. Эти изменения и unit-сценарии написаны, не запускались.

Миграция `02097_v23_series_stats_recovery.sql` добавляет `series_stats_jcs` к pending training receipt. Она требует полный упорядоченный список Stats из canonical `series.balance` Params для каждого series event и проверяет каждый элемент через `v23_series_stat_artifact`; прежний validator обрабатывает остальные поля после временного снятия нового поля. Go recovery проверяет canonical bytes, уникальность ссылок и соответствие набора событий manifest. Fit closure объявляет все сохранённые Stats как `SeriesStats`, а worker требует эти typed entries в точном порядке Params. Unit-сценарии написаны, не запускались. Freeze gate остаётся: Evaluate и quality admission ещё не завершены.

Worker `series_replay.py` теперь проверяет evidence/run/item, stage metadata, Params, всю статистику и точное пересечение регионов перед выбором `ItemCorrection`. `render_holdout_triplet` передаёт один замороженный correction через production `apply_series` в baseline/candidate/approved и повторно проверяет его неизменность. `trainingSeriesStyleEnabled` принимает только точные параметры, которые реально создаёт Apply (`median`, `0.35`, `0.95–1.05`), чтобы сравнение не использовало другой эффект. Написаны unit-сценарии; не запускались.

Миграции `02098_v23_evaluate_series_authority.sql` и `02099_v23_evaluate_series_nested.sql` дают fenced Evaluate-источник для готового evidence и каждого вложенного JSON-документа. Они требуют живой expansion lease, завершённый Fit с точным typed input, текущий consent/Apply producer, готовый backend document и pinned object versions; отдельная owner-only копия Apply locator убирает только интерактивную editor session, сохраняя source/tenant/project/actor проверки. Go reader повторяет authority до/после каждого object IO, сравнивает SQL-метаданные каждого Stats с физическим телом и включает все refs в Evaluate task closure. Go admission допускает лишь точные параметры series, производимые Apply. Unit-сценарии написаны, не запускались. Миграция `02093` по-прежнему запрещает запуск series manifest: её можно пересмотреть только после проверки этих миграций, полного Evaluate/quality acceptance и отсутствия других разрывов.

Миграция `02100_v23_evaluate_series_commit_gate.sql` повторяет проверку каждого holdout series evidence в атомарной транзакции закрытия Evaluate. Она сопоставляет текущий источник и полный список Stats из запечатанного `series.balance` Params с typed входами Evaluate и повторно вызывает nested locator; новый guard включён после существующих defect/dust/detail/protection guard. При неполном наборе Evaluate не открывается. Код написан, миграция и интеграционные проверки ещё не выполнялись. Freeze gate для series manifest остаётся в силе.

`CompileEvaluateClosure` теперь учитывает самый большой набор `SeriesStats` среди последовательных holdout cases в RAM и scratch estimate: 32 KiB pinned body, дополнительный буфер доставки и decoded-object headroom на каждый элемент (до 2000). Границы и арифметика покрыты unit-сценарием. Это статический reserve, а не измеренный peak; freeze gate остаётся до общей проверки на Metal и квалификации качества.

Worker Evaluate повторно вычисляет весь `SeriesCorrections` тем же `series.balance` алгоритмом из запечатанных `SeriesParams` и полного набора `SeriesStats`; сравнение canonical bytes отвергает результат, который не следует из статистик, до выбора коррекции holdout item. Unit-сценарий включает подмену значения коррекции. Рефакторинг и сценарий написаны, но не запускались; для допуска manifest по-прежнему нужны qualification и полный тестовый цикл.

В `series.balance` и Evaluate replay callback активности теперь проверяется перед вычислением, периодически в medoid-поиске и во время fit каждого item. Это позволяет прервать долгую CPU-операцию при потере lease или отмене без изменения порядка суммирования и численной формулы. Unit-сценарии на прерывание и идентичность canonical bytes написаны, но не запускались.

Evaluate replay теперь дополнительно проверяет lease перед чтением каждого элемента полного `SeriesStats` inventory и после его чтения. Отмена во время обработки набора до 2000 статистик не откладывается до завершения всего IO. Unit-сценарий на потерю lease внутри inventory написан, но не запускался.

Контракт `SeriesStats` у worker теперь требует уникальные region ID, допустимый ASCII-формат ID, компоненты mean RGB в `[0,1]` и уникальные warnings. Backend-валидатор запечатанного агрегата использует тот же формат ID и отказывает повторным warnings; Go/Python unit-сценарии покрывают эти границы. Код написан, тесты не запускались.

Миграция `02101_v23_series_frozen_readiness.sql` добавляет закрытый для service roles предикат `v23_series_frozen_ready`: без пользовательской сессии он повторно проверяет текущий Apply/consent source, опубликованный immutable evidence document и полный ordered inventory `SeriesStats` из recovery против Params исходного `series.balance` и каждого текущего producer. Это подготовка к будущему снятию freeze gate, а не его снятие: `02093` всё ещё запрещает series manifest. Negative real-role fixture написан, но не выполнялся; положительный физический lifecycle и quality qualification обязательны до подключения предиката к admission.

Следующая forward-only миграция `02102_v23_series_qualified_freeze_gate.sql` подключает готовый предикат к frozen manifest admission. Series допускается только при DBA-selected `series.balance/1` CPU policy с обязательными checks `v23_series_holdout_replay` и `v23_series_holdout_quality`, действующим trusted passed report, текущем Apply/consent и полном frozen inventory; без такой qualification прежний отказ сохраняется. Для manifest без series оставлен прежний gate. Код и negative role/default-closed сценарий написаны, но миграция и проверки не запускались. Положительная qualification и реальная image-quality acceptance остаются условиями включения.

Статический аудит обнаружил, что исходный Apply `series.balance` создаётся общим CPU execution profile без model/runtime/device SHA. Поэтому миграция `02103_v23_series_producer_qualification_fence.sql` дополнительно требует точного совпадения всех трёх lock-пинов между доверенной policy, canonical producer и завершённым attempt; старые неприкреплённые Apply results остаются пригодными для Apply, но не станут training holdout. Для снятия этого отказа нужен trusted источник lock-пинов в Apply create/worker registration. Код миграции написан, не применялся и не тестировался; non-series path сохраняет прежнее поведение.

Миграция `02104_v23_series_apply_qualification.sql` даёт `photo_api` только текущие DBA-selected model/runtime/device пины при trusted passed report и живом CPU worker с тем же runtime lock. `run.Apply` записывает их в immutable config snapshot, а новый `applySeriesBalanceProfile` переносит их в task execution profile; отсутствие qualification оставляет прежний Apply без пинов и не открывает V23 learning. `model_lock_id=runtime_lock_sha` использует существующий worker authorization. Миграция `02105_v23_series_dispatch_runtime_fence.sql` дополнительно требует этот lock при resource admission и выборе targeted worker для `series.balance`; claim_task остаётся финальной проверкой. Unit и negative integration сценарии написаны, но не запускались. На тестовой фазе требуется положительная проверка реального worker/report/device binding.

Операторские `models` и `style_weights` теперь принимают только ID из закрытого model lock registry. Это статическая защита установки, а не доказательство физической доступности файлов весов; последнее остаётся отдельным acceptance gate.

Все операторские и обязательные V30 export operation model locks теперь должны совпасть с единым `Base.ModelSHA` — внутренним `lock_id` проверенного model lock. Так же worker `ModelPool` идентифицирует модель при выполнении. Несовпадение любого report/policy приводит к отказу при установке export; отдельные unit-сценарии для чужого lock написаны, но не запускались.

В export operator manifest добавлено необязательное поле `style_weights`: отображение `model.id → weight_id` для `StyleV2` и `ResolvedStyle`. Поле `models` сохраняет отдельное значение `model.id → SHA-256 lock` для операций, включая маски и override. Установщик теперь получает оба значения `lock_id` и inventory весов из одних аутентифицированных bytes model lock; операторский `style_weights` принимается только как точное подмножество этого inventory. При установленном manifest пустой `style_weights` разрешает только стили без моделей; нужные веса оператор обязан указать явно. `RenderComposition` передаёт обе политики раздельно. Написаны Go/Python unit-сценарии на одинаковый model ID с разными weight ID и lock SHA, а также отказ при несовпадении веса с model lock; они ещё не запускались. До принятия export необходимо проверить реальную конфигурацию весов и полную native-трассу на тестовом корпусе.
