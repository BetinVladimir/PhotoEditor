# Остаток реализации перед глубоким тестированием

Дата среза: 2026-10-14. Цель остаётся V20–V32 целиком. Этот документ задаёт порядок закрытия кода, а не принимает пакеты: последние миграции и написанные unit-сценарии не выполнялись в рамках текущего implementation-first этапа. Нормативные критерии — `07-execution-acceptance.md`; исходные пакеты — `work-packages.json`.

## Правила учёта

- Считать завершённым кодирование операции только при трассе `клиент/публичный API → авторизованный request → frozen plan/Params → долговечный admission и dispatch → worker → канонический result → transactional adoption → доступный review/Apply/download`, включая отказ, отмену, повтор и GC.
- Код, упомянутый в аудите 2026-10-07 как отсутствующий, повторно искать в текущем дереве. В частности, V30 delivery public create и mixed watermark scheduler constructor уже существуют; это не доказательство полного lifecycle.
- Для каждой новой миграции сохранить forward-only порядок, владельца/ACL/RLS и свежий/upgrade сценарии. До перехода к тестовой фазе сценарии написать, но не объявлять PASS и не применять миграции.
- Для каждой операции, зависящей от весов, камеры, ключей или измерений, отсутствие установленной квалификации даёт явное `unavailable`. Не заменять её synthetic fixture или конфигурационным SHA.
- Отмечать отдельно `coding_closed`, `configured`, `qualified`, `accepted`. Первое не подразумевает остальные три.

## Очередь реализации

### P0: основа первого MVP и всей системы

1. **Реестр трасс V20–V32.** Для каждой операции из `contracts/operations.json` и каждого HTTP route составить current-state строку: request/client, service, SQL, worker, result, adoption, UI, unit-сценарии, объектные роли, cleanup. Обновить старый `completion-audit-2026-10-07.json` только после проверки фактических связей. Блокер считается кодовым, если компонента нет или он не установлен; отсутствие запуска теста учитывать отдельно.
2. **V20/V21 инварианты.** Сверить capability/qualification и model locks для всех реально включённых операций; довести RLS, ACL, идемпотентность, quota, cancellation, output registry, GC и purge до новых V28–V31 артефактов. Проверить, что `photo_fn_owner` сохраняет DELETE только на разрешённом tenant-scoped allowlist для `finish_tenant_deletion`.
3. **Базовый маршрут V22/V25/V26/V30.** Замкнуть `import → session → editor/Apply → review → export → delivery/download` на поддерживаемых входах. Клиент должен показывать статус/ошибку/повтор и не обещать неподдерживаемую камеру/модель. Сохранить старые Apply v4, ICC, alpha, RAW и protected-pixel инварианты.
4. **Обычная V30 delivery.** Проверить установленную цепочку create, selected source, child admission, encoded output, assembly, CAS publish, read/download/revoke и recovery после сбоя. Разделить обычную, metadata и watermark ветки; общая сборка не должна публиковать неполный required bundle. Дописать unit-сценарии каждой ветки и ошибочного/повторного перехода.
5. **Минимальный V32 runtime.** Установить и связать startup-проверки, scheduler capacity, maintenance/reconciliation, безопасный restore и readiness для включённых функций. Не объявлять готовность по одному сформированному probe report.

### P1: обязательное для полного V20–V32, после P0 по зависимостям

6. **V23/V24.** Довести learning `fit → evaluate → safety review → promote/rollback` и consent epoch до runtime; camera/watch-folder capture — до restart/dedup, rotation и public QA. Эти возможности можно не открывать в первом MVP, но их код обязателен для полного плана.
7. **V27 semantic.** Подключить реальный downstream FAN/BiSeNet/skin result, долговечную родительскую оркестрацию, per-target review и Apply. Успешный receipt подготовительной задачи не равен успеху пользовательского workflow.
8. **V28/V29 операции.** Для open-eyes, glare, hair, clothing, reflection, relight, panorama, focus stack, negative и perspective последовательно проверить и дописать точную трассу из правила выше. Сопоставить каждый worker handler с регистрацией, admission, result adoption, GC и UI. Завершить real model/donor authority, а не только локальный compiler или синтетическое принятие.
9. **V30 interchange.** Подключить принятие canonical export result к долговечному рабочему пути по отдельному scheduler-контракту ниже; сохранить исходные actor/request identity, установить `BuildResultInstallerWithAuthority`, завершить run transition и replay. Существующий `ExportResultAdoptionService.AdoptCurrentExportResult` остаётся foreground-методом: сервис и builder есть, но production caller не найден. Для импорта закрыть parse → canonical ingest → review → final continuation/adoption; включить `FrozenInterchangeImportEvidence` в Params/closure согласно `15-execution-contracts.md`. Отдельно довести archive multipart, person-origin и metadata/watermark ветки до полного lifecycle.
10. **V31 provenance.** Установить реальный signer SDK/key/trust/TSA authority и процесс dispatch/adoption/public SignExport. Проверять итоговый подписанный файл после encode/watermark, rotation/revocation и privacy redaction; локальные CBOR/JUMBF и fake SDK тесты не равны production подписи.
11. **V32 полный lifecycle.** Завершить role matrix, restore, multi-bucket physical purge reconciliation, mixed workload/admission/fairness и acceptance-пробы для V20–V31. Production cutover требует независимо прочитанного физического evidence.

### Решение для фонового V30 export adoption

Текущий `ExportResultAdoptionService` использует `tenant.WithTenant(..., domain.Editor)` и `RecoverExportPending`, которые требуют текущую пользовательскую сессию. Она может истечь до завершения export worker. Поэтому этот сервис годится для авторизованного foreground восстановления, но не должен вызываться scheduler с выдуманным либо произвольно выбранным `session_id`. `photo_scheduler` не имеет права на `v30_export_adoption_root` и `adopt_v30_interchange_export`; простое расширение их EXECUTE также не является решением.

Кодовый путь реализации:

1. Добавить forward-only SQL claim для `photo_scheduler`, выбирающий только canonical succeeded `v2.interchange.export` без evidence/terminal completion; вернуть tenant/run/task/result/attempt/fence, исходные actor/key/request SHA из сохранённого pending ledger и точную frozen request. Claim имеет lease/token/cooldown, tenant-first порядок блокировок и не возвращает object URL или произвольный root из запроса.
2. Добавить scheduler-scoped read functions для frozen документов и exact output/result inventory. Они повторно проверяют active tenant/project, неизменный pending ledger, source snapshot, task result, output role/producer/attempt/fence и объектные версии. Не использовать user-session-gated `v25_lens_snapshot_ready` без специально определённой фоновой authority.
3. Установить результатный native validator из того же pinned deployment, что export creation, в scheduler bootstrap. Прочитать ZIP/sidecar/closure через точные versioned objects вне SQL-транзакции, затем recheck claim/fence и object identity.
4. В одной транзакции сохранить evidence, links/inbox/events и финализировать run либо передать его existing finalizer по явно зафиксированному барьеру. Повтор того же claim возвращает прежний результат; заменённый canonical result, отзыв доступа, отмена, истёкшая lease или mismatch SHA отказывают без частичной публикации.
5. Подключить processor к scheduler readiness/shutdown и написать unit-сценарии для каждого перехода, stale lease, logout до worker completion, unknown commit, replay и конфликтующей версии объекта. На тестовой фазе проверить real-role ACL и физические PostgreSQL/MinIO сценарии.

Начат кодовый путь: миграция `02034_v30_export_adoption_claim.sql` и `SQLExportAdoptionClaimStore` дают только приватный lease/discovery с исходным request и deterministic identity; они не читают объекты и не принимают результат. Пока нет scheduler-scoped reader, adoption transaction, processor и runtime installation, V30 export adoption остаётся незавершённым. Миграция и unit-сценарии написаны, но не выполнялись.

Миграция `02035_v30_export_adoption_claim_current.sql` добавляет read-only lease/result fence для повторной проверки перед следующим шагом; Go store и real-role negative fixture написаны. Этот predicate не заменяет snapshot/source, output и object-version authority. Ни 02034, ни 02035 не применялись; fixture не запускался.

Миграция `02036_v30_export_adoption_source_root.sql` добавляет отдельную проверку текущих actor/project прав и V25-эквивалентного snapshot/source inventory без зависимости от истёкшей HTTP-сессии, а также выдачу только точного первого canonical output с versioned object pin. Go reader повторяет claim до и после SQL lookup. Это пока root-only стадия: остальные outputs, transitive closure и финальный commit не установлены; 02036 и сценарии не запускались.

Миграция `02037_v30_export_adoption_outputs.sql` и `SQLSchedulerExportOutputCatalog` расширяют чтение на позиционные InterchangeResult/MappingReport/MappingShard/InterchangeArchive того же canonical result; каталог повторяет lease до и после lookup. Дальше нужно восстановить frozen документы из ledger, собрать `ExportResultReader`, установить input resolver для portable closure и сделать атомарный adoption. 02037 и сценарии не выполнялись.

Миграция `02038_v30_export_adoption_frozen.sql` и `SQLExportAdoptionClaimStore.FrozenExportAdoption` дают служебное чтение original frozen ledger и детерминированную реконструкцию через существующий `DecodeFrozenExportDocuments`. `exportIntentFromClaim` не создаёт фиктивную user session и не является самостоятельным разрешением. Следующие стадии — result reader, portable input closure, transactional adoption и scheduler installation. 02038 и сценарии не запускались.

`SchedulerExportResultReader` связывает frozen ledger, root и позиционный output catalog с существующим `ExportResultReader`, проверяя все JSON документы, SHA и версии до/после чтения. Его результат — только подготовленное структурное evidence, не adopted ticket. ZIP/portable closure, commit и runtime loop по-прежнему отсутствуют; сценарии не запускались.

`SchedulerExportArchiveReader` переиспользует bounded ZIP/manifest/XMP reader и повторно квалифицирует JSON результат после физического IO. Для `photoeditor_bundle` он требует отдельную scheduler-owned person-origin фабрику; session-bound фабрика API не подставляется. Пока такая фабрика не установлена, bundle путь закрыт. Portable source closure, commit и runtime loop ещё не реализованы; сценарии не запускались.

Миграция `02039_v30_export_adoption_person_origin_inputs.sql` и `SchedulerExportPersonOriginInputs` дают scheduler только точные `PersonOriginReceipt`, запечатанные во входах claimed task, с проверкой canonical result и lease до/после чтения. Код сверяет bucket, версию, размер, SHA и тип объекта; unit-сценарии написаны, не запускались. Это источник для будущей фабрики, но ещё не сама фабрика: в ней нужно переиспользовать проверку подписи, маски и текущего producer authority без пользовательской сессии, затем снова сверить object pins перед adoption.

Миграция `02040_v30_export_adoption_result_input.sql` и `SQLSchedulerExportInputCatalog` добавляют служебный каталог точных typed inputs для portable closure, также под canonical result и lease. Каталог не выдаёт документы вне запечатанного input inventory и не использует session-bound draft fallback. Остались физическая квалификация closure, scheduler person-origin producer lookup и общий transactional adoption; миграция и unit-сценарии не выполнялись.

Миграция `02041_v30_export_adoption_person_origin_current.sql`, `SchedulerExportPersonOriginCurrentChecker` и `SQLSchedulerExportPersonOriginInstallation` связывают подписанные receipts с текущим canonical mask.person producer под тем же claim. Фабрика сверяет frozen plan, запечатанный receipt inventory, подписи, MaskRef, Canvas SHA и повторно читает object pins после IO; архивный reader может принять её как `Origins`. Это не финальный adoption: portable closure, транзакционный commit и scheduler runtime ещё отсутствуют. Новая миграция и unit-сценарии написаны, но не выполнялись.

Миграция `02042_v30_export_adoption_evidence.sql` и `PreparedExportAdoption.SaveScheduler` добавляют служебный pre-commit барьер: исходная frozen identity, lease, canonical outputs, typed source inventory и object pins проверяются снова под блокировками перед сохранением immutable evidence. Это не adoption и не terminal transition; метод должен вызываться только после полной физической проверки archive и portable closure. Миграция и unit-сценарии не выполнялись.

Миграция `02043_v30_export_adoption_commit.sql` и `PreparedExportAdoption.AdoptScheduler` добавляют атомарное сохранение evidence и публикацию links/inbox/event с тем же claim; точный replay возвращает прежний результат без второго события. Это SQL/Go commit primitive, а не установленный processor: подготовка portable closure и финализация run ещё отсутствуют. 02042–02043 и сценарии не выполнялись.

Аудит актуального foreground catalog обнаружил расхождение в ещё не применённых 02036/02037/02040: они обращались к несуществующему `artifacts.key`, а 02040 сохранял старую матрицу contract/media. До её применения scheduler export нельзя включать.

Реальная native closure требует ещё остальных authority (`DenseWarp`, LUT, defect, mask, Params mask, resolved origin) и process-installed probes; 02045 и тесты не выполнялись.

Миграция `02046_v30_scheduler_lut_origin.sql` и `SQLSchedulerExportInputCatalog.QualifyExportLUT` добавляют второй native authority: frozen source snapshot, exact `ResolvedStyle → AbsoluteLUTArray` edge и текущий canonical `style.resolve` producer с attempt/fence/outputs проверяются под claim; object pins повторно читаются после SQL. Миграция `02047_v30_scheduler_params_mask.sql` и `SQLSchedulerExportInputCatalog.QualifyExportParamsMask` связывают inline MaskRef в точных Params с текущим завершённым producer, source frozen snapshot и запечатанным MaskPixels input; Go повторяет typed JSON extraction и object pin reads. Это ещё один native authority, но не полная closure; 02047 и сценарии не выполнялись.

Миграция `02048_v30_export_adoption_renew.sql` и `SQLExportAdoptionClaimStore.RenewExportAdoptionClaim` добавляют продление только живого exact-token claim после повторной проверки canonical result. `SchedulerExportAdoptionProcessor.ProcessOne` теперь связывает claim, физическую подготовку и атомарный adoption с heartbeat и отменой при потере lease; `SQLSchedulerExportAdoptionHandler` передаёт подготовленную closure в commit. Это пока не установленный runtime loop: отсутствуют bootstrap/ready/shutdown и полная native bundle authority. Сценарии написаны, но не запускались.

`BuildSchedulerExportAdoptionProcessor` собирает claim/reader/archive/origin/native/commit и проверяет в startup точный `photo_scheduler` SQL surface, owner, SECURITY DEFINER и отсутствие PUBLIC EXECUTE. Фабрика требует process-installed native resolver и trust даже для sidecar, так как один queue claim покрывает также bundle. Подключение фабрики к scheduler loop и реализация недостающих native source authority ещё открыты. Unit-сценарии написаны, не запускались.

Scheduler runtime теперь имеет `RunSchedulerWithInterchangeExport` и `SchedulerInterchangeExportFactory`: установленный job включён в bounded loop, readiness, метрики и shutdown. Startup отвергает nil-job и ошибку фабрики. Executable пока не передаёт конкретную фабрику, так как scheduler native bundle authority ещё не полна; поэтому эта wiring-ветка не считается включённым export lifecycle. Unit-сценарии написаны, не запускались.

Миграция `02049_v30_scheduler_working_warp.sql` и `SQLSchedulerExportInputCatalog.QualifyExportDenseWarpOccurrence` добавляют scheduler authority для `WorkingImage` transform-chain → `DenseWarpField`: sealed inputs, frozen snapshot, собственный текущий canonical producer поля и повторная проверка object pins. Миграция `02050_v30_scheduler_mask_array.sql` и `SQLSchedulerExportInputCatalog.QualifyExportMaskArray` добавляют scheduler authority для MaskRef → MaskPixels, когда оба объекта опубликованы одним canonical producer с единственным WorkingImage input из frozen snapshot. Go проверяет физический JSON edge и повторно сверяет точные object pins. Другие допустимые foreground provenance формы, в том числе разные producer, пока закрыты; 02050 и unit/role-сценарии не выполнялись.

Миграция `02051_v30_scheduler_mask_warp.sql` расширяет DenseWarp authority на MaskRef с уже доказанным MaskRef → MaskPixels edge. Поле может иметь другого canonical producer, но он обязан ссылаться на тот же единственный исходный WorkingImage из frozen snapshot; Go перепроверяет edge и object pins после SQL. Формы MaskRef, не покрытые контрактом 02050, остаются закрытыми. Миграция и role-сценарии не выполнялись.

Миграция `02052_v30_scheduler_defect_label.sql` и `SQLSchedulerExportInputCatalog.QualifyExportDefectLabel` дают scheduler authority для обычного `defects.propose`: точный DefectCandidates → DefectLabelMap edge, frozen source, завершённый canonical producer, report/protection/Params и output fences. Ветки V27 native/target handoff требуют отдельного result-catalog proof и пока явно отклоняются. Миграция и unit/role-сценарии не выполнялись.

`SchedulerExportNativeInstallation` и `NativeExportDeployment.BuildSchedulerExportAdoptionFromDeployment` теперь собирают фоновый native resolver из того же pinned deployment, style validator и физических probes, что foreground export. Для каждого claim валидатор строится заново на точных frozen документах и scheduler input catalog; JSON-only fallback отсутствует. Остальные scheduler authority интерфейсы, нужные стилевому validator, пока не реализованы, поэтому bundle остаётся fail-closed и executable ещё не включает фабрику. Unit-сценарии написаны, не выполнялись.

`SchedulerExportClosureReader` соединяет проверку канонического result/ZIP с существующим полным обходом portable source inventory и manifest validation; он требует process-installed `SchedulerExportNativeResolverFactory`, возвращающий graph-bound native resolver, и после физического IO повторяет result, bundle object и person-origin проверки. Он формирует sessionless immutable evidence для `AdoptScheduler`. Поскольку native factory и оставшиеся SQL authority ещё не установлены, bundle путь по-прежнему fail-closed. Unit-сценарии написаны, не выполнялись.

## Граница первого MVP

Миграции `02074–02076` и scheduler-методы `ReadExportBodyDependencyQualification`, `LookupExportBodyDependencyOrigin`, `MatchExportBodyDependencyProfile` переносят V30 body dependency (`pose.detect`, `face.landmarks`, `pair.fit.body`) на exact export claim. Report проверяется по операторской политике и физическим bytes до/после IO; origin связывает sealed geometry.body Params, accepted source, canonical child producer и original Params; профиль повторяет текущие execution locks после origin recheck. `SQLExportBodyDependencyInstallation` теперь строит этот native qualifier для scheduler без HTTP-сессии. Startup inventory включает три SQL-функции; миграции и unit-сценарии написаны, не запускались. Вложенные fit/alignment/feature/detector установщики ещё требуют отдельного переноса.

Миграция `02077_v30_export_adoption_body_fit_inventory.sql` и `SQLSchedulerExportInputCatalog.QualifyExportBodyFitInputInventory` проверяют полный набор входов BodyFit, полученный из его запечатанного JSON, против текущего canonical `pair.fit.body` producer под exact claim. Оба исходных изображения должны быть принятыми версиями в frozen snapshot; SQL проверяет pinned output и producer attempt/fence, а Go повторяет origin lookup после запроса. Это prerequisite для вложенной alignment-цепочки; alignment origin, qualification, profile и background mask ещё не перенесены. Миграция и unit-сценарий написаны, не запускались.

Миграция `02078_v30_export_adoption_body_alignment_origin.sql` и `SQLSchedulerExportInputCatalog.LookupExportBodyFitAlignmentOrigin` связывают PairAlignment edge в запечатанном BodyFit с исходным `pair.register` Params и теми же двумя изображениями. SQL требует current canonical result/attempt, CPU profile, pinned output, source-ready claim и актуальные consent epochs; Go повторяет BodyFit inventory, fit consumer и output после lookup. Содержимое original Params, qualification/profile и background mask ещё требуют переноса. Миграция и unit-сценарий написаны, не запускались.

Миграция `02079_v30_export_adoption_body_alignment_qualification.sql` и `SQLSchedulerExportInputCatalog.ReadExportBodyFitAlignmentQualification` привязывают выбранный оператором `pair.register` report к актуальной admission policy в exact claim. ## Переход к фазе тестирования

### V23 series learning: текущая граница кода

`learning.fit` теперь объявляет frozen series evidence, исходный stage image, `SeriesParams` и `SeriesCorrections` по точным ссылкам из сохранённого recovery. Go требует совпадение tenant/event/asset/source с manifest и детерминированный ID документа; worker дополнительно сверяет ID с training run и проверяет scene, число и уникальность элементов, reference item и наличие выбранного item в коррекциях. Написаны Go/Python unit-сценарии; согласно принятому порядку они ещё не выполнялись.

Миграция `02093_v23_series_freeze_gate.sql` продолжает запрещать admission manifest с `series_evidence`. До её снятия требуется запечатать и независимо проверить все `SeriesStats` из `SeriesParams`, их исходные `series.measure` и физические входы, затем выполнить одинаковый series replay в baseline/candidate/approved ветвях Evaluate и квалифицировать метрики. Наличие прямых входов Fit не доказывает эти требования.

Миграция `02096_v23_series_stats_locator.sql` даёт event-scoped локатор каждой статистики из того же запечатанного Apply balance: она сверяет вход balance, результат `series.measure`, исходный stage от `image.color`, snapshot item и pinned object version. `PrepareSeriesHoldoutForCandidate` повторяет lookup до/после физического чтения каждого `SeriesStats` и проверяет ID item/image из тела против SQL. Новый валидатор всего агрегата требует SHA/JCS каждого элемента, уникальные item, соответствие выбранному stage image и точное пересечение общих регионов. Эти изменения и unit-сценарии написаны, не запускались.

Миграция `02097_v23_series_stats_recovery.sql` добавляет `series_stats_jcs` к pending training receipt. Она требует полный упорядоченный список Stats из canonical `series.balance` Params для каждого series event и проверяет каждый элемент через `v23_series_stat_artifact`; прежний validator обрабатывает остальные поля после временного снятия нового поля. Go recovery проверяет canonical bytes, уникальность ссылок и соответствие набора событий manifest. Fit closure объявляет все сохранённые Stats как `SeriesStats`, а worker требует эти typed entries в точном порядке Params. Unit-сценарии написаны, не запускались. Freeze gate остаётся: Evaluate и quality admission ещё не завершены.

Worker `series_replay.py` теперь проверяет evidence/run/item, stage metadata, Params, всю статистику и точное пересечение регионов перед выбором `ItemCorrection`. `render_holdout_triplet` передаёт один замороженный correction через production `apply_series` в baseline/candidate/approved и повторно проверяет его неизменность. `trainingSeriesStyleEnabled` принимает только точные параметры, которые реально создаёт Apply (`median`, `0.35`, `0.95–1.05`), чтобы сравнение не использовало другой эффект. Написаны unit-сценарии; не запускались.

Миграции `02098_v23_evaluate_series_authority.sql` и `02099_v23_evaluate_series_nested.sql` дают fenced Evaluate-источник для готового evidence и каждого вложенного JSON-документа. Они требуют живой expansion lease, завершённый Fit с точным typed input, текущий consent/Apply producer, готовый backend document и pinned object versions; отдельная owner-only копия Apply locator убирает только интерактивную editor session, сохраняя source/tenant/project/actor проверки. Go reader повторяет authority до/после каждого object IO, сравнивает SQL-метаданные каждого Stats с физическим телом и включает все refs в Evaluate task closure. Go admission допускает лишь точные параметры series, производимые Apply. Unit-сценарии написаны, не запускались. Миграция `02093` по-прежнему запрещает запуск series manifest: её можно пересмотреть только после проверки этих миграций, полного Evaluate/quality acceptance и отсутствия других разрывов.

Миграция `02100_v23_evaluate_series_commit_gate.sql` повторяет проверку каждого holdout series evidence в атомарной транзакции закрытия Evaluate. Она сопоставляет текущий источник и полный список Stats из запечатанного `series.balance` Params с typed входами Evaluate и повторно вызывает nested locator; новый guard включён после существующих defect/dust/detail/protection guard. При неполном наборе Evaluate не открывается. Код написан, миграция и интеграционные проверки ещё не выполнялись. Freeze gate для series manifest остаётся в силе.

`CompileEvaluateClosure` теперь учитывает самый большой набор `SeriesStats` среди последовательных holdout cases в RAM и scratch estimate: 32 KiB pinned body, дополнительный буфер доставки и decoded-object headroom на каждый элемент (до 2000). Границы и арифметика покрыты unit-сценарием. Это статический reserve, а не измеренный peak; freeze gate остаётся до общей проверки на Metal и квалификации качества.

Worker Evaluate повторно вычисляет весь `SeriesCorrections` тем же `series.balance` алгоритмом из запечатанных `SeriesParams` и полного набора `SeriesStats`; сравнение canonical bytes отвергает результат, который не следует из статистик, до выбора коррекции holdout item. Unit-сценарий включает подмену значения коррекции. Рефакторинг и сценарий написаны, но не запускались; для допуска manifest по-прежнему нужны qualification и полный тестовый цикл.

Операторские `models` и `style_weights` теперь принимают только ID из закрытого model lock registry. Это статическая защита установки, а не доказательство физической доступности файлов весов; последнее остаётся отдельным acceptance gate.

Все операторские и обязательные V30 export operation model locks теперь должны совпасть с единым `Base.ModelSHA` — внутренним `lock_id` проверенного model lock. Так же worker `ModelPool` идентифицирует модель при выполнении. Несовпадение любого report/policy приводит к отказу при установке export; отдельные unit-сценарии для чужого lock написаны, но не запускались.

В export operator manifest добавлено необязательное поле `style_weights`: отображение `model.id → weight_id` для `StyleV2` и `ResolvedStyle`. Поле `models` сохраняет отдельное значение `model.id → SHA-256 lock` для операций, включая маски и override. Установщик теперь получает оба значения `lock_id` и inventory весов из одних аутентифицированных bytes model lock; операторский `style_weights` принимается только как точное подмножество этого inventory. При установленном manifest пустой `style_weights` разрешает только стили без моделей; нужные веса оператор обязан указать явно. `RenderComposition` передаёт обе политики раздельно. Написаны Go/Python unit-сценарии на одинаковый model ID с разными weight ID и lock SHA, а также отказ при несовпадении веса с model lock; они ещё не запускались. До принятия export необходимо проверить реальную конфигурацию весов и полную native-трассу на тестовом корпусе.

Перед переходом: по каждой включённой операции есть трасса и написанные unit-сценарии, все её миграции и installation paths присутствуют в репозитории, ни одна ветка не заканчивается только draft/receipt без результата, доступен явный отказ при отсутствии квалификации. Затем выполнить в порядке: fresh/upgrade PostgreSQL и роли; unit/typecheck; DB+MinIO/gateway integration; браузерные и native клиентские сценарии; фото-корпус и human quality; restore/GC/races; длительную смешанную нагрузку. Текущая аппаратная проверка — Metal с лимитом видеопамяти 10 ГБ. RTX 3060 квалифицировать отдельно; результаты Metal не переносить на него автоматически.
