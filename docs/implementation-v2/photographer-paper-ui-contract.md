# Photographer — React Native Paper

Основание: пользователь потребовал перевести весь UI `apps/photographer` на Paper и затем повторно проверить приложение. Область включает все маршруты и все производственные компоненты, в том числе loading/error/empty/denied/cancelled/recovery состояния и новые экраны.

## Компоненты

- React Native Paper 5, Material Design 3; единый `PhotographerPaperProvider` в `app/_layout.tsx`, SafeAreaProvider и Material Community Icons.
- Обычный текст, ввод, индикаторы, кнопки и интерактивные поверхности — компоненты Paper. Основные действия используют Button с собственными children и режимом contained; дополнительные — text/outlined. Старые фоны/цвета catalog-кнопок не должны перекрывать disabled цвета Paper.
- Состояния checkbox/radio/switch/selected не передаются в Button: библиотека заменяет accessibilityState. Применяются соответствующие компоненты выбора либо TouchableRipple с сохранением точного состояния и единственным дочерним контейнером.
- В текущем React Native Web состояние выбора задаётся также явным `aria-checked`: одного native `accessibilityState.checked` недостаточно. Для языка используются Paper TouchableRipple и визуальный RadioButton с единственным доступным radio на язык; вложенный визуальный индикатор не создаёт второй доступный control. Тесты проверяют реальное checked состояние и disabled-атрибут кнопки, а не отсутствие старого aria-атрибута.
- Для составной строки сохраняются исходные направление, выравнивание и размер контента; добавление View для TouchableRipple не должно превращать горизонтальную строку в колонку.
- React Native остаётся для layout, списков, платформенных API и изображений. Canvas, маски, loupe и before/after остаются специализированными средствами отображения, их обычные элементы управления — Paper.

## Тема и поведение

Текущий общий визуальный профиль — MD3 Dark с нейтральным окружением фотографий и сиреневым primary. Тема находится в `src/paper-theme.ts`, провайдер — `src/paper-provider.tsx`; общие catalog styles используют её цветовые роли. Существующее сохранение предпочтений профиля не удаляется. Внедрение Paper не является доказательством применения всех сохранённых theme preferences на каждом экране.

UI-перенос не меняет API, tenant/role authority, immutable intents, CAS revisions, journal recovery, отмену запросов, подписанные URL, ограничения памяти или принятие AI-результатов. Каждый обработчик должен сохранять прежние проверки актуальности.

## Проверка

1. `npm run typecheck` в приложении.
2. Полный `npm test` без исключения прежних случаев; пропуски фиксируются отдельно и не считаются принятыми live-сценариями.
3. `npx expo export --platform web` на финальных исходниках.
4. Реальный браузер: авторизованные маршруты, действия, формы, сохранение языка, состояния ошибки и отсутствие runtime overlay. Мобильная сборка и аппаратная квалификация имеют собственные границы доказательств.
5. `src/paper-ui-policy.test.ts` проверяет все production TS/TSX в app/src и запрещает возврат обычных UI primitives из React Native.

Точные результаты и source manifest финального прогона сохраняются в `audit/mac-deep-testing-2026-10-17/paper/`. Промежуточный зелёный тест не означает завершения всего модуля или платформы.

## Синхронизация тестовых событий

Установленный React Native Web обновляет PressResponder.disabled/onPress в passive useEffect. Изменение DOM ещё не доказывает обновление этой конфигурации. В jsdom `src/test/paper-events.ts` завершает pending React effects через flushSync до штатного act(event), с защитой от вложенного dispatch и сохранением return/ошибок. События не повторяются, таймеры не продвигаются, библиотека Paper не подменяется. Прямые вызовы сохранённых обработчиков продолжают проверять защиту от устаревшей authority. fsModuleCache кэширует только преобразование модулей в репозитории; выполнение тестов и изоляция не отключены.

Положительные ожидания действий используют `src/test/ui-readiness.ts`:120 прежних проверок aria-disabled дополнены обязательным существованием control и нативным disabled;44 действия, которые раньше ждали только появления кнопки, ждут её готовности. Намеренные нажатия на disabled-кнопки и прямые вызовы устаревших callbacks не заменяются ожиданием enabled. Этот слой не делает запросов и не повторяет событие автоматически.

После последующих полных прогонов62 положительных действия в21 тестовом файле, непосредственно следующие за await waitFor(expectEnabled), дополнительно используют clickWhenEnabled. Исходное ожидание и все последующие assertions сохранены. AST-преобразование не затрагивает raw negative/stale actions. Glare/Relight/Negative/Editor родственные сценарии отдельно просмотрены целыми файлами; намеренные disabled/duplicate/retained callback действия остаются прямыми.
