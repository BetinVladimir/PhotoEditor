# Текущий план закрытого web-MVP

Статус: принят пользователем 2026-10-20. Это актуальная граница первого закрытого релиза; полная цель V20–V32 сохраняется. При конфликте с прежними планами MVP эта запись определяет приоритет выпуска. Контракты данных и безопасности включённых функций сохраняются. Перенос проверки не означает PASS или завершение модуля.

## Продукт первого релиза

Web-приложение для фотографа и небольшой студии: вход → создание проекта/коллекции → импорт поддерживаемых файлов → отбор и сравнение → недеструктивное редактирование/AI → просмотр результата → явный Apply либо отказ → экспорт → публикация и скачивание клиентом. Portal и photographer web выпускаются согласованно с backend/worker. Базовые роли: владелец и фотограф; базовые приглашения и управление доступом. Существующие локализация и языковые URL сохраняются.

Один сервер, PostgreSQL, объектное хранилище, ограниченная очередь и явно заданная параллельность допустимы. Поддерживаемые форматы, камеры и выходные пресеты ограничиваются фактически проверенной матрицей; неподдержанный ввод получает явный отказ, а не неявное ухудшение результата. Матрицу нельзя придумывать до измерения.

Весь фактически доступный AI сохраняется. Стабильные и экспериментальные операции различаются в интерфейсе. Для экспериментальных обязательны честный статус, ограничения, предпросмотр и решение фотографа; они не применяются молча. Метка experimental не заменяет проверки авторизации, контракта входов/выходов, сохранности оригинала, памяти и публикации результата. Неустановленные модели или неквалифицированный backend не объявляются доступными.

Проверки продолжаются локально на Mac/Metal без фиксированного ограничения 10 ГБ. Для Metal используются существующие альтернативы CUDA, когда они есть и проходят свои проверки. CUDA-only без доступной альтернативы остаются недоступными с причиной. RTX установка/квалификация отложена до предоставления сервера по прежнему решению пользователя; Metal-результаты не объявляются доказательством CUDA. Полная аппаратная цель не отменена.

## Обязательные условия выпуска

1. Согласованная новая установка и обновление: действительная цепочка миграций до2625, функции/ACL/ledger, финальные captures, корректные роли, очистка окружений. Обрывать существующую цепочку ради скрытия UI нельзя.
2. Вход/сессия и приглашение базовой роли; положительные сценарии и реальные отказы чужому tenant, чужой роли и отозванному доступу. Изоляция файлов, подписанных ссылок и задач сохраняется.
3. Реальные фотографии проходят основной путь целиком: исходные байты не меняются, lineage/version pins, ICC/color, alpha и поддерживаемый RAW корректны; существенный результат просматривается фотографом до применения.
4. Apply сохраняет атомарность, идемпотентность и корректность повторов/отмены. Нельзя пропустить проверки параллельных запросов и восстановления только потому, что редкие UI-комбинации отложены.
5. Экспорт содержит полный required bundle, корректные ICC/metadata; публикация, отзыв и клиентское скачивание проверены на конечных файлах.
6. Очередь и worker не теряют задачи при поддерживаемых отказах; контролируемые повторы, лимиты памяти/параллельности, понятные ошибки и восстановление проверены на текущем узле.
7. Backup/restore и tenant purge проверены с реальными ролями и объектным хранилищем. Ошибка очистки не превращается в успешный статус. Прежнее требование ждать истечения всех backups для статуса удаления не возвращается.
8. Размер текста/контраст выпускаемых web-экранов измерены; основной путь проверен в текущей сборке. Итоговый gate не допускает необъяснённые FAIL/SKIP в обязательных сценариях.

Платный запуск по-прежнему требует B0–B4 из billing-prelaunch-plan-2026-10-18.md. Эта запись не объявляет биллинг реализованным и не разрешает платные продажи без него. Развёртывание и публикация сохраняют отдельные ранее установленные границы авторизации.

## Порядок работы для ускорения

1. Завершить текущую coherent installation2615–2625 и оставшиеся связанные исправления. Использовать один owner для всех оставшихся фаз с независимыми per-phase gates, а не создавать десять отдельных процессов разработки.
2. На принятой установке последовательно закрыть основной путь фотографа и клиентской выдачи; каждому дефекту дать воспроизводящий сценарий, исправление и целевой повтор.
3. Отдельной параллельной линией подготовить проверки web UI, реального фото-корпуса и Metal. Общий SQL/broker/storage lane остаётся единственным; параллельные агенты не запускают конкурирующие установки.
4. Зафиксировать состав выпуска, модельные/runtime locks, поддерживаемую матрицу и сборку. Не добавлять новые камеры, модели, пресеты или интерфейсы в этот цикл без отдельного решения.
5. Повторять только затронутые проверки и их зависимости. Полный обязательный release regression выполнить на согласованной итоговой сборке; исторические результаты и результаты другого source vector не переносить.
6. После закрытия основного пути выполнить базовые роли/приглашения, негативные security-сценарии, recovery и font/contrast. Расширенные63 браузерных сценария не являются безусловным gate web-MVP, но каждый затрагивающий выпускаемую функцию или инвариант остаётся обязательным. Полная приёмка V26 до всех63 не объявляется.

## Уточнение web-приёмки после инвентаризации 2026-10-20

Источник: `work/mvp-web-release-case-selection-audit-r1/README.md` и `missing-required.json`. В текущем UI 42 логических экрана Photographer (126 языковых URL), три шаблона Portal, всего 44 отображаемых экрана. Из прежних 63 сценариев 49 обязательны, три требуют разделения или нового ограниченного fixture, шесть расширенных сочетаний отложены; пять сценариев каталога стилей остаются в охвате реально доступного UI. Capture также остаётся в охвате: перенос аппаратного tethering не отменяет доступные съёмочные сессии. Это состав проверок, а не PASS.

Существующие 63 сценария не закрывают следующие обязательные группы: вход/регистрация по admission; импорт реальных поддерживаемых фото; отбор/сравнение/редактор; все доступные AI; review и lineage результата; Apply и восстановление; реальные экспортные файлы; положительная клиентская выдача; базовые приглашения и доступ; изоляция обработки и выдачи; очередь/память/отказы; размер текста и контраст текущих состояний; согласованная итоговая сборка/backend gates. Каждая группа требует исполнимых сценариев и фактических результатов.

Роль фотографа должна быть явно сопоставлена фактической серверной роли `editor` в fixture и контракте приёмки; новый enum не вводится предположением. Новый successor должен использовать актуальные языковые маршруты и Portal landing. Mutable evidence-реестры не являются runtime code authority: изменение реестра после snapshot аннулирует соответствующий CAS-check, но само по себе не доказывает дефект приложения. Замороженные audit-пакеты не переписывать.

### Ускорение: общий прогон миграций и функций

По запросу пользователя оставшиеся 2617–2625 и проверки функций объединяются единым оркестратором. Это изменение организации запуска, а не пропуск проверок. Оркестратор сохраняет отдельные evidence для compile/parser/apply/postdelta, проверяет точный исходник и реальную базу каждого этапа, останавливается при первом дефекте или отсутствующем обязательном review. Независимые reviews привязаны к фактическим артефактам; автоматическая выдача фиктивного approval запрещена. После 2625 обязательны существующие проверки функций на принятой изолированной копии. Fresh и upgrade остаются двумя сценариями общего запуска. Цель — убрать ручные переключения; готовность общего запуска подтверждается только его реальным выполнением.
