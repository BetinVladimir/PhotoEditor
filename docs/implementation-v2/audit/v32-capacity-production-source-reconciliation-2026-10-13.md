# V32 capacity scheduler production source reconciliation — 2026-10-13

The old statement that `CapacityRuntime` lacks production scheduler composition is stale as a source-presence claim. `backend/internal/workflow/service.go` reads the explicit `PHOTO_V32_SCHEDULER_POLICY_SHA256` pin, constructs `NewCapacityRuntime` with the scheduler-role pool, and closes it with the scheduler lifecycle. The main dispatch loop calls `capacityRuntime.Dispatch` when installed; its legacy `Dispatcher` is constructed with `LegacyOnly: capacityRuntime != nil`, so the two pickers are separated in the enabled process. `CapacityRuntime` itself checks the installed SQL signature/ACL contract and current policy before every cycle, then dispatches CPU, GPU and signer pools under one leader session.

This is source reconciliation, not V32 acceptance. The optional environment gate means a process without a policy pin still follows legacy dispatch. The V32 SQL migrations, real policy installation/revocation, backlog fairness, tenant isolation, simultaneous scheduler ownership and production worker capacity behavior remain unverified. No tests, builds or migrations were run during this review.

The production loop previously treated a `CapacityRuntime.Dispatch` error as a deferrable cycle even though `CapacityRuntime` closes its leader and selectors on such errors. Every later tick then called the terminal instance again. The loop now returns the capacity error when its parent context is still active, so the service supervisor can create a new instance and leader session; parent cancellation retains ordinary shutdown. Existing closed-runtime unit coverage remains authored but this production lifecycle change is NOT RUN.

The candidate snapshot remains an explicit unresolved V32 scale gap. SQL migration 01668 removed the 10,001-row cap to avoid silently omitting later tenants; `ReadCapacityCandidates` streams the complete statement and rejects errors/cancellation, but returns an in-memory slice of every candidate. `CapacityDRR.Next` compresses only its derived FIFO heads; `ReadCapacityAffinity` and `ApplyAffinity` still consume the full slice. A fixed reader cap would preserve memory but stop dispatch for a large backlog; truncating would break fairness. Bounded-memory completion therefore needs a redesigned per-tenant/class snapshot and scoped affinity interface with a consistent SQL snapshot, not a local limit constant. No cap or partial-snapshot fallback was introduced.

Source trace for the redesign: `CapacityEffectiveQueue` promotes one class after ten minutes using the cycle clock; `CapacityDRR.BeginCycle` needs the maximum runnable charge; `Next` needs the earliest `(created_at, task_id)` for each `(tenant_id, effective_class)`; `ReadCapacityAffinity` and `ApplyAffinity` need only the selected head and same-tenant/class candidates in the following thirty seconds, but may have an arbitrarily large burst. The current `capacity_queue_candidates` function sorts all eligible tasks and its targeted variant only validates one selected task at reservation. A correct bounded-memory change must move class/head/max-cost aggregation and the oldest qualified resident candidate selection into SQL at one consistent cycle authority boundary, expose only bounded head/evidence rows to Go, then revalidate the selected task under reservation. It must preserve all-tenant fairness, FIFO fallback, heavy-tenant exclusion, cancellation and duplicate/foreign affinity refusal. Neither Go slice truncation nor a per-tenant LIMIT meets that contract.

First implementation stage: forward-only 01782 adds a scheduler-only `capacity_queue_head_snapshot` over the complete eligible source. It derives effective class at a caller-pinned database time, excludes heavy tasks already at the tenant cap, returns only the FIFO head per tenant/class and repeats the maximum runnable charge needed for DRR's deficit cap. A private charge helper refuses invalid measured timing rather than silently replacing it. Go `ReadCapacityHeadSnapshot` owns and validates the compressed result, including class, cost, duplicate scope/task, consistent cap and cancellation; unit cases were authored, NOT RUN. This stage is **not installed into production dispatch**: scoped resident affinity and current-snapshot revalidation still use the full candidate slice, so switching now would change behavior. The SQL may still materialize a large source internally and the result scales with tenant count. Migration NOT APPLIED; no bounded-memory or whole-V32 completion claim follows.

Second stage: forward-only 01783 adds a scheduler-only `capacity_queue_head_affinity` for one selected head. It checks the head's current eligible tenant/class/time and heavy cap, chooses the oldest qualified resident task no more than thirty seconds behind that head, or returns the unchanged FIFO head when no residency is proven. It returns one row, never grants a reservation, and still delegates physical node qualification to the existing `capacity_task_affinity` authority. Go `ReadCapacityHeadAffinity` checks exact result count, tenant/class/window, valid model digest, charge and fallback identity; refusal and boundary unit cases were authored, NOT RUN. This source still re-evaluates the complete candidate function inside SQL and production dispatch still uses the previous full slice. Integration requires a head-aware DRR receipt/settlement path, a consistent database cycle clock, current policy and reservation checks, plus migrated SQL lifecycle tests. 01783 is NOT APPLIED and does not yet establish bounded database work or V32 completion.

Third stage: `CapacityDRR.BeginHeadCycle` now validates the SQL-compressed heads and uses the independently supplied maximum runnable cost when granting class quanta. `ApplyHeadAffinity` accepts one same-tenant/class, within-thirty-second resident hint only against the current pending FIFO receipt; it preserves the head when no residency is proven or a replacement exceeds the deficit. Replacement invalidates the old receipt and `Settle` continues to charge only a committed selected task. Existing full-candidate methods remain available. Unit cases for maximum-cap accumulation, replacement settlement and unchanged pending state after refusal were authored, NOT RUN. Production dispatcher has not been switched, and the two SQL migrations remain unapplied.

Fourth stage: the production `CapacityRuntime` now calls `DispatchHeadCycle` after its startup contract confirms both new scheduler-only functions. One database clock pins the head read and DRR age. Each attempt rechecks the immutable policy, reads one current affinity hint, applies it to the pending receipt, and uses the existing targeted authoritative reservation. A stale head is removed for the cycle; a resident replacement denied by reservation is excluded from later hints in that cycle, preserving the FIFO head without repeatedly retrying the same replacement. Only successful commits advance deficit and heavy accounting. 01783 now accepts an explicit bounded unique exclusion array; the Go reader copies and validates it. Refusal unit cases were authored, NOT RUN. The migrations are NOT APPLIED and full SQL/leader/concurrent backlog tests are outstanding. SQL still evaluates the complete candidate source internally, and one head per tenant/class still reaches Go; therefore absolute bounded-memory and V32 acceptance are not yet proven.

The 01783 affinity source was subsequently narrowed from the global `capacity_queue_candidates` call to a private `capacity_queue_tenant_candidates` function. Its predicates mirror the active tenant, v2/sealed run, ready/noncancelled task, admission delay, pool and eligible-node gates of 01633, with an explicit tenant and cycle-time filter. Only the selected tenant's current candidates are considered during repeated affinity attempts. The helper is owned by `photo_fn_owner` and not executable by scheduler/API/worker directly; the public scoped wrapper remains scheduler-only. This removes the repeated all-tenant SQL scan per hint, but does not remove the full queue scan for the initial head snapshot or establish absolute bounded DB memory. Migration remains NOT APPLIED; predicate parity and index-backed performance require deferred SQL checks.

Production startup now checks both new public scheduler functions and both private helpers (`capacity_queue_charge`, `capacity_queue_tenant_candidates`) for exact owner, SECURITY DEFINER/search path and role-specific EXECUTE posture. Contract unit inventory and migrated catalog drift cases were extended for private-function renaming, privilege grants, owner/invoker and search-path changes; authored NOT RUN. This prevents a partial 01782/01783 installation from starting the head-aware runtime, but does not prove function behavior or performance.

Head-aware DRR received a source-level parity case against the prior full-candidate DRR across multiple tenants/classes, an aged training task, a non-head expensive task affecting the cap and a heavy-at-cap tenant over sixty cycles. It checks task/tenant/class/charge and deficits after settlement. `ApplyHeadAffinity` now refuses a resident response for the same head when its current measured cost changed, rather than retaining an old receipt charge. The new 01782 head snapshot no longer calls the all-row `capacity_queue_candidates` PL/pgSQL set source. It reads eligible tasks directly under the same active-tenant, v2/sealed run, ready/noncancelled task, admission delay, pool and eligible-node predicates, aggregates queued GPU count once per tenant, and then computes effective class/charge/max-cost/FIFO heads. The 01783 tenant-scoped source likewise computes its heavy count once per call; its resident-choice CTE is materialized so fallback and selected result inspect one evaluation. These are authored SQL changes, NOT APPLIED or tested. They remove repeated correlated heavy counts and the extra global set-return materialization, but SQL still scans the eligible queue and may spill ranking/aggregation to disk; measured resource behavior and predicate parity remain open.

Forward-only 01784/01785 add separate concurrent indexes for `(tenant_id,created_at,id) WHERE state='ready'` and `(tenant_id) WHERE state='queued' AND resource_class='gpu'`. The existing ready admission index orders by admission_after/priority before created_at and cannot supply this FIFO order directly. Separate no-transaction migrations avoid blocking task writes during index construction; an interrupted concurrent build can leave an invalid index and must be detected/repaired before retrying. The scoped affinity SQL now rechecks that the snapshot head is still the first runnable task for its tenant/effective class by `(created_at,task_id)` in the current tenant source. A head displaced between snapshot and selection returns no row and is discarded for this cycle; the next cycle takes a fresh snapshot. The rollback-only semantics fixture adds both a preexisting non-FIFO head and a newly inserted earlier eligible task after the snapshot, each expected to be refused. The Go head dispatch cycle now indexes the validated complete head snapshot by task ID once, instead of scanning all tenant heads again for each of up to 100 selections. The map entry is removed when a FIFO head is retired in the cycle. This only reduces lookup work; `CapacityDRR.Next` still sorts/visits all active heads per attempt and the SQL snapshot still scans eligible tasks. Authored, NOT RUN.

The head dispatcher now calls a specialized DRR selector for the already validated one-head-per-tenant/class snapshot. It scans for the lowest eligible tenant UUID in the same class-cursor/pass order as the old selector, without allocating a grouping map or sorting the entire inventory on each attempt. The existing 60-cycle parity fixture now compares full-candidate DRR, previous head `Next`, and specialized `nextHead` selections/settlements. Authored, NOT RUN. This reduces in-process selection work but does not establish a bounded-memory snapshot or physical throughput.

Current source reconciliation: production `CapacityRuntime.Dispatch` now invokes `DispatchBoundedHeadCycle` for CPU, GPU and signer pools. Forward-only 01787 exposes `capacity_queue_bounded_head_choice`, which scans the complete eligible head set inside SQL but returns one DRR-eligible head plus the complete maximum runnable charge. Go retains only that one choice and up to 100 per-cycle exclusions, then rechecks scoped affinity, current policy, targeted reservation and settlement. `CheckCapacitySchedulerContract` includes the bounded function. Earlier paragraphs describing the production dispatcher as still using `DispatchHeadCycle` or retaining every tenant/class head are historical stages, not the current source path.

The bounded choice is recomputed from the complete SQL head snapshot on the initial cap read and on each of up to 100 attempts. This bounds application-memory transfer but may perform repeated full-queue scans, ranking and temporary-disk work. Existing rollback-only SQL parity fixtures cover a small two-tenant scope; no migrated high-cardinality query plan, work_mem/spill budget, simultaneous-leader behavior, 5000-target fairness run or production capacity result has been executed under the current code-first phase. `DispatchBoundedHeadCycle` now tears down its leader generation and selector when the initial clock/cap SQL read or `BeginBoundedHeadCycle` fails, matching its later-cycle error path. The production runtime also closes on propagated errors; this closes the lower-level lifecycle boundary. Authored source change NOT RUN.
