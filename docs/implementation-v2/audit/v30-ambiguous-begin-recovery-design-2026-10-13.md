# V30 archive Begin: recovery from an ambiguous S3 Create

Status: generation ledger, API/client status, exact-key storage paths and a cross-key admission fence are authored but **not tested or deployed**. Terminal proof for a dispatched Create with a lost reply remains unimplemented. `ARCHIVE_BEGIN_RECONCILIATION_REQUIRED` is a diagnostic refusal, not a release authorization.

## Safety invariant

An S3 multipart Create call may succeed after its client has timed out. `ListMultipartUploads` returning empty at one instant does not prove that the call has terminated. Therefore no retry, operator action, or cleanup may close an open Begin writer, release its reservation, or reuse its object key based only on a listing. A multipart ID observed by listing is also insufficient to bind the reservation, because it is not an authenticated receipt of the original Create call.

The recovery boundary must combine two independently durable facts: (1) the exact generation's Create request has terminated at the object-store client boundary, with a success ID or definite failure, or the generation has been permanently fenced by a provider operation with a documented terminal guarantee; (2) every multipart belonging to that generation has either been bound as the sole accepted upload or confirmed aborted. If neither terminal fact can be established, the reservation remains in `reconciliation_required`, quota remains held, and tenant purge remains blocked. Availability must not be obtained by weakening this invariant.

## Key and ledger model

Keep the logical `archive_upload_id`, request hash, intent and artifact identity stable across retries. Give each storage Create attempt a fresh, never reused `generation_id` (UUID) and object key `tenants/{tenant}/interchange-uploads/{upload}/generations/{generation}/archive.zip`. The exact key formatter is shared by Begin, Parts, Complete, Abort, discovery and purge. The canonical formatter, SQL ledger and production storage operations are authored but not qualified by migrated SQL or physical storage tests.

Add a `photo.v30_archive_begin_generations` ledger with `(tenant_id,upload_id,generation_id)` primary key, unique `(tenant_id,object_key)`, reservation token, writer token, creator user/session, request SHA, state (`creating`, `created`, `create_failed`, `aborting`, `aborted`, `bound`), nullable multipart ID, started/terminal timestamps and monotone revision. The parent upload will eventually record one active generation. Identity and object key never change after insertion. Partial unique constraints allow at most one generation in `creating|created|aborting|bound` per upload; transition functions must additionally enforce a single bound generation over the upload lifetime. Migration 01796 authors the table, constraints, RLS and tenant-purge fence, but does not create any generation rows or change legacy Begin. The existing writer ledger stays authoritative until a later forward-only migration handles legacy open writers explicitly. No migration may infer a multipart ID from S3 listing.

`start_v30_archive_begin_generation` is a SECURITY DEFINER tenant-scoped transaction: validate editor/session/project/request hash, lock the upload and writer rows, refuse a live generation, insert `creating`, attach it to the parent, and return the frozen generation/key to the caller. It must never call S3. `finish_v30_archive_begin_generation` accepts only the matching writer token, generation and a validated Create success receipt, stores the multipart ID and `created` state, and is idempotent only for identical bytes. `bind_v30_archive_begin_generation` atomically attaches that same ID/key/generation to the reserved upload and marks `bound`. Token or ID substitution is a conflict. Every function has explicit owner, `SET search_path`, revoked PUBLIC EXECUTE, and a minimal role allowlist; the migration updates installation ABI checks.

## Create result and cancellation

The Begin adapter allocates the generation before any network call and passes its key to S3 Create. It persists the returned multipart ID in a cancellation-independent, bounded transaction before trying to bind. An error, timeout, process crash, or unknown reply leaves `creating`; it never triggers another Create for that key. If the process receives a definite successful ID but the SQL close is uncertain, retry first reads the generation ledger. A durable matching ID can be rebound. A different ID is integrity failure. A local error is **not** a terminal failure proof unless the storage adapter establishes that the Create request could not have been sent or received a provider-declared definitive rejection.

The storage adapter must expose explicit outcomes `success(id)`, `definite_not_created`, and `unknown`. The current generic `(id,error)` cannot safely distinguish the latter two. Unit tests must inject a reply lost after provider success, cancellation before dispatch, cancellation during dispatch, crash after S3 success, lost SQL close reply and lost bind reply.

## Recovery and cleanup

A recovery controller reads the active generation under tenant and writer authority. For `created`, it binds the recorded ID; for `bound`, it returns the original reservation. For `creating` with an unknown outcome, it requires a terminal Create proof from the storage adapter/provider, **then** enumerates that exact generation key and aborts every observed multipart ID. It repeats discovery after the terminal boundary and confirms aborts; failure leaves the generation open. Only after this may SQL mark it `aborted` and allow a new generation/key. A provider without a usable terminal Create proof leaves the generation for manual provider investigation; an operator cannot override it by asserting an empty listing. Recovery never copies a discovered ID into a successful receipt.

All V30 cleanup and tenant deletion paths must enumerate every historical generation key, including abandoned and legacy generations, and retain the SQL rows until object-store deletion is confirmed. They must refuse purge while `creating`, `created`, or `aborting` remains unresolved. This is a forward-only change to the existing deletion contract, not a background TTL release.

## Public behavior and acceptance

Archive-upload and read-only attempt status expose `begin_recovery`: `none`, `reconciliation_required`, `receipt_pending_bind`, `resolved`. `receipt_pending_bind` means a concrete Create receipt was committed but parent binding is pending; it does not imply an active recovery process. Status never exposes generation ID, writer token or multipart ID. Begin retries with the same idempotency key and request hash return the original bound upload or 409 `ARCHIVE_BEGIN_RECONCILIATION_REQUIRED`; migrations 01805–01806 fence a different key for the same actor/project/request or content bytes in both Reserve and Start while a prior Begin is unresolved. The photographer client retains its local attempt and offers explicit status refresh. It does not start a replacement upload automatically.

Acceptance requires migrated PostgreSQL tests for concurrent Begin/recovery/abort/tenant purge and RLS/EXECUTE, an object-store fault harness that simulates late Create after timeout, lifecycle tests for every listed crash boundary, positive archive upload→parse→ingest after a recovered generation, and proof that no multipart for any historical generation remains after cleanup. These tests belong to the agreed later verification phase and have not been run.
