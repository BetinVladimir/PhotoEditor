# V23 Evaluate: frozen effect closure, source audit 2026-10-14

This is a code-phase source finding, not a passing test or a V23 acceptance claim. No build, test, migration or photographic qualification was run for this audit.

The requirement in `10-algorithms-calibration.md` evaluates baseline, candidate and human-approved output on the **same holdout frames and renderer**, including rendered color, clipping, protected pixels and identity. `07-execution-acceptance.md` requires leakage-free sessions, explicit activation, rollback and consent revocation for V23.

Current source correction: Go `TrainingRenderCase` (`backend/internal/v2learning/manifest.go`) and Python `RenderCase` (`workers/photo_worker/operations/learning/contracts.py`) now carry optional event-owned reviewed-defect and sensor-dust evidence in addition to the image, recipes, protection, faces, consent/effective mask, region masks and background asset. The guarded SQL closure, Go resolver and Python `pinned_provider.py` / `defect_replay.py` / `dust_replay.py` support those two qualified replay paths with their own restrictions; the rest of this document records how that support was added. `pipeline_admission.py` still refuses geometry, culling, series, composition, portrait detail, inpainting, generation, upscale and generated background, and refuses simultaneous reviewed defect and dust. `workspace.py` renders the supported color/beauty/background and reviewed replay paths. The remaining refusals must stay in place until each effect has exact frozen evidence and matching rendering for all three arms; dropping a refusal would compare incomplete images and could promote an invalid candidate.

The repository's production `workers/photo_worker/v2/render_defects.py` has a separate reviewed `defects.repair@1` path based on `DefectRepairParams`, current image, explicit protection, candidate and review documents, resolved style, runtime qualification and proposal outcomes. It cannot be inferred from the V23 style's `defects.enabled` flag. Other refused effects likewise require their own exact input closure and qualified renderer path; no shared generic no-op is valid.

Current source dependency for two further effects: `workers/photo_worker/v2/render_composition.py:compose_render_pixels` accepts an already prepared same-canvas base, declared layers/masks and a qualified proposal callback; its contract explicitly excludes geometry and cannot execute `StyleV2.extensions.composition` from the scalar flag alone. `workers/photo_worker/v2/render_detail.py:prepare_pinned_detail` requires exact version-pinned `PortraitParams`, its `WorkingImage`/`ResolvedStyle`, explicit region/protection mask arrays, current RGB/alpha bit equality, resource admission and review outcomes. The V23 `RenderCase`/Fit→Evaluate closure has no frozen portrait-detail Params/region-mask lineage for each example. To enable either effect, extend the event-owned manifest, Go/SQL closure and worker provider with those exact documents and binary references; preserve identical frozen input identities across baseline/candidate/approved, execute at the production stage, and require effect-specific quality/identity measurements. The existing refusal is correct until that path is present and independently qualified.

The existing review owner is `backend/internal/review/defects.go`: `DefectSnapshot` is read from a locked row plus verified proposal, and `DefectSelection` binds proposal, image, label map, revision and accepted/rejected candidate IDs. The production Python helper then reads `DefectRepairParams` and its image, proposal, review and resolved documents, compares an explicit protection document, checks source color/source SHA, retains candidate outcomes and applies the current-image pixel binding. The V23 `train_case_assembler.go` currently selects protected and region masks but never asks that review owner for a defect selection. `draft_manifest_validation.go` and the Python `RenderCase.identity_evidence_pair` validate the current reference set only. Those are the concrete source and validation insertion points; a V23 snapshot cannot synthesize candidate decisions from the StyleV2 flag.

The selected decision is stored in the `photo.reviews` row as `selection` JSONB plus `decision_hash`, `decision_route`, `revision` and actor metadata (`backend/internal/review/persist.go`). It is **not** already an immutable object-store reference. The new holdout evidence publisher must lock and authorize that decided row, independently validate the stored `DefectSelection`, bind its decision hash/revision/route to the exact current source and repair Params, then publish a new immutable document. A manifest field must reference that newly published document only after SQL registration; fabricating an artifact ref from the review UUID or reading an arbitrary review row by client-supplied ID would break authority.

Further source audit: `photo.v23_training_candidate_rows` selects `photo.correction_events` bound to an accepted `asset_version_id` and its source master; `photo.create_defect_review` binds a separate `defects.propose` task to a run-local WorkingImage. Neither `correction_events` nor the current training candidate projection records a reviewed defect ID or its repair Params. A hash match or caller-selected review ID is insufficient to establish that the correction example and review describe the same version and edit lineage. The next SQL design needs an explicit tenant/project/version/event/review association, created only under current editor and producer authority, with source image, proposal, selected revision, repair Params and consent pins. Existing historical correction events without this association cannot acquire defect holdout evidence by inference.
