# Интеграция, миграции, безопасность и lifetime v2.2

## Границы функций и authority

Repository functions работают в переданной TX, не открывают вторую независимую транзакцию. Service формирует staged JSON до TX; TX не обращается к object storage, model runtime или сети. SQL проверяет relational facts: tenant/project, membership, source IDs, immutable artifact metadata/digest, canonical task/fence, current pointers, consent epochs. Pydantic/Go semantic validators до TX проверяют содержимое JSON/масок; SQL не притворяется способным прочитать artifact bytes. При commit повторить relational checks; staged result без commit удаляется обычным staging TTL. Артефакт immutable, поэтому hash проверенного содержимого остаётся действителен.

Автор derive из authenticated principal существующего API; SQL функции не принимают произвольного actor без проверки соответствия trusted session principal. Worker не может вызвать функции API и назначить actor. Trusted scheduler adoption проверяет persisted authenticated principal из admission snapshot. Все функции SECURITY DEFINER, owner photo_fn_owner, фиксированный search_path, REVOKE PUBLIC, explicit EXECUTE. Вызов function через API с подложным tenant/project не должен обходить membership даже при корректном app.tenant_id.

Единый порядок locks для бизнес-ресурсов: tenant lifecycle → project (при provisioning) → consent grants sorted UUID → runs sorted UUID → tasks sorted UUID → profiles sorted UUID → streams sorted UUID → остальные owner resources sorted(table,id) → quota ledger. Для V2 transport publisher и начального seal существует конкретный порядок `tenant_usage → run → task`: он совпадает с уже существующим `reserve_backend_document` и предотвращает инверсию при параллельной публикации объекта. Admission child inside review использует заранее выделенный child UUID; parent run lock приобретается до owner target locks; дочерний новый run ещё не видим и не участвует в конфликте. Revoke берёт все затронутые locks в этом порядке. Grant/profile lookup без lock до TX является только hint; после acquisition повторная проверка closure. SQLSTATE40P01/40001 retry entire TX максимум3 с jitter25..100ms; body/idempotency unchanged, затем409 RETRYABLE_CONFLICT. Нельзя retry после внешней отправки: её выполняет outbox.

## Точные команды изменения

`mutate_v2_resource` command allowlist: CreateSession, UpdateSession, CreateProfile, CreatePerson, ConfirmObservation, RevokePerson, ReplaceShotList, RegisterDevice, RevokeDevice, Acknowledge, PublishDelivery, ApplyApproved, CloseSemanticReview, DecideImport, CloseImportReview, ReviewLearningSafety. Каждая branch вызывает отдельную typed service/repository function, описанную13/15; name неизвестен→INVALID_COMMAND. Read methods, workflow admission, RecordCorrection, device challenge и receipt имеют отдельные entrypoints ниже; не generic dynamic CRUD.

Signatures для новых SQL entrypoints: первые аргументы tenant uuid, project uuid, principal uuid; затем typed request JSONB (проверить schema_id/version по branch), staged artifacts JSONB[{id,sha256,purpose,ordinal}], expected bigint nullable только там, где API не имеет CAS. Adoption/finalizer вместо user principal принимает canonical run/task/attempt/fence/result arguments03. Возвращаемый JSON строго по endpoint response schema. Request JSON не является источником arbitrary column names. Go repository функции: AdmitWorkflow, RecordCorrection, MutateResource, PersistChallenge, ConsumeChallenge, AcceptReceipt с тем же explicit DTO и passed TX.

photo_worker/photo_publisher/photo_portal не получают EXECUTE этих mutations. photo_auth не получает SELECT v2 table wholesale; auth-функции сами получают нужную строку. photo_api SELECT новых таблиц сохраняет tenant RLS, API отдельно project ACL; public Resource исключает capture_challenges, cleanup, private keys, raw ledger. Denied-role tests для каждого EXECUTE и прямого INSERT/UPDATE/DELETE обязательны.

## Миграционные детали

00196 добавляет v2_document_approvals и v2_review_batches вместе с document foundation. FK на будущие tables не создавать: обе таблицы зависят только от v2_documents/v2_workflows/runs/users/artifacts. Foundation guards не должны обращаться к отсутствующим session/learning tables. Каждая следующая migration заменяет guard function полным накопленным allowlist и добавляет собственные branches, не включает writers более поздних features. Draft learning_version_id/identity dependency запрещены до V23 capability. Проверять перед activation migration_head и registry entries.

00197 вводит sessions/persons/consent, unique(asset_version_id,face_id) для person_observations. face_id находится в immutable FaceObservations; observation_id в API — ID наблюдения в этом artifact, а DB evidence хранит его сопоставление через face_id. ConfirmObservation повтор same person/source/face возвращает row; другая person association409. После revoke person перепривязка требует нового explicit confirmation и нового consent, history сохраняется в audit.

00198 добавляет learning_safety_reviews и enum needs_review; identity.compare registry/version/policies регистрируется здесь, не ждёт00203/V28. 00199 хранит capture_policy в session, defaults для ранее созданных sessions вводить только если есть qualified calibration: до него capture unavailable, не fabricated qualified default. SessionCreate уже требует явный capture_policy, но capability проверки для unavailable capture не блокируют обычный Session Brain, если capture ещё не используется. 00205 добавляет interchange_targets, optional manifest pointers и delivery slots flags/hashes; текущие пустые v2 tables не требуют destructive backfill.

Reference SQL содержит формы будущих таблиц целиком. При разбиении по migrations поле capture_policy вводится в00197 как nullable до V24, в00199 приложение делает обязательным на новых/редактируемых capture-enabled sessions; legacy sessions могут хранить null до явного enable. Read schema RowShootSessions.capture_policy nullable, SessionCreate/Update.capture_policy nullable; отсутствие не блокирует остальные workflows. Не ставить NOT NULL без данных. Миграции не загружают calibration из сети.

Mutable revision всегда изменяет trigger; caller не делает отдельное +1 поверх trigger. Initial inserted revision1, subsequent update+1; первый успешный save draft возвращает revision2 после назначения current pointer. Immutable approvals и history не UPDATE. version_eligibility mutable, learning_versions immutable. reason lengths: review≤256, public name≤200, public person/device label≤120. DB constraints не должны быть уже API schemas. Capture sequence0 допустим, int64 upper bound проверяется до SQL.

## Artifact retention и purge

`RegisterClosureRefs(owner,closure)` в adoption/документной TX создаёт v2_document_refs либо v2_artifact_links для КАЖДОГО transitively referenced artifact. purpose = typed JSON path hash (SHA256 hex,≤256), ordinal=stable DFS index; unique(owner,purpose,ordinal). Direct FKs на artifacts не заменяют интеграцию existing GC live-reference predicates. Model qualifications, approvals.resolved_artifact_id, frozen delivery presets/shards, review decisions, imported files, output dense fields и signing manifests входят в тот же live set. Table/model links удерживают owner lifecycle.

`CanRetire(document,now)`: возраст≥90days, ни current/approved, ни learning_example/model_use, ни active workflow, ни publication, ни approval-retention hold. Retention удаляет bytes через existing GC tombstone ledger, оставляет immutable metadata с tombstone reference; GET retired document410 DOCUMENT_RETIRED. Исторический SHA не превращается в downloadable link. Не удалять immutable metadata отдельной maintenance DELETE; tenant purge остаётся единственным новым разрешённым physical metadata DELETE path. Уточнение read schema: Resource.document nullable при tombstone; история показывает state retired через existing artifact availability projection.

Revoke немедленно запрещает новые URL/compute по sensitive closure, но физическое удаление shared bytes ждёт окончания независимых authorized refs. Immutable links на revoked training records — audit refs, не independent legal pin; GC active-use predicate исключает disabled models и revoked-epoch workflows после fence. Оригиналы и обычные approved exports остаются independently pinned. cleanup consent ledger получает все sensitive artifact IDs, state blocked_shared только при реальном другом разрешённом использовании; ledger dependency/reason вычисляется join по links, отдельные несуществующие колонки не требуются.

Purge реализуется explicit allowlist database.json плюс прежний00195; pointers current/approved/active обнулить только deletion lifecycle. Порядок вычислить reverse FK dependency DAG после удаления этих cycle edges; guards допускают nullification в deletion state. FK DEFERRABLE не отменяет необходимость удалить всё до commit. Все новые objects включая staged ZIP/signature/warp поля должны входить object-cleanup inventory. После proof storage empty → physical metadata DELETE в existing finish_tenant_deletion. Grants photo_fn_owner DELETE не дают право удаления из generic mutation. Test пытается вызвать каждый service function вне lifecycle и подтверждает отказ.

## Device и ключи

Device public key32 bytes base64url без padding, signature64 bytes→86 chars, nonce32 bytes→43 chars; после decode проверять canonical re-encode. `CAPTURE_ORIGIN` задаёт точный HTTPS origin API для JCS-подписи challenge; в development по умолчанию используется `APP_ORIGIN`. JWT для устройства имеет отдельный `aud=capture` и 15-минутный срок, а каждая mutation повторно сверяет active state и credential_epoch в primary DB. Challenge encrypted server-side, TTL60s, consumed once; для unknown/revoked возвращается однотипный dummy response без DB provisioning. Limits: challenge5/min/device,30/min/IP, token10/min/device, excess429; per-device unknown IDs не дают unlimited IP budget. Tokens15min, mutations каждый раз проверяют device state+epoch на primary. Device creation Admin проверяет unique public key среди active devices project; private key никогда не приходит API.

Rotation в v2 — register replacement device → подтвердить connection → revoke old device. Sequence относится к device ID, новая начинается0. Journal переносит ещё не подтверждённые uploads с новым device/sequence; verified content dedup через существующий ingest, receipt другой пары не создаёт второй asset. Отдельного недокументированного rotate endpoint нет. Для lost key revoke немедленно, не ждать migration journal.

## Qualification и внешние входы

QualificationReport JSON хранится как artifact: schema_version1, operation/version, model_lock_sha, runtime_lock_sha, device_profile_sha, dataset_sha, input_fixture_shas[], checks[{id,passed,evidence_sha}], metrics{p50_ms,p95_ms,peak_vram_bytes,peak_rss_bytes,scratch_bytes}, status passed/failed, issuer_id, created_at. Схема в contracts. Trusted import сравнивает hashes с фактическими locks, issuer authorization, checks по package acceptance, отсутствие calibration/test overlap. Поле status=passed от обычного клиента не принимается. Никакой «положительный» fixture docs validator не является qualification report.

Model bytes/license clearance, камеры, signed certificate/trust policy, ICC/test corpus и RTX3060 benchmark остаются внешними evidence. Для каждого пакет сообщает конкретно awaiting_evidence с отсутствующими hashes/commands. Выбор vendor runtime для C2PA заключён в adapter с qualification; генерация интерфейса не означает interoperable signing до фактического SDK qualification. Выпуск всей заявленной системы требует эти gates, core-only release не закрывает полную дорожную карту.


`ImportQualification(report_ref,expected_locks,operator_principal)` — deployment CLI `photo-v2-qualifications import --tenant UUID --project UUID --operator UUID --report-artifact UUID --sha256 SHA --locks PATH`, не публичный user API. После JCS/schema/hash/license/evidence checks CLI читает immutable object version через `photo.v2_qualification_report_object` и вызывает `photo.import_v2_qualification(tenant uuid,project uuid,report uuid,sha text,operator uuid,backend text,body_text text) returns uuid` с EXECUTE только photo_maintenance. Последний аргумент нужен SQL, поскольку metadata таблица `artifacts` не содержит JSON body; SQL повторно вычисляет SHA256 UTF-8 bytes и сравнивает размер с artifact metadata. Backend берётся из deployment lock и сверяется с DBA-managed `v2_qualification_policies`, не из report. SQL повторяет configured operator allowlist (`v2_qualification_operators` + active owner/admin membership), exact locks, fixture/evidence policy и artifact metadata; INSERT immutable model_qualifications с `trusted_import=true` и audit/outbox. Policies/operators по умолчанию disabled и недоступны для mutation сервисным ролям; DBA включает их только после проверки внешнего корпуса, лицензии и issuer. Старые строки имеют `trusted_import=false` и не доказывают qualification. Existing passed row не изменяется; requalification создаёт новый row. `admission_enabled` на policy разрешается только у одной строки на operation/version; `photo.resolve_v2_qualification` отдаёт model и dataset SHA лишь при exact совпадении этой DBA-политики с ready `trusted_import` report данного tenant/project. Session Create/Update/Analyze дополнительно сверяет оба SHA с неизменяемым calibration artifact. Ни latest timestamp, ни произвольный passed row не выбираются. Команда не принимает flag skip-tests/force-passed. trusted config/SDK/model/ICC locks доступны read-only; ModelFamilySpec/SigningPolicy ordinary user не может подменить через artifact upload.
