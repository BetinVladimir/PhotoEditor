Масштабирование PhotoEditor
Кому: Владельцу и команде PhotoEditor
Автор: Codex
Дата: 30 сентября 2026
Тема: Архитектура роста и эксплуатация
Предмет решения
Как развивать PhotoEditor от одного узла с RTX 3060 до сервиса для нескольких студий, сохраняя качество обработки, изоляцию клиентов и управляемую стоимость. Меморандум определяет этапы роста, ресурсные ограничения, поведение при сбоях и критерии перехода. Он предназначен владельцу продукта и команде разработки для планирования инфраструктуры и реализации эксплуатационного контура.
Краткий ответ
Начать с одного вычислительного узла и измеряемых лимитов. Затем отдельно масштабировать API, CPU, GPU и хранение, сохранив PostgreSQL источником состояния, а объектное хранилище источником файлов. Добавлять узлы по очередям и фактической загрузке, а не по числу зарегистрированных пользователей. Шардирование БД оставить для подтверждённого узкого места.
Сохранение результата требует действующей аренды задачи, актуальных прав и согласий, проверки контрольных сумм и атомарного принятия результата сервером. Увеличение числа worker не должно менять эти правила. Пороговые значения ниже являются стартовой политикой и целями приёмки; подтверждённой производительности RTX 3060 и гарантированного числа обслуживаемых студий пока нет.
Исходные условия и источники
Исходное оборудование задано владельцем: RTX 3060 с 12 ГБ видеопамяти, 32 ГБ оперативной памяти и Ryzen 5600. Размер и скорость накопителей, сеть, резервное питание и фактически доступная память под нагрузкой не зафиксированы. До расчёта ёмкости их необходимо измерить. Все бюджеты в GiB означают двоичные единицы; advertised объём оборудования не заменяет показания runtime.
Архитектурная база — документация PhotoEditor v2.1 в docs/implementation-v2. Go обслуживает API и транзакции; Python workers выполняют вычисления; PostgreSQL хранит состояние; RabbitMQ доставляет задания; объектное хранилище хранит оригиналы и артефакты. Существующие Apply v4, WorkingImage, Canvas, TransformChain и проверки качества сохраняются.
Основные источники: 12-scale-product.md — этапы и бюджеты; 09-workflow-transactions.md — аренды, принятие результатов и финализация; 11-consent-lifecycle.md — согласия и удаление зависимостей; 03-database.md и work-packages.json — схема и порядок внедрения. Этот меморандум подробно развивает эксплуатационную часть. Предлагаемые структуры учёта ниже необходимо сопоставить с существующей схемой перед реализацией; они не означают, что новые таблицы уже созданы.
Анализ и проектные решения
1 Границы компонентов
Control plane принимает запрос, проверяет права, фиксирует входной snapshot, резервирует ресурсы и сохраняет граф задач с transactional outbox. Compute plane получает только объявленные входы и выполняет операцию. Data plane обслуживает файлы и проверенные выходы. Такое разделение позволяет увеличить GPU pool без переноса сессий API и без копирования локальных каталогов между серверами.
Единственный статус исполнения v2 workflow хранится в runs.status; тип запуска — v2. Дочерний Apply или export использует прежнюю статусную модель. Завершение планирования родителя не означает завершения обработки ребёнка. Интерфейс должен показывать оба этапа, иначе горизонтальное масштабирование создаст ложные сообщения об успехе.
Ни API, ни worker не публикуют результат только потому, что файл записан в storage. Результат становится доступным после проверки canonical result, attempt, fence, schema, digest, tenant lifecycle и согласий. Сообщения допускают повторную доставку; exactly once требуется для бизнес-эффекта через уникальный ключ и транзакцию, а не обещается транспортом.
2 Один узел и стартовые бюджеты
На RTX 3060 разрешён один одновременно исполняемый тяжёлый CUDA task. В GPU-памяти удерживается одна модель через общий ModelPool. Стартовый предел model plus activations — 9,5 GiB; при меньшем доступном объёме admission понижает доступную ёмкость, а не пытается занять весь номинал. Конкуренция независимых GPU-процессов без общей резервации запрещена.
Для CPU-фотоопераций начальная concurrency равна двум, threads на задачу — двум. Совокупный предел RAM для photo workers — 16 GiB; control plane — 8 GiB; оставшиеся 8 GiB отводятся ОС и кешу. Это общий бюджет узла, не лимит каждому контейнеру. Процессы архивирования, декодирования и подписывания также учитываются в общей памяти.
API допускает не более восьми одновременных тяжёлых процедур admission; сверх этого возвращает 429 с возможностью повторить запрос. По умолчанию tenant имеет до двух тяжёлых заданий в совокупности queued и running. Массовая загрузка фотографий не должна открывать неограниченное число compute reservations. Изменение лимита администратором записывается с revision и audit.
3 Расчёт памяти и временного пространства
Один RGB float32 буфер занимает width × height × 12 байт. Для 45 мегапикселей это 540 миллионов байт, примерно 515 MiB. Source, output, masks, encoder и промежуточные массивы существуют одновременно; оценка по одному буферу недостаточна. Memory mapping не гарантирует нулевой RSS и не освобождает от admission.
Базовый tile — 512 пикселей, halo определяется конкретной операцией. Вход и выход ограничены 200 мегапикселями до allocation. Для panorama и focus stack учитывать все активные tiles и промежуточные файлы, но не загружать полные исходники одновременно. Масштабирование стороны в четыре раза увеличивает число пикселей в шестнадцать раз.
Scratch резервируется до decode: worst-case размер одновременно живущих intermediates плюс 20 процентов. При свободном месте ниже 15 процентов новые scratch-intensive jobs не стартуют. Временные файлы именуются по run, task, attempt и fence. Cleaner удаляет только завершённые или просроченные unreferenced attempts; текущая lease и pinned history защищены от очистки.
При OOM текущий result fenced. Разрешён один повтор с меньшим tile, только если такой execution profile квалифицирован; новый profile фиксируется в provenance и cache key. Повторный OOM завершает задачу RESOURCE_EXHAUSTED. Нельзя незаметно сменить модель, precision или backend ради успешного статуса.
4 Очереди и справедливое распределение
Классы очередей: interactive, capture, batch, training. Начальные веса deficit round robin — 4, 3, 2, 1. Стоимость задачи равна max(1, estimated_gpu_ms / 1000); неизвестная стоимость оценивается в 1800 единиц. Счётчики deficit сохраняются между циклами диспетчеризации, иначе дорогая задача никогда не накопит право на запуск.
В каждом классе tenants обходятся циклически; внутри tenant действует порядок created_at и id. Неиспользованный deficit ограничивается конфигурацией, чтобы длительно отсутствующий клиент не забирал весь pool при возвращении. Для первой реализации предел накопления должен быть не меньше максимальной допустимой стоимости задачи; его значение фиксируется в scheduler policy и тесте starvation.
После десяти минут ожидания training повышается до batch. Batch не получает interactive приоритет только из-за возраста. Сходство с уже загруженной моделью помогает выбирать между равноправными задачами, но не позволяет бесконечно откладывать другую модель. GPU kernel не прерывается произвольно; cooperative checkpoint разрешён на квалифицированной границе tile.
Capture p95 до пяти секунд после готовности proxy — цель при свободном совместимом ресурсе. При занятой GPU интерфейс показывает queue wait отдельно от compute time. При возрасте QA задания более 30 секунд отчёт помечается задержанным; его нельзя выдавать за оперативное подтверждение качества текущего кадра.
5 Приём задания и резервирование
AdmissionBudget(plan, capacityPolicy) возвращает gpu_bytes, host_bytes, scratch_bytes, output_bytes, estimated_gpu_ms и execution_profile_hash. План оценивается после фиксации inputs, operation versions и моделей. Для зависимых стадий резервируется максимум одновременно исполняемого frontier, а не сумма памяти всех последовательных стадий; output storage учитывается по всем сохраняемым результатам.
ReserveBudget(run_id, expected_policy_revision, budget) выполняет атомарную проверку лимитов и запись резервации. Квота tenant и физическая ёмкость узла — разные ограничения. Output bytes и tenant budget можно закрепить при admission; host/GPU/scratch конкретного worker закрепляются при dispatch. Не удерживать GPU на всё время human review.
ReleaseBudget(run_id, terminal_key) идемпотентен. Сбой после commit, но до ответа клиенту не создаёт второй резерв при повторе того же ключа. Settler освобождает остаток и фиксирует фактическое использование только один раз. Reconciler находит orphan reservations по terminal runs и fenced attempts; возраст записи сам по себе недостаточен для освобождения живой задачи.
6 Структуры и методы эксплуатационного контура
CapacityProfile содержит node_id, hardware fingerprint, cpu_slots, gpu_slots, host_limit_bytes, gpu_limit_bytes, scratch_limit_bytes, disk watermark, policy_revision и qualified capabilities. WorkerHeartbeat содержит worker_id, node_id, observed_at, free/reserved bytes, active lease IDs, resident model SHA и состояние accepting, draining либо offline. Значения памяти — int64 bytes, timestamps — UTC; отрицательные значения запрещены.
TaskCostEstimate ключуется operation, version, backend, model SHA, execution profile и диапазоном пикселей. Он хранит sample_count, p50, p95, peak bytes и measured_at. EstimateCost использует p95 подходящего квалифицированного профиля; при отсутствии данных возвращает conservative unknown cost. Модель оценки не меняет quality profile задачи.
ResourceReservation связывает tenant, run, task attempt при dispatch, node, vector ресурсов и state reserved, active, released либо expired. Уникальный ключ содержит scope, run, task и attempt; переход release идемпотентен. UsageEntry содержит settlement_key, measured unit, quantity и canonical result ID. Один canonical result не может повторно начислить одну единицу учёта.
CanDispatch проверяет квалификацию, права, lifecycle, queue eligibility и все resource dimensions. AcquireLease атомарно назначает worker, attempt и fence. RenewLease требует совпадения worker, attempt и fence. AdoptResult повторно проверяет fence и согласия. BeginDrain закрывает admission узла для новых leases; FinishDrain ждёт нулевого active count либо явно fence оставшиеся задачи по timeout.
Эти структуры являются контрактами доменного слоя. Перед добавлением таблиц нужно проверить существующие task leases, quota ledger, worker registration и capability registry. Совпадающие поля расширяются миграцией существующего владельца данных; параллельный scheduler или второй независимый ledger не создаются. Новую миграцию резервировать после фактического head, не переиспользовать номера v2.
7 Несколько вычислительных узлов
Первый переход — вынести GPU compute на второй узел, затем при необходимости CPU и storage. API становится stateless и может работать в двух экземплярах за балансировщиком. Оба API используют одну авторитетную БД и одинаковые контракты; локальная память не хранит единственную копию draft, idempotency key или reservation.
Worker получает artifacts через gateway по exact digest. Локальный диск — только scratch и восстанавливаемый кеш. Пути вроде /tmp/frame.npy не передаются как межузловой контракт. Итоговый artifact публикуется через существующий fenced upload/adoption, а не копированием файла в общий каталог.
Heartbeat — каждые 10 секунд; через 30 секунд без heartbeat worker считается offline и не получает новых заданий. Lease обновляется каждые 10 секунд, timeout — 60 секунд. Offline не даёт права немедленно принять чужой late result или одновременно переиспользовать живую lease; новый attempt возникает после истечения или явного fencing старой аренды.
При сетевом разделении worker может закончить вычисление локально, но не подтверждает результат без сервера. Сервер принимает только действующий fence. Время аренды определяет БД, а не часы worker. После восстановления соединения устаревший результат отклоняется, а staging очищается по TTL и ссылкам.
8 Масштабирование по метрикам
Кандидат на увеличение pool возникает, если oldest eligible wait превышает 30 секунд три минуты подряд либо reserved utilization превышает 75 процентов пять минут подряд. Eligible означает наличие выполнимой задачи: ожидание отсутствующих весов, согласия пользователя или недоступного source не запускает покупку GPU.
Контроллер сначала проверяет максимальное число узлов, бюджет, доступность нужного model bundle и storage throughput. Решение фиксируется с причиной и policy revision. Один незавершённый scale action на pool предотвращает лавину параллельных запусков. Новый worker допускается после readiness, проверки модели и qualification, а не после самого старта процесса.
Уменьшение допускается после 15 минут idle. Узел переводится в draining, перестаёт получать leases и завершает активные задания. Если deadline истёк, применяется явный fence и допустимый retry; файлы scratch не удаляются до фиксации этого решения. Минимум один пригодный worker нужной capability сохраняется, если capability объявлена доступной.
При собственном оборудовании контроллер может только включать подготовленные узлы или выдавать оператору capacity event. Автоматическая аренда облачных GPU требует отдельного provider adapter, credentials и финансового лимита. В базовый запуск она не включается неявно.
9 Хранилище и передача данных
Пропускная способность ограничена минимумом из decode, GPU, object read/write и сети. Нужно измерять объём чтения и записи на одно успешно обработанное фото, cache hit rate и конкуренцию upload с export. Добавление GPU при насыщенном storage увеличит очередь I/O и стоимость простоя.
Оригиналы private; derivative выдаётся через авторизованный intent с ограниченным сроком действия. CDN допустим для разрешённых вариантов выдачи с учётом политики доступа. Public URL по угадываемому SHA не используется. Ревокация запрещает выдачу новых ссылок; уже скачанные внешние копии технически не отзываются.
Cache key включает tenant namespace, source SHA, canonical params SHA, operation/renderer versions, model lock, runtime/backend qualification и precision. Повторное использование кеша проверяет lifecycle и согласия. Eviction удаляет только воспроизводимые и не закреплённые refs; удаление кеша не удаляет originals или approved history.
Capacity forecast включает originals, previews, immutable drafts, exports, models, backup versions и свободный резерв. Для временных upload и failed staging действует отдельный TTL cleaner с проверкой живых attempts. Scratch volume и durable bucket могут иметь разные сроки хранения; их нельзя очищать одной общей age-based командой.
10 База данных и очередь сообщений
Первый способ роста БД — измерить запросы и блокировки, добавить нужные индексы, уменьшить длинные транзакции и ограничить pagination. Поиск причин основан на lock wait, slow queries, connection saturation и WAL rate. Сетевые вызовы и обработка изображения не выполняются внутри SQL transaction.
Replica может обслуживать галерею, если интерфейс допускает задержку. Авторизация, CAS, квоты, admission, согласия, snapshots и finalizer читают primary. После сохранения интерфейс получает подтверждённую revision из primary, а не показывает более старую копию с replica.
Partitioning подходит для крупных append-only журналов, но требует совместимости unique keys, FK и purge. В PostgreSQL нельзя предполагать сохранение глобального UNIQUE без учёта partition key. Перед переносом нужны отдельная миграция, backfill, dual-read validation и план переключения. Mutable task leases не разделяются по времени только ради сокращения размера таблицы.
RabbitMQ доставляет уведомления о работе; потеря сообщения восстанавливается outbox/reconciliation. Сбой API после фиксации TX не теряет задачу. Повторная публикация безопасна благодаря inbox/idempotency. Рост очереди измеряется возрастом runnable jobs в БД и transport lag, а не только числом сообщений брокера.
11 Отказоустойчивость и границы доступности
Два API и несколько GPU повышают устойчивость compute, но не устраняют единую точку отказа PostgreSQL, broker и storage. Для обещания повышенной доступности нужны независимые failure domains, проверенное переключение primary и восстановимые данные. Backup сам по себе не обеспечивает непрерывную работу.
На single-node этапе допустим перерыв обслуживания при отказе хоста; это должно отражаться в обещаниях пользователю. На следующем этапе compute-узлы не должны одновременно зависеть от одного неисправного scratch volume. Потеря одного GPU снижает ёмкость pool; система ограничивает admission, а не начинает неквалифицированную обработку.
Проверки отказов включают остановку worker во время decode, model load, upload и adoption; потерю broker; сетевую изоляцию; restart API после commit; заполнение диска; revoke consent при активном compute. Ожидаемый итог — один принятый результат, отсутствие двойного начисления и сохранение исходников.
12 Согласия и жизненный цикл
Для каждого обучения и зависимого рендера закрепляются consent_id и epoch. Revoke увеличивает epoch, отключает связанные active versions, отменяет зависимые runs и запускает cleanup. Перед adoption и activation проверка повторяется под согласованными блокировками. Межузловая задержка кеша не может разрешить результат со старым epoch.
Cleanup ledger содержит pending, deleting, deleted и blocked_shared. Shared artifact удаляется только после освобождения всех независимых refs; состояние blocked_shared видно оператору. Обычные фото и ранее утверждённые exports не исчезают только из-за отзыва согласия на обучение: это отдельные команды удаления.
Tenant purge остаётся forward-only и выполняется finish_tenant_deletion после подтверждённой очистки object storage. Новые capacity/audit records с tenant references включаются в purge и retention по своей роли. Никакого общего DELETE для API или worker; права функции ограничены явным allowlist.
13 Локальная студия и размещение данных
Для каждого tenant или явно изолированного project назначается один authoritative appliance/region. Originals, face embeddings, training artifacts и signing keys остаются в выбранном контуре. Центральная панель получает health и агрегированные counters без изображения, person IDs и персональных метаданных.
Студийный agent хранит SQLite journal upload и локальные правки. Он продолжает наблюдение за папкой при отсутствии сети, но не подтверждает server approval или consent офлайн. При reconnect использует sequence, SHA, Idempotency-Key и CAS; конфликт версии предъявляется пользователю, а не разрешается silent overwrite.
Перенос проекта выполняется frozen bundle с manifest, digests и явной проверкой прав. Импорт создаёт новые IDs и revoked consents. Автоматическая двусторонняя синхронизация двух независимых источников истины в v2 не вводится. Будущая межрегиональная репликация требует отдельного решения по conflicts, residency и deletion propagation.
14 Учёт стоимости и ограничение расходов
Разделить infrastructure cost и пользовательское начисление. Фактический GPU time failed attempt нужен для оценки расходов, но не означает успешную услугу. За неполученный output не начисляется successful-output usage. Повторный canonical result не увеличивает счётчик; terminal settlement имеет уникальный ключ.
Единицы учёта — byte-days хранения, bytes успешной выдачи и измеренные GPU milliseconds. Себестоимость серии оценивается как compute cost плюс storage retention, egress, CPU и доля постоянной инфраструктуры. До измерений нельзя обещать цену обработки по одному только объёму VRAM.
Для расчёта GPU capacity использовать N ≥ ceil(λ × t / U), где λ — tasks в секунду, t — среднее GPU-время задачи в секундах, U — целевая доля загрузки меньше единицы. Формула оценивает среднюю ёмкость, но не доказывает p95 latency; burst, model switching и retry учитываются нагрузочным тестом.
Иллюстрация, не benchmark: при 600 задачах в час, 10 GPU-секундах на задачу и U=0,7 требуется ceil(600 × 10 / 3600 / 0,7)=3 GPU slots. Реальные λ и t нужно получить на своём pipeline. Платёжный провайдер, тарифы и автоматическое списание не входят в этот эксплуатационный план.
15 Наблюдаемость и действия оператора
Metrics включают queue wait, execution time, model load, upload/adoption lag, OOM, stale fence, retries, admission rejects, output bytes, scratch reservations, purge/cleanup lag и protected-pixel failures. Разрезы — operation, version, resource class и квалифицированный profile. Tenant/person IDs не используются как высококардинальные metric labels; детализация доступна в защищённом audit.
Trace связывает request, run, task, attempt и artifact. Logs не содержат raw prompt, email, GPS, nonce или key material. По каждому terminal failure доступны reason code, runtime/profile hash, стадия и факт освобождения резервации. Это позволяет отличить нехватку ресурса от дефекта алгоритма.
Стартовые alerts: heartbeat отсутствует 30 секунд; queue age больше пяти минут; outbox lag больше 60 секунд; disk free ниже 15 процентов; oldest consent cleanup старше суток; неуспешный restore drill. При alert оператор сначала ограничивает новые admission затронутого класса, затем проверяет lease и storage, и только после этого повторяет задачи. Массовый retry без диагностики запрещён как причина повторной перегрузки.
16 Резервное копирование и восстановление
Ежедневный base backup PostgreSQL дополняется непрерывным WAL архивом; object manifests и версии storage сохраняются согласованно с retention. Ключи имеют отдельную encrypted backup и audit доступа. Проектные цели RPO не более 15 минут и RTO не более четырёх часов подтверждаются реальным восстановлением, а не фактом успешного backup job.
Восстановление выполняется при paused scheduler и закрытом admission. Сначала выбрать recovery point, восстановить БД и keys, затем сопоставить artifact refs с объектами и их digests. Отсутствующие объекты не помечать ready; восстановление должно завершиться явным reconcile report. После проверки replay outbox допускается идемпотентно.
Deletion tombstones и consent revocation journal сверяются с наиболее свежим доступным защищённым журналом. Если актуальность журнала не доказана, affected tenant остаётся заблокированным до разрешения расхождения. Нельзя открыть старый backup так, чтобы удалённые tenants или отозванные модели снова стали доступны.
Раз в квартал выполнить restore drill в отдельной среде: recovery time, фактическая потеря данных, refs/objects reconciliation, отсутствие resurrection и smoke tests старого Apply и v2. Только после этих проверок включаются writers, затем scheduler, затем внешняя выдача. Результат drill хранит commit, snapshot IDs, timestamps и протокол проверки.
17 Порядок внедрения и миграции
Шаг S0 — зафиксировать baseline: hardware/runtime fingerprints, существующие quality tests, migration head и representative corpus. Шаг S1 — реализовать resource estimates, reservations, fairness и metrics на одном узле. Принятие S1 требует bounded memory, корректной отмены и доказанного отсутствия regression качества.
Шаг S2 — подключить второй worker к общему control plane, проверить remote artifact gateway, leases, late results и drain. Шаг S3 — обеспечить capacity policy, autoscale decisions и лимиты расходов. Шаг S4 — при необходимости повысить отказоустойчивость БД, очереди и storage; compute scaling сам по себе не считается выполнением S4.
Изменения БД идут expand, backfill, validate, switch. Сначала deploy compatible binaries с flags off, затем migration и grants, потом mixed-version tests, и лишь затем включение tenant cohort. Contract changes сохраняют совместимость старых runs. Откат сервиса означает flags off и drain; применённые forward-only migrations не откатываются DROP-командой.
Шардирование относится к отдельному будущему шагу S5. Placement directory хранит tenant home shard; вся транзакция tenant выполняется там. Миграция tenant требует freeze writes, копирования metadata и refs, проверки digests, переключения placement revision и fencing старого маршрута. Cross-shard workflow не допускается. До выявления bottleneck этот шаг не является обязательным.
18 Приёмка и решение о расширении
Benchmark включает cold и warm model starts, смешанные preview, capture, batch, export и training; серии разного размера до лимита snapshot, реальные RAW и большие outputs. Для каждого сценария фиксировать входные SHA, model/calibration lock, runtime, queue policy, peak RAM/VRAM/scratch, p50/p95 и ошибочные/unsupported случаи. Сравнение выполняется с текущим quality baseline на тех же inputs.
Этап A принимается, когда пределы памяти соблюдаются и повторяемая нагрузка не нарушает качество, квоты и отмену. Этап B — когда принудительное падение одного узла не создаёт двойного adoption, starvation tenant или потерю оригиналов. Этап C — когда load test выявил конкретное ограничение DB/storage, предложенная оптимизация его устранила и restore/purge продолжают работать.
Каждый пакет сдаётся с commit, migration head, contract hashes, командами и результатами тестов, устройствами и dataset hashes. Mocked model не доказывает image quality, а static schema validation не доказывает успешную migration. При отсутствии реального оборудования или моделей статус — awaiting_evidence, а capability не объявляется готовой.
Заключение
Рекомендуется сначала реализовать и измерить этап A на имеющемся оборудовании, затем добавить второй compute-узел при устойчивом росте runnable очереди. Следующий шаг выбирается по измеренному bottleneck: GPU, CPU, storage, сеть или БД. Покупка дополнительных GPU оправдана только если остальной контур способен их обслужить.
Владелец продукта утверждает допустимое ожидание и предел расходов; backend-команда отвечает за leases, quotas и lifecycle; команда image processing — за qualification и неизменность качества; оператор — за capacity, backup и восстановление. Конкретные исполнители и календарные даты назначаются при планировании этапа. До включения каждого этапа обязательны evidence report, rollback через flags/drain и проверка восстановления.
