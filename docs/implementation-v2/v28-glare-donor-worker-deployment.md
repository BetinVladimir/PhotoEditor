# V28 donor glare worker installation

`portrait.glare` donor mode is unavailable by default. Install it only on a GPU-class worker explicitly using the `cpu` backend. This resource class is the task scheduling contract; donor patching itself remains CPU-only.

Required operator configuration:

- `PHOTO_MODEL_ROOT` and `PHOTO_MODEL_LOCK` containing an approved, byte-verified `glare_mask` entry with `passed` CPU backend; `PHOTO_GLARE_DONOR_MODEL_LOCK_SHA` must equal the ModelLock `lock_id`.
- `PHOTO_GLARE_DONOR_ENABLED=true`, `PHOTO_GLARE_DONOR_RUNTIME_LOCK` (absolute canonical file), and `PHOTO_GLARE_DONOR_RUNTIME_SHA`. The glare runtime lock covers donor and glare source bytes, package versions, CPython version and machine. Use `photo-worker verify-glare-donor-runtime PATH EXPECTED_SHA` to inspect local identity; its `qualification: not_measured` output is not a passed model/corpus report.
- `PHOTO_GLARE_DONOR_MATERIAL_SCRATCH_ROOT`, `PHOTO_GLARE_DONOR_MATERIAL_MAX_BYTES` and optional `PHOTO_GLARE_DONOR_ALPHA_MODE` (`require_float32` or `normalize_uint16`). The material limit must fit the worker's total scratch budget.
- The existing `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` and optional `S3_REGION` for exact-version input reads.

Startup verifies both locks, the local model bytes and backend, the runtime inventory, and worker-only SQL functions from migrations `01895`, `01896`, `01933` and `01934`. Each donor-mode task rechecks the leased SQL authority, server-issued DonorConfirmation source/face binding, exact glasses/protected masks and strength, current consent and qualification before donor bytes are read and again before result handoff. Input locations are obtained only through `v28_glare_donor_input_evidence` for the current attempt; the reader verifies exact version, length and SHA.

Migration `01938` adds a scheduler-only read-only ticket for uncertain graph-seal commits. Recovery compares the canonical original Params proposal excluding the server-issued confirmation ref, verifies the proposal placeholder ID against the document owner ID and the final Params ref against the separately allocated document artifact ID and digest, then checks the compiled resource/qualification profile, project, shoot session, input snapshot, both selected observation IDs, deterministic task ID, current tenant/session/consent, immutable `v28_restoration` draft intent and the sealed graph before returning the historical queued receipt. A changed request must not reuse the run's ticket. This migration and its Go unit test have been written but have not been executed. Public route wiring and full-module acceptance remain open.

`NewSQLGlareDonorRestorationCoordinator` now assembles the scheduler-only confirmation/Params/transport publishers and separate editor-role catalogs for the exact base and donor asset versions. `Admit` rejects a project or base/donor version mismatch before SQL or object IO. The HTTP route still needs wiring to the trusted draft beginner and a server-owned qualification source before it can call `Admit`; it must not accept a run, pin or catalog version merely because the client supplied it.

Migration `01939` and `SQLGlareDonorDraftBeginner.Begin` create the required empty V2 preview draft before confirmation/Params publication. The deterministic run/workflow, original proposal digest, project, snapshot, shoot, selected observations, base/donor versions and qualification pin are immutable in the run config. The proposal confirmation owner placeholder must equal the deterministic `portrait.glare` task ID for its workflow and ordinal; Go rejects a mismatch before database IO and migration `01939` repeats the check. SQL receives the exact proposal bytes and recomputes its digest and version binding; it rechecks editor/session/snapshot/qualification and quota, and an exact pending replay retains one reservation. This is a draft-only step: the API must use server-derived key, pin and snapshot, then call the coordinator and return its verified admission ticket. The migration and Go unit test are authored but unexecuted.

`GlareDonorRestorationSubmitter.Submit` now orders sealed-ticket recovery, empty draft begin and full coordinator admission. It rejects a begin result with different deterministic run/workflow or catalog versions before publication. `NewSQLGlareDonorRestorationSubmitter` composes these steps with separate scheduler/editor pools. The API deployment supplies actor/session from authentication and qualification/profile/reservation from operator configuration; production enablement still requires model/corpus qualification and full lifecycle acceptance.

The project API now exposes `POST /api/v1/tenants/{t}/projects/{id}/glare-donor-intents` with `Idempotency-Key`. The JSON body contains only `schema_version`, `shoot_session_id`, `snapshot_id`, `ordinal`, `params_proposal`, `source_observation_id` and `donor_observation_id`; unknown or noncanonical fields are refused. The authenticated middleware supplies actor/session. `PHOTO_V28_GLARE_DONOR_CONFIG` is an operator-owned canonical JSON document with `schema_version:1` and `projects[]` entries containing `tenant_id`, `project_id`, `qualification`, `base_profile`, `reserved_bytes`, `license_cleared:true`. `V28_GLARE_DONOR_SCHEDULER_DATABASE_URL` supplies a separate scheduler pool. Absent configuration keeps the route unavailable; startup rejects missing required SQL migration functions. Runtime/model qualification and full photographic acceptance remain prerequisites to setting this configuration in production.

Migration `01943` adds paginated manual-mask pair discovery. It joins the target MaskRef, protected MaskRef and both physical pixel artifacts from the same succeeded `mask.rasterize` task, then requires `v28_manual_pair_origin` for the current snapshot and base binding. The API exposes `/glare-mask-pairs`; Go and client decoders require all four distinct pinned refs. This produces complete selectable pairs rather than mixing independent masks.

Migration `01942` adds a bounded source-observation catalog for the selected accepted frame and V2 snapshot. It returns only confirmed observation IDs and exact face-evidence refs when one current identity-matching grant exists. The API exposes `/glare-source-candidates`; `OwnerAPI.glareSourceCandidates` validates each page. The picker can now choose an observation rather than require its UUID from manual input.

Migration `01941` adds bounded, scheduler-only discovery of confirmed same-person donor observations from the selected shoot. It verifies current editor/snapshot scope, source version, ready face evidence and exactly one active identity-matching grant; responses contain donor asset/version/source and observation refs, without exposing person or consent IDs. `GlareDonorSubmissionService.ListCandidates` and `OwnerAPI.glareDonorCandidates` enforce typed pagination and digest checks. The caller must obtain each donor canvas binding through the existing version API and check that its version/source match the candidate before preparation. Candidate discovery is a choice list, not admission authority. `EditorGlareDonor` now appears in the V2 editor. It creates a scoped snapshot, lists shoot sessions, loads source observations and manual mask pairs, then loads same-person donor candidates for the selected source. Before confirmation it resolves the selected donor asset through `v2Binding` and checks exact version/source. It then passes the frozen selection to `GlareDonorControls`; an existing journal is recovered without creating a new snapshot. UI, API and SQL paths are authored but not yet executed or visually qualified.

Migration `01940` and `ReadGlareDonorPreparationProof` provide a scheduler-only read of current face choice, consent proof and qualification before a draft run exists. They require an active editor session, live V2 snapshot, confirmed same-person observations, matching source/donor versions and current donor session locks. The Go reader canonicalizes and verifies the proof and derives its digest for a proposal; this read grants no publication authority, and issuer/submit still recheck. The project API now exposes `POST /api/v1/tenants/{t}/projects/{id}/glare-donor-preparations` with the same `Idempotency-Key` later used for submission. The client selects source/donor bindings, confirmed observations, masks and mask pixel refs; the server derives the deterministic confirmation owner, operator model/calibration pin and live proof digest, then checks manual-mask producer lineage. It returns a canonical authored intent without creating a run. Submission repeats all live checks. The editor picker is wired through these catalogs, but its tests and visual acceptance have not been run.

The photographer client now has `OwnerAPI.submitGlareDonor`, strict authored-intent/ticket parsing and an exact-body idempotent attempt journal. The journal persists before send, keeps an ambiguous attempt for verbatim replay, refuses changed requests and clears on logout. The client also exposes `OwnerAPI.prepareGlareDonor` and validates that the returned proposal retains the exact selected inputs. `GlareDonorControls` now coordinates preparation, journaled exact-body submission, ambiguous retry and workflow-ticket verification for a supplied selection. The editor exposes donor-glare selection and controls; it must call preparation with the same idempotency key before submission and must not fabricate confirmation or qualification from UI state. This remains a V28 implementation gap, not a passed screen.

The existing DonorConfirmation issuer was built for open-eyes Params. `OpenEyesConfirmationService.IssueGlareParams` derives face IDs from pinned source/donor observation documents and returns canonical final glare Params with the owner placeholder replaced by the separately allocated confirmation document ID and digest. Where pre-issuer face documents are not yet catalog-authorized, `OpenEyesConfirmationService.IssueGlareParamsFromObservations` calls `ReadGlareDonorFaceChoice` and migration `01937` to resolve IDs from confirmed observations only after the existing donor proof builder verifies the current run, consent, shoot session, source versions and evidence refs. Both paths then publish the confirmation in the same draft run and recheck the selected observations after object IO. Accepting face IDs directly from the request is forbidden. `SQLRestorationParamsPublisher.PublishDonorGlare` saves an immutable prepublication intent, publishes the returned Params through the dedicated `RestorationPortrait` object route and rechecks the intent. Migrations `01935` and `01936` bind reserve/replay/complete to the same draft run, manual mask producer, current qualification, donor proof and actor session. `BuildRestorationInputInventory` derives the complete direct and physical input list from the verified source/donor/mask documents. `GlareDonorRestorationCoordinator.Admit` composes these steps, recompiles under live authority, publishes/registers transport and seals the graph. The endpoint must still supply a current draft run/workflow/snapshot and production SQL/object/catalog dependencies, and its restart path must distinguish an uncertain seal commit from a new submission. The worker SQL gate requires the same-run issuer context. Real donor photographic/corpus qualification is still required before the feature is considered available. No model weights, qualified report, applied migrations or deployment evidence are included in this repository.
