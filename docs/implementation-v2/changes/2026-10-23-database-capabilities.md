# Общая миграция БД и исправление доступности функций

Дата: 2026-10-23. Статус: нормативный план доработки; не свидетельство выполнения.
Основание: пользователь потребовал общую миграцию всей БД без сложного ручного версионирования.
Этот документ заменяет требования отдельных установщиков и двойного direct-SQL/Goose-применения из временных work-пакетов для данного изменения. Полный объём V20–V32 сохраняется.

## Результат

Один штатный запуск мигратора создаёт новую БД либо обновляет существующую до текущего состояния. Необходимые таблицы, функции, ограничения, индексы, политики и права применяются всей цепочкой. Оператор не выбирает номера миграций, версии функций, PID worker или манифесты отдельных объектов. После успешного применения запускается совместимый API и клиент.

Существующий механизм уже находится в backend/cmd/photo/main.go: роль migrate → ValidateBundle → goose.Up по embedded backend/db/migrations → ValidateInstalledSecurity. Его нужно использовать, а не создавать дополнительный release-установщик для 02660. Секрет DATABASE_URL поступает из существующего окружения/секретов, не из документов или журналов.

Команда для заранее собранного штатного backend-бинарника photo:

```sh
PHOTO_ROLE=migrate ./photo
```

DATABASE_URL должен быть настроен заранее. Путь к бинарнику определяется действующим compose/образом. В production используется тот же бинарник и набор embedded миграций, который прошёл проверку. Эта команда не выполняет рестарт API и не заменяет сборку/развёртывание приложений.

## Правила миграции

1. Goose-журнал остаётся техническим учётом применённых изменений; ручное управление им запрещено. Повторный запуск без новых миграций не меняет данные и не добавляет записи применения.
2. Применённые исторические файлы не переписываются. Исправления добавляются forward-only. Номер 02660 является очередным файлом общей цепочки, а не отдельной процедурой установки.
3. CREATE OR REPLACE применяется для совместимых изменений функций. Изменение RETURNS в PostgreSQL требует отдельного совместимого объекта либо контролируемой замены зависимостей; нельзя обещать универсальный CREATE OR REPLACE для любой схемы.
4. Подготовленная 02660 добавляет photo.tenant_capabilities_versioned(). Историческая photo.tenant_capabilities() сохраняется для совместимости. Новый объект является внутренней деталью этой миграции; оператор его отдельно не устанавливает и не выбирает.
5. Существующие данные, роли, tenant isolation, qualification, worker registrations и включение операций не изменяются этим исправлением. Нельзя автоматически включать AI-функции или переписывать старые задачи.
6. Мигратор должен возвращать ненулевой код при ошибке. Проверки bundle/security обязательны. После неудачного запуска API с несовместимой схемой не запускается. Goose выполняет цепочку по миграциям; атомарность всей многолетней цепочки одной транзакцией не предполагается.
7. Нельзя добавлять ручное подтверждение каждого объекта, отдельные launch-пакеты по номеру БД или привязку установки к PID worker. Контрольные снимки и receipts служат тестированию и аудиту, а не второму механизму установки.
8. Операция удаления/изменения RETURNS не должна использовать CASCADE без явного описания зависимостей. Этот пакет не содержит destructive replacement и не меняет правила purge.

## Обнаруженный дефект

На фактической MAIN2659 API capabilities вернул 117 строк. render.compose присутствует для версий 1 и 2, но историческая SQL-функция и DTO не передают версию и объединяют evidence по имени. Это допускает перенос доступности одной версии на другую. Дополнительно прежний реестр из 114 идентичностей не включал region.authored_crop, render.authored_geometry, render.authored_segment.

Актуальный scope: docs/implementation-v2/current-operation-scope-2026-10-23.json, 117 идентичностей, из них 109 product. Число идентичностей не равно числу версионных строк API или числу принятых функций. Старые 114 записей сохранены.

Пример wire-строки:

```json
{"operation":"render.compose","operation_version":"2","resource_class":"gpu","model_id":null,"supported_backends":["cpu"],"available_backends":[],"available":false,"status":"unqualified","reason":"no_qualified_worker"}
```

Названия версии в API нужны машинам для безопасной совместимости. В пользовательском UI нет переключателя версий. Старые данные и текущие producer определяют контракт, а не строковое сравнение номеров.

## Открытая граница region.authored_crop

Есть canonical producer/installation config и фактическая строка registry, но полноценная регистрация и worker runtime-цепочка не подтверждены. В 02660 функция остаётся unavailable даже при рекламировании имени worker. Это честный временный отказ, а не завершённая реализация. Отдельная доработка должна замкнуть registry → handler → квалификация → обычный task execution → принятие результата; после неё соответствующий допуск меняется новой общей миграцией и тестами.

## Порядок работ

1. Завершить ревью подготовленного SQL/API/клиентского пакета; проверить все call sites на соответствие producer version.
2. Перенести согласованные изменения в основной код с проверкой отсутствия посторонних правок.
3. Адаптировать SQL fixture: не применять 02660 внутри pytest и не требовать head2659; тест получает полностью мигрированную текущую БД. Прямое исполнение SQL не заменяет штатный Goose-путь.
4. Собрать штатный мигратор из текущего полного набора миграций. На отдельной чистой БД выполнить всю цепочку одной штатной командой и тесты из соседней матрицы. На другой отдельной БД проверить обновление 2659 → current и повторный запуск.
5. После успешных проверок выполнить ту же штатную команду на целевой БД в согласованном окне и развернуть совместимый API/клиент. Не выполнять будущие тестовые fixture на целевой БД.
6. Получить фактический versioned capabilities и отчёт V20. Проверить отсутствие ambiguous duplicate pairs и переноса readiness. Зафиксировать результаты текущей сборки.

## Граница готовности

Готово только при полном прохождении матрицы тестов: чистая установка, upgrade, повтор, безопасность, версия evidence, реальный API, клиентские сценарии и отчёт. Только collect SQL cases, offline mock PASS или установленная функция без работающего API не закрывают изменение. Все остальные пункты V20–V32 остаются в цели.
