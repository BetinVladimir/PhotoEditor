# V23 learning.evaluate installation

## Current sensor-dust implementation (source authored, NOT RUN)

The frozen reviewed sensor-dust path is now connected from event-owned evidence
through the pinned holdout provider to production Telea repair on each of the
three independently rendered arms. The path requires the exact reviewed
selection, Params, source binding and protected-pixel restoration; it refuses
simultaneous reviewed defects, denoise and upscale. A signed Evaluate
qualification must explicitly include the restoration.sensor_dust effect and
digest-bound reviewed_sensor_dust quality evidence. A color-only report refuses
the dust arm before rendering. These source changes and authored unit tests
have not been run, and no CUDA quality proof has been issued. Historical
paragraphs below that call dust unconnected describe the earlier state.

The installed Python source-tree digest keeps the existing path/length/content
hash format, but the verifier now refuses symlinked Python files and package
directories, reads each file through no-follow directory descriptors and caps
each file at 8 MiB and the whole tree at 128 MiB. A package changed after the
qualification was signed must be rejected before Evaluate is installed. The
dependency lock is also re-read through a no-follow descriptor with an 8 MiB
limit on every qualification check. The new refusal cases are authored but
remain unexecuted in the code-first phase.

Development worker build/run accept `learning_evaluation_installation=LearningEvaluationInstallation(provider, verify_runtime)`. This is an explicit dependency, not inferred from model presence or environment booleans. Worker class must be gpu, backend cuda, matching the current frozen evaluate profile. Existing Metal verification policy does not silently change that profile.

The provider owns renderer_version v2.2, model_lock_sha, icc_lock_sha and the complete `render` context-manager implementation. Its actual runtime/renderer/detector/verifier qualification must be checked by verify_runtime, which returns None on success and raises on failure. False/True are not qualification receipts. Renderer/model/ICC/method drift refuses installation or execution; task drift becomes CONFIG_INVALID. Checks run before artifact IO and across provider entry, measured evidence consumption and exit. Startup validates shape and pins; it does not establish full algorithm acceptance.

The current PinnedColorHoldoutProvider implements aligned color/local/region stages, production portrait beauty with pinned Face19 skin and recovered FAN confidences, optional explicitly installed SCUNet denoise, and keep/solid/transparent/blur backgrounds with source protection. Blur requires explicit pinned depth installation. Reviewed `defects.repair@1` can run only when Evaluate carries the event-owned immutable review evidence and the exact producer/selection/Params/protection closure; the same accepted repair is applied before all three color arms, with protected source pixels checked again at the renderer boundary. Geometry, upscale, generative backgrounds and other unconnected effects still refuse. Reviewed dust requires its frozen evidence and a separately signed qualification effect. Do not label it a qualified complete renderer or enable it merely because weights are present. A production installation must cover the full frozen style/document contract and pass later qualification. No synthetic skin, face confidence, consent or identity pass is allowed.

Authored unit/platform scenarios cover explicit registration, absent installation, wrong worker class before TLS, run forwarding, malformed locks/backend/renderer/verifier, runtime pin changes, provider open/close mutation and pre-artifact refusal. NOT RUN. Models, CUDA/Metal, database migrations and end-to-end learning activation are not qualified by these source changes.

Production CLI enablement requires a deployment-owned qualification proof. The proof must bind the exact `v2.2` renderer/source hash, required detector and identity-verifier hashes, model lock, ICC lock, CUDA device/runtime identity, supported effect set, resource envelope and passed real-image safety/quality checks. The verifier must authenticate its issuer and exact report bytes from a trusted deployment source, reject expiry or pin drift, and be rechecked during each task. A boolean environment flag, model-file presence or `Calibration.qualified` alone is insufficient. The installer must refuse a frozen case whose enabled effect lies outside the qualified effect set, even when the source renderer supports that effect. The existing Metal code-check profile does not imply CUDA production qualification.

The proof reader is `operations/learning/qualification.py`: it verifies a detached Ed25519 signature with a deployment-supplied trusted raw public key over exact canonical report bytes, report expiry, model/ICC pins, the complete installed `photo_worker` Python source tree, an external package lock, CUDA device tuple, VRAM ceiling, allowed effects and mandatory check IDs. Effect-specific checks are required for reviewed defects, reviewed sensor dust, denoise, blur depth and asset decoding. The report is never generated or self-signed by the worker. This source does not by itself qualify any model or image pipeline. Its unit source is authored and unexecuted.
Each signed check is `{id, passed: true, evidence_sha}` with a physical-evidence digest, not a bare check name. Signed metrics must show positive baseline loss, candidate/baseline loss ratio at most 0.9, nonpositive rendered color p95 delta and clipping delta, zero protected-pixel error and identity failures, and at least two holdout sessions and ten examples. These are qualification-fixture measurements, not a replacement for per-training-run Evaluate or human safety review. A trusted issuer must publish and sign the underlying evidence; the worker only validates report structure, signature and installed-runtime binding.
The worker also requires `PHOTO_LEARNING_EVIDENCE_ROOT`. Each signed digest must have a bounded local `<sha256>.json` file there with matching physical bytes; files are rehashed during every runtime verification. Missing or modified evidence removes the qualification. Physical hash equality does not independently rerun the signed real-image experiments.
The `real_images` evidence file is a canonical document with exact signed metrics and one `{sha256, session_id}` entry per holdout frame. Its sample count and distinct session count must equal the signed metrics, source image hashes must be unique, and the canonical sample-list digest must equal the signed `dataset_sha`. This binds qualification numbers to a concrete frozen holdout inventory. The trusted issuer remains responsible for proving those hashes correspond to real photographs and measured renders.
Evidence files are opened relative to one no-follow directory descriptor, checked as regular files on the opened descriptor and read under an enforced 8 MiB bound. Replacing the configured evidence root between validation and opening refuses instead of following a new directory; replacing it during the read fails the final device/inode check. A symlink or file replacement cannot turn the preliminary size check into an unbounded read. This is source-only until the deferred runtime tests execute.

The explicit `LearningEvaluationInstallation` optionally carries that verified proof. Its provider wrapper checks model/ICC equality and expiry, derives the effects actually requested by the three frozen arms, and refuses any effect outside the signed set before calling the renderer. The explicit installer remains available for development and component verification. Production build_worker accepts only SignedLearningRequest, preventing a direct unsigned installer from bypassing deployment qualification.

`operations/learning/qualified_installation.py` implements the explicit factory. It reads the actual current CUDA device, repeats the signed report/source/package/ICC checks and verifies every required approved CUDA model file against the installed lock. For `restoration.denoise` and `background.blur`, the report must contain exact nonzero VRAM provider peaks with RAM/scratch/output bounds and effect-specific quality checks. The factory creates `NativeDenoiseProvider` and `HoldoutDepthProvider` on the existing ModelPool from those signed peaks, or validates equivalent explicitly supplied providers. Their verifier repeats the signed runtime checks before and after native use. No peak is inferred from model presence.
The Evaluate compiler reserves 10,000,000,000 VRAM bytes in the sealed task profile for the current target hardware. The signed provider refuses a task whose `resource_estimate.vram_bytes` is below the report's measured `peak_vram_bytes` before artifact IO. A report above this envelope cannot run on this profile; future device-specific scaling requires an explicit compiler/profile change with capacity evidence. The SQL stage range already permits this value. This code path has not been measured on CUDA or Metal.
The compiler also reserves 1 GiB RAM and 1 GiB scratch for one sequential native denoise/depth provider above the existing holdout buffers. The signed report refuses a provider peak above either reserve or any provider `output_bytes`, because these intermediates remain inside the task scratch rather than a separate published output. The worker's own denoise/depth admission still computes full image-size and halo costs; the signed peak is added there. This reserves resources for the reported model without inferring a smaller peak from model presence.
For `background.asset`, the signed factory supplies a decoder verifier when the signed report includes the `asset_decoder` check and effect. That callback repeats the full signed runtime check before and after the pinned background decode; physical source/ICC/resource validation remains in `normalize_frozen_background`.

The regular CLI now accepts only a complete qualification set: `PHOTO_LEARNING_QUALIFICATION_REPORT`, `PHOTO_LEARNING_QUALIFICATION_SIGNATURE`, `PHOTO_LEARNING_TRUSTED_PUBLIC_KEY` (raw 32-byte Ed25519 key), `PHOTO_LEARNING_PACKAGES_LOCK`, `PHOTO_LEARNING_TRUSTED_ISSUER_ID` and `PHOTO_LEARNING_EVIDENCE_ROOT`. The signed report's issuer must exactly match this deployment-owned identifier as well as verify under the trusted key. The operation is disabled when all are absent and refuses partial configuration or non-CUDA workers. `build_worker` resolves this request after constructing the existing GPU ModelPool and registers `learning.evaluate` only after the signed factory passes. No qualification report or trusted production key is bundled or fabricated by this repository; the path has not been executed on CUDA, and SQL capability/real-image acceptance remain separate gates.

The CLI retains the exact report, signature and trusted-key paths and supplies a callback that rereads all three before every factory verification. Removal, symlink substitution or byte changes reject the task as `CONFIG_INVALID` through the installed provider, so process restart is not required to stop using a rotated trust bundle. Package-lock bytes and the installed Python source are independently rehashed by the qualification reader. Unit refusal sources for rotation were authored but not run.
At CLI startup, the report, signature, key and package-lock paths are opened with no-follow semantics and a per-file byte cap; `fstat` on the opened descriptor controls the read. This closes a `stat`/`read` replacement window for those initial trust-file reads. The package-lock reader still checks its signed SHA during each verification.
An authored integration-style unit case builds a real Ed25519-signed report, physical evidence files and model weights, installs through the signed factory with a fake CUDA device observation, then changes a weight and requires the next verification to fail. It has not been run and does not stand in for native CUDA or photographic qualification.


## Authored denoise installation

PinnedColorHoldoutProvider accepts optional denoise_provider=NativeDenoiseProvider with the same ModelPool and CUDA backend. Installation must supply qualified provider_peak and verify_runtime. Each style is rendered through production SCUNet denoise before color and beauty, strength=denoise_strength*style.strength once. Model ID/lock and execution resource envelope are mandatory. All-off restoration is identity; upscale still refuses. Reviewed sensor dust uses a separate frozen replay path and cannot be combined with denoise. The evaluate scratch envelope now reserves one sequential denoise RGB buffer. Authored pixel parity/refusal/cancellation scenarios are NOT RUN; this connection does not qualify a full renderer.


## Same-canvas background

Holdout supports keep/solid/transparent with actual pinned LRASPP person segmentation. Composition follows color/beauty and production linear-light solid/transparent math; uint16/float32 source opacity combines with subject coverage. Positive protection restores original RGB/alpha bits. Triplet background modules must match to share output alpha. Subject confidence below .75 refuses. Blur requires pinned depth, asset requires frozen background lineage, generation requires accepted output: these remain unconnected and refuse. Authored parity/refusal/binding scenarios NOT RUN.


## Pinned blur depth

PinnedColorHoldoutProvider now accepts depth_provider=HoldoutDepthProvider.create(pool, backend="cuda", verify_runtime=..., provider_peak=...). Pool must be the same installed ModelPool. DepthAnythingV2-small uses the exact production work-to-model and cubic/minmax normalization shared with depth.predict; component inventory now includes operations/depth/prepare.py, requiring new runtime qualification hashes. Flat depth is not measurable. Any source alpha==0 refuses because the production blur stage does not accept invalid depth masks. Production prepare_blur executes after beauty with blur_strength*style.strength once; source alpha is retained and positive protected pixels restore exact original RGB. Admission includes full halo support, model peak and retained depth/blur scratch. Ten authored scenarios NOT RUN. Historical statements that blur is unconnected describe prior implementation; asset/generation and full effect qualification remain open.
