# Удержание квоты во время очистки перед retry

Статус: принятый implementation contract для исправления P0.6.04/P0.6.06; реализация 02541 в работе. Это не результат выполненных проверок.

## Наблюдаемый конфликт

Shown Apply резервирует объём на один час. Pending output сохраняет трёхчасовой quiet period перед очисткой. Простое ожидание очистки в retry_wait не позволяет вернуть квоту: резерв истекает раньше. Task.deadline является сроком одной попытки и обновляется при claim; применять его как абсолютный срок ожидания cleanup нельзя. У run абсолютного deadline сейчас нет.

## Правило

Scheduler продлевает только существующий, ещё не истёкший run reservation, когда текущая задача находится в retry_wait и её предыдущие output allocations ещё не возвращены. Tenant/run/user principal и immutable reservation identity должны оставаться действующими; cancellation/terminal run не допускают продление. Продление не изменяет bytes/files, tenant usage или лимит квоты и не создаёт новый резерв.

Предел ожидания — latest outstanding allocation.created_at + 4 часа: существующие три часа quiet period плюс час на подтверждение очистки. created_at берётся из сохранённой allocation, а не из изменяемого cleanup_after. Каждый шаг продления ограничен 15 минутами и абсолютным пределом. Истёкший резерв не оживляется. Новая попытка не расходуется, пока соответствующие allocations ожидают settlement.

После физически подтверждённой очистки возврат в резерв выполняется ровно один раз под canonical locks. При неизвестном результате удаления возврата нет. Если очистка не подтверждена до предела, продление прекращается; система должна показывать причину ожидания/истечения и сохранять учёт занятого объёма до settlement. Увеличивать лимит tenant ради recovery нельзя.

## Подключение и сценарии

Продление вызывается scheduler до отбора задач на activation: discovery filter пропускает ожидающие задачи, поэтому помещать продление только внутрь activation недостаточно. Под lock повторяются identity/state/expiry/bound predicates; renewal и settlement должны сериализоваться с cancellation/release. Startup проверяет установленный ABI и закрытые ACL.

Нужны сценарии: один час→продление→три часа→подтверждённая очистка→тот же retry; отсутствие подтверждения→истечение четырёхчасового предела; expired/terminal/cancelled/wrong-principal отказ; параллельные renewal/refund/release; отсутствие изменения bytes/files/usage; отсутствие расхода нового attempt во время ожидания. Проверки отложены до общей фазы тестирования.
