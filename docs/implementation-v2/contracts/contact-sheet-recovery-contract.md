# ContactSheet uncertain admission and closure

The original normalized `ContactSheet.Create` request is `{selection_snapshot_id, locale, columns, rows}`. Its original Idempotency-Key and body remain immutable while the result is unknown. Resource refusals, timeouts and cancellation do not prove absence of an earlier accepted run and cannot erase that intent.

`POST /api/v1/tenants/{t}/contact-sheets/abandon` takes that same body and key. Current tenant/project Editor and the selection's exact user principal are required before and after receipt waits, including accepted replay and expired selections. It uses the same `ContactSheet.Create` receipt identity and lock as normal admission, without allocating font resources, checking fresh worker qualification or requiring a live selection expiry. No new domain row lock precedes the receipt lock.

If admission committed first, response 202 is the original strict `{run_id,status:"queued"}` receipt. Its resource ID must equal the canonical response run ID; the persisted run must be an export owned by this actor with the exact input snapshot and contact-sheet config selection/locale/columns/rows. This proof is repeated even when the receipt already has a parent binding. No run is cancelled or deleted.

If abandonment commits first, response 200 is `{status:"abandoned",key,selection_snapshot_id}`, with no resource ID and a `selection:<uuid>` parent binding. Its retention is explicitly extended to year 9999 under the receipt lock, including an existing unsealed row. Normal admission recognizes the tombstone in its locked replay path before font preparation and again after transactional Use, returning typed 409 `CONTACT_SHEET_ABANDONED`; it cannot create a later run. A concurrent preparation may already be in flight after an earlier replay miss, but its final receipt gate cannot admit a run after abandonment wins.

The Collection client stores the original intent before POST. A validated accepted receipt is retained in the current scoped component before awaiting local persistence; known acceptance uses run GET recovery. Verified navigation is published before local acknowledgement. Only the exact confirmed 200 abandonment clears a pending local journal. A persisted closed-key acknowledgement prevents a stale browser context from restoring that intent; logout generation fences remain active. UI Stop releases waiting and keeps the uncertain request. Closure uses a bounded 15-second flight and the Collection's shared exact-token mutation lock. Initial selection creation cannot submit a ContactSheet job before the immutable job intent exists, so it does not require a combined selection/job abandonment protocol.

Source candidate only: authored unit, decoder/store/mounted and application-role PostgreSQL scenarios are not executed. Physical processing, photo quality and deep concurrency qualification remain for the agreed test phase. No new migration, DELETE privilege, counter mutation or cancellation semantic is introduced.
