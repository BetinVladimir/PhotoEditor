## Итоговое мнение

**Сильные стороны.** Инженерные инварианты проработаны глубже, чем у типичного MVP: fencing-токены и lease задач, transactional outbox, quorum-очереди RabbitMQ, идемпотентные мутации, изоляция tenant на уровне SQL-ролей/ACL, mTLS между worker и object-gateway, неизменяемость оригиналов, версионированные модели и ICC-профили, «fail closed» при недоступности модели/квалификации. Обе клиентские части компилируются без ошибок типов (проверено: `tsc --noEmit` для `apps/portal` и `apps/photographer` — 0 ошибок). Тестовая база очень большая (по грубому подсчёту ≈6 000 Go-тестов, ≈7 000 Python-тестов, ≈2 800 JS/TS-кейсов).

**Главные проблемы (по убыванию влияния на MVP).**

1. **Worker не рассчитан на VPN-разрывы и жёстко связан с PostgreSQL.** GPU-воркер подключается напрямую к PostgreSQL (≈100 SQL-функций как ABI), к RabbitMQ и к object-gateway. Любой одиночный сбой heartbeat (задачи или ёмкости) останавливает воркер и бросает идущую GPU-задачу; результат не буферизуется; загрузка/выгрузка артефактов без докачки. Требование «полностью асинхронно по VPN» не выполнено на уровне устойчивости, хотя pull-модель (воркер сам ходит к серверу) ему соответствует. → [MVP/01](MVP/01-worker-and-vpn.md).
2. **Нет воспроизводимого пути «собрать → развернуть → проверить».** Нет CI; e2e для web-приложений отсутствуют в репозитории (только разрозненные скрипты в игнорируемом `work/`); `make test` не запускает ни web-тесты, ни интеграционные тесты с БД; 413 Go-файлов и 76 Python-файлов тестов зависят от `PHOTO_TEST_DATABASE_URL`; в документации ≈300 записей «tests authored NOT RUN». → [MVP/06](MVP/06-testing-ci-e2e.md).
3. **Обработка фото в «боевом» контуре не включена и топология не соответствует целевой.** Развёртывание — один узел Docker Compose; PostgreSQL/RabbitMQ/MinIO в единственном экземпляре; scheduler остановлен; БД на проде на миграции 2597 при нумерации до 02659 в репозитории; у RabbitMQ в compose/provision нет TLS, а worker в production принимает только `amqps://`. VPN/кластерная схема нигде не описана. → [MVP/05](MVP/05-deploy-and-ops.md).
4. **Избыточная сложность и стоимость сопровождения.** 2 626 файлов миграций (нумерация до 02659; крупные — 80–170 КБ), 60+ «installation»-команд, конструкторы воркера с ≈40 именованными параметрами, 55 «attempt-store» в клиенте, `OwnerAPI` с ≈200 методами, нет форматтера/линтера (2 271 строка >200 символов в production-коде photographer). Знание о системе живёт в 4 000+ каталогах доказательств `work/`, которые не версионируются.
5. **Расползание объёма MVP.** В приложении фотографа 42 экрана, включая отложенные функции (interchange, подпись C2PA, обучение стиля, tethering-съёмка). Защита от выпуска незавершённого опирается на серверные capability, а не на явный список маршрутов MVP. → [MVP/03](MVP/03-photographer.md).

**Отдельно — подтверждённый дефект безопасности/доступности (D-18).** API определяет IP клиента по `r.RemoteAddr` и не учитывает прокси-заголовки; за Caddy все клиенты выглядят одним адресом, поэтому лимит «20 OTP/час на IP» (`backend/internal/auth/service.go:144`) общий для всех — вход можно заблокировать всем сразу. Исправление — [MVP/02](MVP/02-backend-and-contracts.md), пункт B-0.

## Методология и ограничения (честно)

* Ревью **статическое**: код читался выборочно, но по всем уровням (worker runtime, gateway/queue/auth на стороне Go, оба клиента, deploy, документация). Проект слишком велик (≈377 тыс. строк Go без тестов, 110 тыс. строк Python в worker) для полного построчного разбора.
* **Запущено:** `tsc --noEmit` для `apps/portal` и `apps/photographer` — ошибок нет. **Не запущено:** Go-тесты (Go в окружении ревью отсутствует), Python-тесты (venv собраны под macOS), vitest (нативный rolldown только для darwin-arm64), e2e. Все числа о тестах — результат подсчёта по исходникам, а не прогона.
* Не оценивались: качество ML-результатов и художественная приёмка, юридические аспекты (C2PA, лицензии моделей), производительность на реальном GPU.
* Утверждения в файлах помечены ссылками на пути. Там, где вывод — гипотеза, это указано словом «проверить».
