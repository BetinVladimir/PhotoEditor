# MVP-07. Ревью программы доработок: достаточна ли она для выхода на MVP?

Дата: 2026-10-24. Оценивается план из [README.md](README.md) и файлов 01–06 относительно «Обязательных условий выпуска» из `docs/implementation-v2/mvp-web-release-plan-2026-10-20.md` и целевой топологии (серверный кластер + GPU по VPN, асинхронно).

## Вердикт

**Нет, не полностью.** План закрывает инженерную надёжность и проверяемость (≈80 % пути), но не закрывает часть условий выпуска, зависящих от данных, оборудования и процессов. Ниже — покрытие условий и недостающие пункты.

## 2. Чего не хватает

1. **Квалификация моделей и матрица камер/форматов (блокер, зависит от железа).** MVP-план запрещает объявлять поддержку без измерений, а большинство GPU-операций в статусе «awaiting_evidence». В моём плане есть только калибровочный каталог для scheduler (O-2) и упоминание в G-08. Нужен отдельный пакет: выбор 3–5 камер и форматов, корпус реальных съёмок (≥ 200 кадров, разные условия), прогон каждой включаемой операции на целевом GPU, фиксация `supported / experimental / unavailable` в `packages/contracts/mvp-operations.json`. Без него профиль MVP (B-4) нечем наполнить.
2. **Приёмка результата фотографом.** Технические проверки (SHA, ICC) не заменяют оценку качества. Нужны критерии: пороги по метрикам регрессии качества (T-8 сейчас P2 — поднять до P1), слепой просмотр 20–30 кадров 2–3 фотографами, правила отключения операции при провале.
3. **Purge tenant и удаление данных.** Условие №7 требует проверки purge с реальными ролями и объектным хранилищем. Добавить e2e-сценарий E-24: удаление проекта/tenant → оригиналы, производные, ссылки портала и очереди очищены; ошибка очистки не показывается как успех; сроки хранения.
4. **Многоузловая выдача задач.** Приёмка из `docs/implementation-v2/18-capacity-operations.md` требует: два узла не берут одну задачу, гибель узла после стадии, OOM-повтор, справедливость между tenant. В плане есть chaos сети, но нет сценария с 2+ воркерами (CPU и GPU, включая Mac). Добавить к W-11: `test_two_workers_lease_exclusivity`, `test_node_death_after_stage`, `test_oom_retry_tile256`.
5. **Ёмкость и стоимость GPU.** План не отвечает: сколько фотографов/кадров в час выдержит имеющийся GPU-парк, какая очередь допустима. Нужен расчёт: время операции × число операций на кадр × размер серии, лимиты на tenant (`tenant_heavy_queued`), решение о degraded-режиме при недоступности GPU (UI/портал продолжают работать — проверить в e2e: E-25 «GPU выключен»).
6. **Доставляемость почты.** Вход только по OTP через почту (SMTP-реле). Нужны SPF/DKIM/DMARC, мониторинг отказов, лимиты, запасной канал для поддержки; e2e-проверка на реальном почтовом ящике в staging.
7. **Безопасность перед открытием наружу.** В плане есть заголовки, rate-limit, IP. Не хватает: независимый аудит сотен `SECURITY DEFINER`-функций (владелец, `search_path`, ACL) — расширить `scripts/check-sql-function-syntax.py`; сканирование зависимостей на уязвимости поверх существующего SBOM (`make release-check` проверяет только дрейф); проверка сброса сессий и CSRF на каждом изменяющем маршруте; пентест-чеклист для портала (перебор `share_id`, повторное использование ссылок скачивания).
8. **Эксплуатационный минимум.** Runbook инцидентов (недоступен воркер, переполнен диск scratch, рост очереди, отказ брокера), дежурство, страница статуса, процедура отката релиза (forward-only миграции → откат только флагами и старым бинарником), политика обновления сертификатов. Частично в O-4/O-5, но как документы не оформлены.
9. **Юридический и продуктовый минимум.** Условия использования, политика конфиденциальности, согласия субъектов на обработку лиц (в системе есть consent lifecycle и распознавание лиц), хранение данных в ЕС. Не инженерная задача, но блокер публичного открытия; для закрытой беты — подписанные соглашения с участниками.

## 3. Риски самого плана

* **Допущение о сроках.** Оценки 3–4 разработчика × 10–14 недель — ориентир без учёта процессных издержек проекта (frozen-пакеты доказательств, независимые review, evidence-гейты). Если сохранить этот процесс для каждого изменения, срок вырастет кратно: ввести «лёгкий» режим для MVP-доработок (PR + CI вместо отдельных пакетов доказательств).
* **Зависимость от железа.** Этапы 2–4 требуют стенд с реальным WireGuard и GPU; без него W-11, O-2 (калибровка) и п. 2.1 не закрываются. Назначить владельца стенда и дату.
* **Не проверенные гипотезы.** R-05 (квота `localStorage` при импорте тысяч файлов), R-06 (хеширование больших RAW на клиенте), поведение `Cache-Control` портала — оценки основаны на чтении кода, нужны замеры в первую неделю.
* **Масштаб W-7.** Control-plane API для worker вынесен за MVP (этап 5). Это допустимо только при выполненных W-1…W-6 и W-4 (verify-full, пул, keepalive); иначе GPU-хосты остаются с прямым доступом к БД по VPN. Фиксировать как осознанный остаточный риск с датой пересмотра.
* **Единая точка отказа** до O-3: PostgreSQL/RabbitMQ. Для закрытой беты допустимо при проверенном восстановлении (RPO ≤ 15 мин / RTO ≤ 4 ч), для открытого запуска — нет.

## 5. Итог

С добавлением X-1…X-9 программа достаточна для выхода на **закрытую бету** (ограниченный круг фотографов, один GPU-парк, поддерживаемый список камер). Для **публичного MVP** дополнительно нужны O-3 (HA), W-7/W-8 и платный контур (B2–B4).
