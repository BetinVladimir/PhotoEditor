# Доработка MVP силами модели 35B с контекстом 64k (карточки рассчитаны с запасом на 32k)

> Исполнитель - агент OpenCode: см. **[OPENCODE.md](OPENCODE.md)** (рабочий режим). Разделы ниже про `tools/` описывают необязательный автономный раннер; формат SEARCH/REPLACE и `SYSTEM.md` нужны только ему.

Весь план из `01…07` разложен на **карточки** (`agent/tasks/*.md`): каждая — одна маленькая, самодостаточная правка с проверкой. Инструменты в `docs/review/MVP/agent/tools/` собирают для карточки промпт ≤ 17k токенов, применяют ответ модели и сами запускают проверки. Человек ревьюит diff каждой карточки.

## 1. Почему именно так (расчёт окна)

Карточки нарезаны так, чтобы промпт ≤ 17k токенов - это укладывается и в 32k, и с большим запасом в 64k. Целевое окно сейчас 64k (OpenCode); таблица ниже показывает худший случай 32k, её цифры остаются верными для автономного раннера `tools/`.

| Часть окна (худший случай 32k) | Токенов | Комментарий |
|---|---|---|
| Системная инструкция `SYSTEM.md` | ≈ 0,8k | формат ответа и правила |
| Карточка (цель, точная спецификация, тесты) | 0,8–3k | пишется человеком/сильной моделью заранее |
| Код-контекст (вырезки `путь::символ`) | 1–12k | только нужные функции, не файлы |
| **Потолок промпта** (`AGENT_PROMPT_BUDGET`) | **17k** | `agent.py check` падает, если карточка больше |
| Ответ модели (`LLM_MAX_TOKENS`) | 6k | ≈ 200–250 изменённых строк |
| Обратная связь после неудачи | ≈ 2,5k | хвост вывода упавшей проверки |
| Запас на ошибку оценки токенов (3 символа ≈ 1 токен) | ≈ 3k | |

Принципы, которые из этого следуют:

1. **Одна карточка — одна правка** (XS/S). Если спецификация не влезает в ≈ 3k токенов или нужно > 3 файлов — это не карточка, а задача на разбиение (`NOT-CODEGEN.md`).
2. **Контекст вырезается, а не загружается.** Карточка перечисляет `файл::Класс.метод`, `файл::функция` или `файл:10-80`; сборщик находит символ в текущем коде (Python, Go, TS/TSX). Файл целиком допускается, только если ≤ 300 строк.
3. **Каждая попытка независима (stateless).** При неудаче история не накапливается: промпт собирается заново из свежего кода + короткая выдержка из упавшей проверки. Окно не растёт.
4. **Модель не придумывает API.** Новые функции описаны в карточке сигнатурой и правилами; чужие — видны в контексте. Если данных нет, модель обязана ответить `BLOCKED: …`.
5. **Проверка детерминирована.** Карточка = команды `verify`. Тест пишется в той же карточке; golden-тесты и «source pins» проекта используются как сетка безопасности.
6. **Формат ответа — SEARCH/REPLACE**, а не diff: так надёжнее для моделей этого размера; применитель требует ровно одно совпадение, всё-или-ничего, проверяет синтаксис `.py`/`.json`, ограничивает список файлов картой карточки.
7. **Откат автоматический:** неудачная попытка возвращает файлы к исходному состоянию.

## 2. Запуск

Требуется Python ≥ 3.8 (стандартная библиотека). Проверки карточек используют окружение проекта: перед запуском `make setup-platform` и активируйте `.venv-platform` (worker), для TS — `npm ci` в приложениях, для Go — `go` в PATH.

```bash
export LLM_BASE_URL=http://localhost:8000/v1   # любой OpenAI-совместимый сервер (vLLM, llama.cpp, LM Studio)
export LLM_MODEL=<имя модели>                  # temperature=0.1, max_tokens=6000 по умолчанию
python3 docs/review/MVP/agent/tools/agent.py check           # валидность всех карточек и бюджет токенов
python3 docs/review/MVP/agent/tools/agent.py list            # статус
python3 docs/review/MVP/agent/tools/agent.py next            # следующая готовая карточка
python3 docs/review/MVP/agent/tools/agent.py run W-1a        # промпт → модель → применить → проверки (до 3 повторов)
git diff                                       # человек смотрит правку
git commit -am "agent(W-1a): extract heartbeat loop"
```

Без API: `agent.py prompt W-1a > p.txt` → вставить в любой чат → ответ в файл → `agent.py apply W-1a ответ.txt` → `agent.py verify W-1a` → `agent.py done W-1a`.

После 3 неудачных попыток карточка получает статус `blocked` (причина в `STATUS.json`, ответы моделей — `work/agent-<ID>-<n>.txt`). Дальше: уточнить спецификацию карточки или передать её крупной модели/человеку. **Не повышайте лимиты и не расширяйте список файлов, чтобы «пропихнуть» карточку.**

## 3. Правила для человека-ревьюера

* Один коммит на карточку, сообщение `agent(<ID>): <заголовок>`.
* Карточки с общими файлами не запускать параллельно (смотрите поле `edit`); независимые — можно.
* Красный тест, найденный карточкой-аудитом (`P-4b`, `P-6a`), — результат, а не поломка: чинить отдельной карточкой.
* Осторожные места: `workers/tests/test_heartbeat_chain_source_pins.py` (текстовые срезы `database.py`), тесты, читающие исходники (`readFileSync`), `ui-message-keys.json`, golden-файлы. Карточки, затрагивающие их, содержат соответствующую проверку.
* Нельзя удалять код, миграции, файлы доказательств — применитель этого не умеет, но следите за `FILE:`-блоками, которые «заменяют» функцию пустотой.
* Прогон `make verify` и CI — обязательны после каждого этапа (A…E), без исключений: карточные проверки локальны.

## 4. Как писать новую карточку

Файл `agent/tasks/<ID>.md`:

```
---
id: <ID>              # = имя файла
title: <одна строка>
area: worker|backend|portal|photographer|ops|tests
size: XS|S            # больше нельзя
depends: [<ID>, ...]  # опционально
edit:                 # единственные файлы, которые можно менять; "(new)" для новых
  - path
  - path/new_file.py (new)
context:              # что показать модели (только нужное)
  - workers/photo_worker/runtime/executor.py::Executor.process
  - backend/internal/httpapi/server.go:96-126
verify:               # команды, ВСЕ должны завершиться с кодом 0
  - cd workers && python -m pytest tests/test_x.py -q -p no:cacheprovider
---
## Goal  (зачем, 2–4 строки)
## Spec  (точные сигнатуры, имена, правила; для хитрой логики — эталонный фрагмент)
## Test  (какие тесты, какие значения)
## Do not (чего не трогать)
```

Хорошая карточка: названы все новые имена; указаны ожидаемые значения в тестах; перечислены «нельзя»; нет слов «при необходимости», «аккуратно», «по аналогии» без ссылки на конкретный код. После написания — `agent.py check` (бюджет, символы, зависимости) и `agent.py prompt <ID> --stats`.

Если в карточке нужен код, которого ещё нет (создаётся зависимостью), он автоматически считается «планируемым» — сборщик подставит заглушку для оценки размера; реальный фрагмент подтянется после выполнения зависимости.

## 5. Ограничения инструментов

* Поиск символов эвристический (регулярные выражения + баланс скобок). Для очень плотных TSX-файлов с длинными строками вырезка может быть шире нужного — используйте диапазон `файл:a-b`.
* `agent.py` не умеет параллельный запуск и не коммитит сам.
* Оценка токенов — по символам (3 символа ≈ 1 токен). Для вашего токенайзера проверьте реальный размер `agent.py prompt ID | wc -c` и при необходимости измените `AGENT_CHARS_PER_TOKEN`.
* Эти инструменты проверены на устройстве только синтаксически и dry-run-ом на реальных карточках; ни одна карточка ещё не выполнялась реальной моделью.
