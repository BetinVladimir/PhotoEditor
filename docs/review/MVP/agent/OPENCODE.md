# Выполнение карточек агентом OpenCode (модель 35B, окно 64k)

OpenCode сам читает файлы, правит их и запускает команды, поэтому формат SEARCH/REPLACE из `SYSTEM.md` и папка `tools/` ему **не нужны** (оставлены как необязательные). Карточки из `tasks/` используются как есть: агент читает карточку, затем только перечисленные в ней куски кода.

## 1. Главный риск: окно съедается не карточкой, а самим агентом
Системный промпт OpenCode, описания его инструментов и накопленные результаты вызовов занимают в окне заметно больше, чем карточка. Чтобы остаться в пределах окна:

| Мера | Как |
|---|---|
| Одна карточка = одна новая сессия | не продолжать диалог между карточками; окно каждый раз чистое |
| Урезанный агент | свой агент с минимумом инструментов: `read`, `edit`, `write`, `bash`, `grep`, `glob`; отключить `webfetch`, `task`/субагенты, todo и прочее |
| Короткий промпт агента | текст из раздела 2 (≈ 300 токенов), без общих «советов» |
| Чтение по диапазонам | читать не файл, а строки из `context:` карточки (`read` с offset/limit); большие файлы целиком не читать |
| Усечение вывода команд | проверки запускать с `| tail -40`; полный лог не выводить |
| Автосжатие истории | включить компакцию контекста при ≈ 70% окна (порог в конфиге OpenCode), но карточки должны укладываться и без неё |
| Лимит ответа | `max_tokens` ответа ≈ 4–6k |

Бюджет при окне 64k (грубо):

| Часть | Токенов |
|---|---|
| Служебное OpenCode (промпт, описания инструментов) | 10-12k |
| Карточка и промпт агента | ≈ 3k |
| Чтение кода по `context` | до 17k |
| Вывод проверок и до 3 повторов | 10-15k |
| Ответ и правки | ≈ 10k |
| **Итого** | **≈ 45-55k** |

Одна карточка целиком помещается в одну сессию без компакции, даже с тремя повторами. Если карточка не помещается, это сигнал разбить её, а не поднимать лимиты. Не заполняйте окно до конца: на длинном контексте модель 35B хуже держит инструкции.

Что можно ослабить относительно режима 32k: читать файл целиком до 300 строк (вместо вырезок), не так жёстко обрезать вывод проверок (`tail -80`). Карточки XS/S менять не нужно. Фактический расход окна проверьте на первой карточке (W-1a) и только потом объединяйте мелкие карточки.

## 2. Промпт агента (вставить в конфигурацию агента `card`)
```
Ты исполняешь ровно ОДНУ карточку задачи из репозитория. Больше ничего не делай.
1. Прочитай файл карточки. Её поле `edit` - единственные файлы, которые можно менять; `context` - единственное, что нужно читать (читай диапазонами, не файлы целиком).
2. Если для задачи не хватает данных - остановись и напиши `BLOCKED: <чего не хватает>`. Не угадывай API и имена.
3. Вноси минимальные правки в стиле окружающего кода. Не форматируй, не переименовывай, не удаляй существующее (код, тесты, миграции).
4. Тесты из карточки пиши в той же сессии. Затем запусти команды `verify` по очереди, вывод обрезай (`| tail -40`).
5. Если проверка упала - исправь причину и повтори, не более 3 попыток. Потом остановись и опиши остаток словами.
6. Финал: одна строка `DONE <ID>` или `BLOCKED <ID>: причина`, затем список изменённых файлов. Не коммить.
```

## 3. Запуск
Пример (имена флагов уточните по вашей версии OpenCode):
```bash
opencode run --agent card "Выполни карточку docs/review/MVP/agent/tasks/W-1a.md"
git diff                       # человек смотрит правку
git commit -am "agent(W-1a): <заголовок карточки>"
```
Порядок карточек - в `INDEX.md`; готовность по зависимостям проверяйте глазами по полю `depends` (команда `next` из `tools/` необязательна). Перед запуском следующей карточки убедитесь, что предыдущая зелёная и закоммичена.

## 4. Что изменяется в карточках при работе через OpenCode
* Поле `context` = «что прочитать». Строки вида `путь::Класс.метод` агент находит поиском по имени (`grep -n "def метод"`), строки вида `путь:10-80` читает по диапазону.
* Фразы «ответьте блоками SEARCH/REPLACE» и «`BLOCKED: need ...`» читать как «правь инструментом редактирования» и «остановись с сообщением».
* Команды `verify` выполняются самим агентом; результат всё равно проверяет человек (`git diff`, CI).

## 5. Практические советы для модели 35B
* Не давать нескольких карточек в одной сессии и не просить «заодно» исправить соседнее.
* Для карточек, где нужен точный кусок кода (`XS` правки по подстроке, например `P-1c…P-1e`), в тексте карточки уже приведена точная подстрока - агент должен искать именно её.
* Если агент начинает читать много файлов подряд - это признак, что карточка недоопределена; остановить, уточнить `context`/`Spec`.
* Любой `BLOCKED` обрабатывает человек или более крупная модель; карточку после уточнения запускают заново в новой сессии.

## Карточки с инструментом (код не перепечатывается)

Если в карточке есть команда `python3 docs/review/MVP/agent/tools/<tool>.py ...`, агент **запускает её** (сначала `--dry-run`), не правит перенесённый код вручную и при `REFUSED:` отвечает `BLOCKED: <сообщение>`. Инструменты детерминированы и сами проверяют скобки/импорты:

| Инструмент | Для чего | Карточки |
|---|---|---|
| `move_routes.py` | блок маршрутов из `catalogRoutes` в отдельный метод (Go) | `B-5m-*` |
| `move_methods.py` | методы `class OwnerAPI` → функции `src/api/<домен>.ts` + фасады (`--prepare`, `--list`) | `P-5p`, `P-5m-*` |
| `extract_stmts.py` | диапазон операторов Python → функция | `W-9m*` |
| `endpoint_info.py` | контракт и типы эндпоинта для разведки | `T-2e*r` |
| `cards_from_plan.py` | утверждённый план (`notes/*-plan.md`) → карточки извлечения, цепочка снизу вверх | после `P-9-plan`, `B-6-plan`, `B-7-plan` |
| `make_index.py` | пересобрать `INDEX.md` (`--check` для CI) | - |

Ворота человека (`APPROVED-BY`, проверка плана) перечислены в конце `INDEX.md`; чек-листы - в `NOT-CODEGEN.md`.
